# 保存データをプロジェクトとモジュールに分ける（計画）

状態: **計画中**

- 段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../docs/workflow.md)の「実装を始める合図」）。
- 決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../docs/documentation.md)の「計画の文書」）。

## 目的

保存データの形式を、**プロジェクトの形式**と**モジュールの形式**の 2 つに分け、どちらも v1 から数える。今の形式（プロジェクトとモジュールが一体の形式。v1〜v4）は v4 で終わりにし、v4 のデータは、プロジェクト v1 とモジュール v1 に変換して読む。

- モジュールの形式: 回路 1 つ分の中身（`id`、名前、パッケージ、シートの大きさ、部品と配線）。メイン回路もこの形式で持つ。
- プロジェクトの形式: プロジェクトの構造（どのモジュールが入っているか、並び、フォルダ）。モジュールは中に持つ（インライン）か、`id` で参照する（下の「プロジェクトの形」）。

あわせて、モジュールの形式 v1 の中身を、今の一体の形式 v4 から次のように変える（もとは計画 17「保存データの version 5」で計画していたもの。2026-10-17 にこの計画にまとめた）。

- split のモジュールの外側のピンの順を、中の位置の順から、ポート番号の順にする（目的と画面の側は [split のピンの順をポート番号の順にする](../split-pin-order/plan.md)、計画 16）。
- メイン回路にもパッケージを持たせる（目的と画面の側は [メイン回路をモジュールと同じに扱う](../main-as-module/plan.md)、計画 18）。

解きたい課題: [プロジェクト管理機能](../project-management/plan.md)（計画 1）で、モジュールのファイル、未解決のモジュール、フォルダによる整理を作るには、モジュール 1 つを単独で扱える形式と、プロジェクトの構造を持つ形式が要る。

計画 1（上位の計画）の下位の計画の 1 つで、ほかの下位の計画（未解決のモジュール、モジュールのファイル、プロジェクトパネル）の土台になる。

## 前提

- 今の形式は、プロジェクトとモジュールが一体の version 4（2026-10-13 に公開）。保存データ（localStorage の `sazanka.project`）と共有用 JSON は、包み方だけが違い、中身は同じ形。
  - プロジェクトは回路の平らな並び（`circuits`）を持ち、先頭がメイン回路（`id` は `"main"`）。部品はモジュールを `id` で指す。
  - split のピンの順は、形式の文書（`docs/format/v4.md` の「モジュールのピン」）で「座標の順」と決めている。
  - メイン回路は名前とパッケージを持たない。モジュールのパッケージは省略できない（既定値で補うと、既定値を変えたときに古いデータのピンの位置が変わるため）。
- モジュールは `id` だけで識別する（計画 1 の「決めたこと」）。回路の `id` は UUID の形で、プロジェクトをまたいでも重ならない。
- 位置の順を使っている所（`circuit/module.ts`）:
  1. `getPortsInPinOrder` の split の分岐: split の外側のピンの順。展開（`simulation/flatten.ts`）とシート上の配置（`getPinout`）がこれを使う。**この計画で番号の順に変える**。
  2. `assignPortNumbers`: 置いた・貼り付けたポートが複数あるとき、番号を付ける順。番号を振る処理なので位置の順のまま。
  3. `fillPortNumbers`: 読み込みで、番号がない・重なるポートに番号を付け直す順。同じく位置の順のまま。
  4. `listPortsInPositionOrder`: 「上から順に割り当て直す」の割り当て順（位置の順のまま。split から DIP / QFP に変えたときは計画 16 でポート番号の順にする）。
- メイン回路を特別に扱っている計算: 検証（`circuit/project.ts` の `checkCircuit`。モジュールにだけ名前とパッケージを求める）、保存の形との変換（`file/storage.ts`。メイン回路の名前を書かない・捨てる）、空のプロジェクト（`emptyProject`。メイン回路にパッケージがない）。置いたポートへのピン番号の付け方（`assignPinNumbers`）は、パッケージがないものを split と同じに扱う。
- [保存データ](../../docs/persistence.md)の「開発者からの指示」に、「保存データと共有用 JSON の版は別々の番号。片方だけ上げることになったら、文書の分け方を開発者に相談する」とある。形式を 2 つに分けるので、この決まりも直す。

## 決めたこと

開発者が決めたこと。

形式の分け方（2026-10-17）:

- 保存データを、プロジェクトの形式とモジュールの形式に分ける。どちらも v1 から数える。
  - 一体の形式（v1〜v4）は v4 で終わり。v4（とそれより古い版）のデータは、今までの変換（`upgradeV1`〜`upgradeV3`）で v4 にしてから、プロジェクト v1 とモジュール v1 に分けて読む。
  - 一体の形式と新しい形式は、データの形で見分ける（新しい形式は `format` を持つ。一体の形式は持たず、いちばん外の `version` と、`project` の中の `circuits` を持つ）。番号（`version: 1` など）だけでは見分けない。下の「ファイルの見分け方」。
  - 採らなかった案: モジュールの形式は一体の形式の続きとして v5 から数える（番号は重ならないが、モジュールの形式の v1〜v4 は単独では存在しなかった）。
- プロジェクトは、モジュールを `id` で識別する（中に持つモジュールも `id` を持ち、参照だけの要素は `moduleId` で指す）。
- メイン回路も、モジュールの形式として持つ。メイン回路の `id` は今までどおり `"main"` に固定する。プロジェクトに「どれがメイン回路か」の項目は持たず、`id` が `"main"` のモジュールがメイン回路で、プロジェクトに必ず 1 つある、とする。
  - 理由: 今のコードは、メイン回路かどうかを `id` で判定している。固定しておけば、古いデータからの変換も、判定もそのまま使える。同じ情報を 2 か所に持たないので、食い違いが起きない。シミュレーションは、開いている回路をいちばん外側として動かすので、メイン回路を入口として特別に扱う処理はない。
  - 採らなかった案: ほかのモジュールと同じく UUID にする。プロジェクトに「どれがメイン回路か」の項目を持つ（判定のたびにプロジェクトを引く）。モジュールに「メイン回路」のフラグを持つ（2 つに立つ・どれにも立たない、という壊れた状態がありうる）。
- この計画を、計画 1 の下位の計画として作る。未解決のモジュール、モジュールのファイル、プロジェクトパネルより先に進める（それらの土台になるため）。
- ブラウザの中での保存（localStorage）は、今と同じく 1 つのキーに入れる。中身は、モジュールをインラインで持つプロジェクトのデータ（プロジェクトとモジュールが、それぞれ自分の版を持つ）。形式は分けても、保存の場所は分けない。
  - 採らなかった案: モジュールごとにキーを分ける（例: `sazanka.module.<id>`）。
- 共有用 JSON（プロジェクト全体の書き出し）は、今と同じく 1 ファイルで受け渡せるようにする（下の「プロジェクトの形」のとおり、モジュールをプロジェクトの中にインラインで持つ）。
- 計画 17（保存データの version 5）は、この計画にまとめた。version 5 はなくなる。
- 形式の文書は、`docs/format/project/v1.md` と `docs/format/module/v1.md` を新しく作る。一体の形式（v1〜v4）は `docs/format/archive/` に置く（今の `docs/format/v4.md` も `archive/` に移す）。
  - 採らなかった案: 1 つの文書の中で、プロジェクトの形式とモジュールの形式を節で分ける。
- ブランチは `new-format`。計画 19、18、16 を、このブランチで順に進める。

プロジェクトの形（2026-10-17）:

- プロジェクトは、要素の平らな並び（`modules`）を持つ。並びは、プロジェクトパネルの並び。要素は、モジュールとパス（フォルダ）の組。木構造にはしない（フォルダはパスから組み立てる）。
  - 要素は、モジュールのデータをそのまま中に持つ（インライン）か、`id` で参照するだけか、のどちらか。
    - インライン: `module` に、モジュールの形式のデータ（版を含む）をそのまま入れる。`id` はモジュールのデータの中にあるので、要素には書かない（2 か所に書くと食い違うため）。
    - 参照だけ: モジュールの `id` を `moduleId` に書く。中身がプロジェクトの中にないので、未解決のモジュールになる（[計画 20](../unresolved-module/plan.md)）。項目名を `id` にしないのは、要素そのものの `id` に見えないようにするため（2026-10-17）。
  - インラインのモジュールも、モジュールの版を持つ。モジュールのファイルとまったく同じ形にして、書き出しと持ち込みを、中身を移すだけで済ませるため。採らなかった案: 版を持たせず、プロジェクトの版に従う。
  - フォルダはプロジェクトが決める（モジュールのデータは、どこに置かれるかを知らない）。同じモジュールを、別のプロジェクトでは別のフォルダに置ける。空のフォルダは作れない（最初は要らない）。
  - 採らなかった案: フォルダの木構造で保存する（形が込み入る）。
- 要素のパスは、フォルダの部分だけを持つ（例: `"adders"`。メイン回路のようにフォルダに入れないものは `""`）。モジュールの名前はモジュールのデータが持つ。名前はモジュールのファイルと一緒に持ち運ばれ、フォルダは置き先のプロジェクトが決める、という分け方になる（2026-10-17）。
  - 採らなかった案: パスに名前まで含める（例: `"adders/full-adder"`。名前をプロジェクトが持つことになり、持ち込むときに名前をどこから取るかを別に決めることになる）。
- 参照だけの要素（中身のない要素）は、形式の文書には書くが、この計画のアプリでは、読み込むときに断る（今の `MISSING_MODULE` と同じ扱い）。開けるようにするのは、[未解決のモジュール](../unresolved-module/plan.md)（計画 20）で行う。アプリが書き出すデータには、参照だけの要素は出てこない（2026-10-17）。
  - 採らなかった案: この計画で、未解決のモジュールとして開けるところまで作る（範囲が大きくなる）。
- メイン回路は、今と同じく `name` を持たない（表示言語の名前で出す）。ほかのモジュールは `name` が要る（2026-10-17）。
- 作者名は、モジュールごとに持つ（モジュールの形式の項目 `author`。入れていなければ持たない）。回路設定（[計画 18](../main-as-module/plan.md)）で入れられるようにする（2026-10-17）。作者名はモジュールのファイルと一緒に持ち運ばれる。
  - 採らなかった案: 今と同じく、プロジェクトの項目として持つ。
  - プロジェクトの作者名はやめる（2026-10-17）。書き出しのダイアログの「作者名」の欄はなくし、回路設定で入れる。採らなかった案: プロジェクトにも作者名を残す（作者名が 2 か所になる）。
  - 古いデータ（一体の形式）のプロジェクトの作者名は、すべてのモジュール（メイン回路を含む）の作者名に写す（2026-10-17）。採らなかった案: メイン回路の作者名にだけ移す。
  - 作者名の入ったデータを読み込んだときのお知らせ（今の「『〇〇』さんの回路を読み込みました。」）はやめる。作者名は回路設定で見られれば足りる（2026-10-17）。採らなかった案: メイン回路の作者名でお知らせを出す。作者名の入ったモジュールをすべて並べる。
- パスの決まり（2026-10-17）: 区切りは `/`。フォルダに入れないものは `""`。先頭と末尾の `/`、空の部分（`a//b`）、`.`、`..` は使えない。部分の中は、`/` 以外ならどの文字でもよい（日本語や空白も使える。モジュールの名前と同じく）。大文字と小文字は区別する。長さの上限は決めない。
  - 採らなかった案: 部分に使える文字を、英数字と `-`、`_` に限る（日本語のフォルダ名が使えない）。
- 包み（プロジェクトとモジュールを入れる外側の入れ物）は作らない。保存データと共有用 JSON は、プロジェクトの形式のデータそのものにする。
  - 採らなかった案: 包みに、プロジェクトとモジュールの一覧を別々に並べる（インラインで持てるので要らない）。包みにも版を持たせる。

- 部品（`kind` が `"module"`）がモジュールを指す項目も、`module` から `moduleId` に変える（モジュールの形式 v1。2026-10-17）。モジュールを `id` で指す項目を、要素でも部品でも `moduleId` にそろえるため。要素の `module`（モジュールのデータそのもの）と、名前が同じで中身の種類が違う、ということもなくなる。一体の形式 v4 からの変換（`upgradeToProjectV1`）で付け替える。
  - `module` という名前は、version 3 のときに「モジュールをパスで指す案になっても名前がずれないように」と選んだもの。`id` だけで識別すると決めたので、その理由はなくなった。
  - 採らなかった案: 部品は `module` のまま。
- ファイルの見分け方: プロジェクトとモジュールのデータに、種類を表す項目 `format` を持たせる。値は、プロジェクトが `"sazanka-project"`、モジュールが `"sazanka-module"`（2026-10-17）。インラインのモジュールにも入る（モジュールのファイルとまったく同じ形のため）。古い一体の形式は、この項目がないことと、中身の形（いちばん外の `version` と `project` の中の `circuits`）で見分ける。
  - 項目名を `kind` にしない理由: `kind` は、要素（部品と配線）の種類と、パッケージの形の種類に使っている。データの形式を表す項目は、別の名前にして取り違えを防ぐ。
  - 採らなかった案: 項目名を `kind` にする。プロジェクトだけに目印を持たせ、モジュールは形で見分ける。今の目印の `"app": "sazanka"` をそのまま使う。

叩き台（`...` の所は形式の文書を書くときに決める）:

```json
{
  "format": "sazanka-project",
  "version": 1,
  "modules": [
    { "path": "", "module": { "format": "sazanka-module", "version": 1, "id": "main", ... } },
    { "path": "adders", "module": { "format": "sazanka-module", "version": 1, "id": "7b3e…", "name": "全加算器", ... } },
    { "path": "adders", "moduleId": "c91a…" }
  ]
}
```

モジュールの形式 v1 の中身（もとは計画 17 で決めたもの）:

- split の外側のピンの順を、ポート番号の順にする。入力は入力のポート番号の順、出力は出力のポート番号の順（2026-10-14）。
  - 採らなかった案: split は位置の順のまま、取り決めの例外にする（版を上げずに済み、番号を変える操作も要らないが、ポートを動かすとピンが入れ替わる課題が残る）。
- 一体の形式 v4 のデータを分けるときに、split のモジュールの中の INPUT / OUTPUT のポート番号を、入力と出力で別々に、1 から位置の順（上から、同じ高さなら左から）に振り直す。そのあとは番号の順でピンが並ぶので、今の配線は同じピンにつながったまま（2026-10-14）。
  - 飛びのある番号は詰まる。例: 番号が 1、3、4 で、位置が上から入力 4、入力 1、入力 3 なら、上から 1、2、3 になる。
  - 位置の順と番号の順がもともとそろっていて飛びもないモジュール（ふつうに上から置いたもの）は、番号が変わらない。DIP / QFP のモジュールは変えない。
  - 採らなかった案: 今ある番号の組はそのままに、位置の順に配り直す（上の例なら 1、3、4。変わる番号は少ないが、決め方が込み入る）。
- メイン回路にもパッケージを持たせる（2026-10-17）。メイン回路は「外側のピンがどこにもつながっていないモジュール」とみなす。DIP / QFP にしてピン番号を割り当てても、ピンはどこにもつながらない。メイン回路は、今までどおりほかの回路に置けない。
- メイン回路のパッケージも省略できない（モジュールと同じ）。変換では、メイン回路に split を書き込む（2026-10-17）。
  - 理由: モジュールのパッケージを省略できなくしたのと同じ（既定値で補うと、既定値を変えたときに古いデータの意味が変わる）。
  - 採らなかった案: 省略でき、ないときは split とみなす。
- 変換では、メイン回路のポート番号も、split のモジュールと同じく位置の順に振り直す（2026-10-17）。変換の決まりを、メイン回路とモジュールで同じにするため。メイン回路のピンはどこにもつながらないので、配線には響かない。シート上の「入力 1」などの表示が変わることはある。
  - 採らなかった案: メイン回路は振り直さない。

進め方（2026-10-17）:

- 新しい形式（プロジェクト v1 とモジュール v1）は、[保存データ](../../docs/persistence.md)の「版の状態」で「作業中（未公開）」として管理する。
- 新しい形式の中身は、まだ足されるかもしれない。足すものが出たら、この計画に書き足し、変換も直す。公開するまでは変換を直してよい（[保存データ](../../docs/persistence.md)の「開発者からの指示」）。
- 形式の版の決まりを、次のように直す（[保存データ](../../docs/persistence.md)の「開発者からの指示」。2026-10-17 に開発者が了承した。直すのは段階 1）。
  - 「保存データと共有用 JSON の版は別々の番号。片方だけ上げることになったら、文書の分け方を開発者に相談する」を、「プロジェクトの形式とモジュールの形式は、それぞれ版を持つ。保存データと共有用 JSON は、どちらもプロジェクトの形式のデータそのもの（版は同じ）」に替える。
  - 「1 版ずつの変換を順に通す」「一度作った変換は直さない（公開する前は直してよい）」「版ごとに文書を 1 つ」は、プロジェクトとモジュールのそれぞれに当てはめる。
  - 一体の形式（v1〜v4）の変換は、レガシーとしてコードを分けて置き（下の「ファイルの置き方」）、古い形式を読むためだけに残す。直さない。これから足す変換は、プロジェクトとモジュールの版を上げる変換として置いていく。

## 気になるところ

- 版の流れが 2 本（プロジェクトとモジュール）になると、古いデータを読む変換も 2 本になる。今の決まり（1 版ずつの変換を順に通す）を、それぞれに当てはめる。
- 新しい形式にすると、古い版のアプリ（もう公開していない）は新しいデータを読めない。今は最新版だけを公開しているので問題にならない（[保存データ](../../docs/persistence.md)の「形式を変えるとき」）。
- 変換でポート番号が変わったモジュールでは、シート上の「入力 1」などの表示が、前と違うポートに付く。配線とピンの順は保たれる。
- `fillPortNumbers`（読み込みで番号がない・重なるポートに付け直す）は位置の順のまま。新しい形式のデータで番号が重なっていたら、split のピンの順は、付け直したあとの番号の順になる。
- この計画だけを終えた時点では、split でピンの順を並べ替える手段がない（計画 16 で足す）。公開しないこと。
