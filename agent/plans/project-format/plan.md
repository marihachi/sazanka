# 保存データをプロジェクトとモジュールに分ける（計画）

状態: **進行中**

- 段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../docs/workflow.md)の「実装を始める合図」）。
- 決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../docs/documentation.md)の「計画の文書」）。

## 目的

保存データの形式を、**プロジェクトの形式**と**モジュールの形式**の 2 つに分け、どちらも v1 から数える。今の形式（プロジェクトとモジュールが一体の形式。v1〜v4）は v4 で終わりにし、v4 のデータは、プロジェクト v1 とモジュール v1 に変換して読む。

- モジュールの形式: 回路 1 つ分の中身（`id`、名前、パッケージ、シートの大きさ、部品と配線）。メイン回路もこの形式で持つ。
- プロジェクトの形式: プロジェクトの構造（どのモジュールが入っているか、並び、フォルダ）。モジュールは中に持つ（インライン。下の「プロジェクトの形」）。

あわせて、モジュールの形式 v1 の中身を、今の一体の形式 v4 から次のように変える（もとは計画 17「保存データの version 5」で計画していたもの。2026-10-17 にこの計画にまとめた）。

- split のモジュールの外側のピンの順を、中の位置の順から、ポート番号の順にする（目的と画面の側は [split のピンの順をポート番号の順にする](../split-pin-order/plan.md)、計画 16）。
- メイン回路にもパッケージを持たせる（目的と画面の側は [メイン回路をモジュールと同じに扱う](../main-as-module/plan.md)、計画 18）。

解きたい課題: [プロジェクト管理機能](../project-management/plan.md)（計画 1）で、モジュールファイル、未解決のモジュール、フォルダによる整理を作るには、モジュール 1 つを単独で扱える形式と、プロジェクトの構造を持つ形式が要る。

計画 1（上位の計画）の下位の計画の 1 つで、ほかの下位の計画（未解決のモジュール、モジュールファイル、プロジェクトパネル）の土台になる。

## 前提

- 今の形式は、プロジェクトとモジュールが一体の version 4（2026-10-13 に公開）。保存データ（localStorage の `sazanka.project`）とプロジェクトファイルは、包み方だけが違い、中身は同じ形。
  - プロジェクトは回路の平らな並び（`circuits`）を持ち、先頭がメイン回路（`id` は `"main"`）。部品はモジュールを `id` で指す。
  - split のピンの順は、形式の文書（`docs/format/v4.md` の「モジュールのピン」）で「座標の順」と決めている。
  - メイン回路は名前とパッケージを持たない。モジュールのパッケージは省略できない（既定値で補うと、既定値を変えたときに古いデータのピンの位置が変わるため）。
- モジュールは `id` だけで識別する（計画 1 の「決めたこと」）。回路の `id` は UUID の形で、プロジェクトをまたいでも重ならない。
- 位置の順を使っている所（`circuit/module.ts`）:
  1. `getPortsInPinOrder` の split の分岐: split の外側のピンの順。展開（`simulation/flatten.ts`）とシート上の配置（`getPinout`）がこれを使う。**この計画で番号の順に変える**。
  2. `assignPortNumbers`: 置いた・貼り付けたポートが複数あるとき、番号を付ける順。番号を振る処理なので位置の順のまま。
  3. `fillPortNumbers`: 読み込みで、番号がない・重なるポートに番号を付け直す順。同じく位置の順のまま。新しい形式では、一体の形式からの変換の中でだけ使う（`portNumber` を必須にし、重なりは断るため）。
  4. `listPortsInPositionOrder`: 「上から順に割り当て直す」の割り当て順（位置の順のまま。split から DIP / QFP に変えたときは計画 16 でポート番号の順にする）。
- メイン回路を特別に扱っている計算: 検証（`circuit/project.ts` の `checkCircuit`。モジュールにだけ名前とパッケージを求める）、保存の形との変換（`file/storage.ts`。メイン回路の名前を書かない・捨てる）、空のプロジェクト（`emptyProject`。メイン回路にパッケージがない）。置いたポートへのピン番号の付け方（`assignPinNumbers`）は、パッケージがないものを split と同じに扱う。
- [保存データ](../../docs/persistence.md)の「開発者からの指示」に、「保存データとプロジェクトファイルの版は別々の番号。片方だけ上げることになったら、文書の分け方を開発者に相談する」とある。形式を 2 つに分けるので、この決まりも直す。

## 決めたこと

開発者が決めたこと。

形式の分け方（2026-10-17）:

- 保存データを、プロジェクトの形式とモジュールの形式に分ける。どちらも v1 から数える。
  - 一体の形式（v1〜v4）は v4 で終わり。v4（とそれより古い版）のデータは、今までの変換（`upgradeV1`〜`upgradeV3`）で v4 にしてから、プロジェクト v1 とモジュール v1 に分けて読む。
  - 一体の形式と新しい形式は、データの形で見分ける（新しい形式は `format` を持つ。一体の形式は持たず、いちばん外の `version` と、`project` の中の `circuits` を持つ）。番号（`version: 1` など）だけでは見分けない。下の「ファイルの見分け方」。
  - 採らなかった案: モジュールの形式は一体の形式の続きとして v5 から数える（番号は重ならないが、モジュールの形式の v1〜v4 は単独では存在しなかった）。
- プロジェクトは、モジュールを `id` で識別する（中に持つモジュールは `id` を持ち、部品は `moduleId` で指す）。
- メイン回路も、モジュールの形式として持つ。メイン回路の `id` は今までどおり `"main"` に固定する。プロジェクトに「どれがメイン回路か」の項目は持たず、`id` が `"main"` のモジュールがメイン回路で、プロジェクトに必ず 1 つある、とする。
  - 理由: 今のコードは、メイン回路かどうかを `id` で判定している。固定しておけば、古いデータからの変換も、判定もそのまま使える。同じ情報を 2 か所に持たないので、食い違いが起きない。シミュレーションは、開いている回路をいちばん外側として動かすので、メイン回路を入口として特別に扱う処理はない。
  - 採らなかった案: ほかのモジュールと同じく UUID にする。プロジェクトに「どれがメイン回路か」の項目を持つ（判定のたびにプロジェクトを引く）。モジュールに「メイン回路」のフラグを持つ（2 つに立つ・どれにも立たない、という壊れた状態がありうる）。
- この計画を、計画 1 の下位の計画として作る。未解決のモジュール、モジュールファイル、プロジェクトパネルより先に進める（それらの土台になるため）。
- ブラウザの中での保存（localStorage）は、今と同じく 1 つのキーに入れる。中身は、モジュールをインラインで持つプロジェクトのデータ（プロジェクトとモジュールが、それぞれ自分の版を持つ）。形式は分けても、保存の場所は分けない。
  - 採らなかった案: モジュールごとにキーを分ける（例: `sazanka.module.<id>`）。
- プロジェクトファイル（プロジェクト全体の書き出し）は、今と同じく 1 ファイルで受け渡せるようにする（下の「プロジェクトの形」のとおり、モジュールをプロジェクトの中にインラインで持つ）。
- プロジェクトファイルをファイルに保存するときの名前を、`sazanka-YYYY-MM-DD.json` から `project-YYYY-MM-DD.sazanka.json`（端末の日付）に変える（2026-10-18）。モジュールファイルのファイル名（`modules-YYYY-MM-DD.sazanka.json`。[計画 22](../module-files/plan.md)）とそろえるため。採らなかった案: 今の名前のままにする。
- 「共有用 JSON」という言葉はやめ、プロジェクト全体を書き出したものを「プロジェクトファイル」、モジュールを書き出したものを「モジュールファイル」（[計画 22](../module-files/plan.md)）と呼ぶ（2026-10-18）。どちらも JSON として書き出せるので、「共有用」では役割が分けられないため。
  - コードの中の名前とコメント（`file/share.ts`、`ShareError`、`SHARE_VERSION` など）は、段階 3 で書き出しと読み込みを作り直すときに合わせて直す。
- プロジェクトの受け渡しは、ファイルだけにする（2026-10-18）。今の、文字列のコピー（書き出し）と貼り付け（読み込み）はやめる。採らなかった案: 文字列とファイルの両方を残す。
- プロジェクトの書き出しと読み込みは、アプリのダイアログを出さずに、直接行う（2026-10-18）。書き出しは押すとすぐ保存し、読み込みは押すとすぐファイルを選ぶ画面を開く。作者名の欄、文字列の欄、読み込み元の選択がなくなり、ダイアログに残るものがないため。読めないファイルのときは、今と同じくお知らせを出す。読み込むと、元に戻す・やり直しの履歴を消す（下の項目。元に戻すでは戻せなくなる）。
  - ブラウザ（OS）の画面は使う。読み込みは、ファイルを選ぶ画面（`<input type="file">`。どのブラウザでも出る）。書き出しは、保存場所とファイル名を選ぶ画面（`showSaveFilePicker`）を、使えるブラウザ（Chrome、Edge など Chromium のもの）で出す。使えないブラウザ（Firefox、Safari）では、今の仕組み（`<a download>`）で保存し、保存場所を聞くかはブラウザの設定に任せる。どのブラウザでも書き出せるので、「特定の環境を前提にしない」決まりとはぶつからない。
  - 今の[保存データ](../../docs/persistence.md)の「`showSaveFilePicker` は Chromium でしか動かないので使わない」は、「使えるときだけ使う」に直す（段階 3）。
  - プロジェクトを読み込んだときは、元に戻す・やり直しの履歴を消す（2026-10-18）。履歴はプロジェクトごとのもので、別のプロジェクトを開けば、前のプロジェクトの履歴はなくなるのが当然、という考え方による（開発者が決めた）。読み込みは元に戻せなくなる。今は元に戻す対象（`commit`）なので、[編集と元に戻す](../../docs/editing.md)の表も直す。新規作成も同じく履歴を消す（[計画 21](../project-panel/plan.md)）。採らなかった案: 今と同じく元に戻せるようにする（ファイルを取り違えたときに戻せる）。
  - ファイルとして開いて保存する形（開く・上書き保存・名前を付けて保存、保存していない変更の扱い、開く前と新規作成の前の確認）は、[プロジェクトをファイルとして開いて保存する](../project-file/plan.md)（計画 24）で作る。この計画では、書き出しと読み込みをファイルだけにし、ダイアログをなくすところまで。
  - ヘッダーの「書き出し」「読み込み」は、[計画 21](../project-panel/plan.md)でプロジェクトパネルの「⋯」に移してなくす。それまでは、ヘッダーのボタンで、この動きにする。
  - 採らなかった案: ダイアログは残し、「ファイルに保存」と「ファイルを選ぶ」だけにする。今の `<a download>` だけで保存する（Chrome では保存場所を選べない）。
- 同じフォルダの中のモジュールの名前は重ならない（[計画 21](../project-panel/plan.md)で決めた）ので、新しい形式の読み込みでは、同じフォルダに同じ名前のモジュールがあれば断る（2026-10-18）。一体の形式 v4 のデータは、今のアプリが改名で重なりを断っていないので、同じ名前がありうる。変換では、並びのあとのものの名前に ` (2)` などを付ける（変換後はどれもフォルダなしに入るため）。採らなかった案: 重なりを許し、読み込みでも断らない（重ならない決まりはアプリの操作にだけ当てはめる）。
- 新しい形式で必須にする項目（2026-10-18）。省略したときの意味が既定値の項目は、既定値を変えたときに古いデータの意味が変わるので、必須にする（モジュールのパッケージを省略できなくしたのと同じ理由）。新しく足す項目も、ないことと空を区別しなくてよいものは必須にして、決まりを簡単にする。
  - モジュールの `sheet`（シートの大きさ。一体の形式では省略でき、ないと 300×200 マス）。
  - CLOCK の `period`（周期。一体の形式では省略でき、ないと 100）。
  - INPUT / OUTPUT の `portNumber`（ポート番号。一体の形式では省略でき、ないと読み込みで付け直していた。ポート番号の順で split のピンが決まるようになるので、ないと意味が決まらない）。
  - モジュールを置いた部品の `moduleName`（名前の写し）。
  - プロジェクトの `folders`（空でもよい）と、要素の `path`（フォルダなしは `""`）。
  - モジュールの `author`（作者名がなければ空文字 `""`）。省略したときの意味は「ない」ことだが、空文字で表せるので、ほかとそろえて必須にする（開発者が決めた）。
  - 一体の形式 v4 からの変換で、ないものを補う（`sheet` は 300×200、`period` は 100、`portNumber` は今の付け直し（`fillPortNumbers`）と同じ決め方、`moduleName` は指すモジュールの名前、`author` はプロジェクトの作者名か、なければ空文字）。新しい形式の読み込みでは、ポート番号の付け直しはしない（変換の中でだけ行う）。
  - 省略できるままにするもの（省略したときの意味が「ない」こと）: INPUT / OUTPUT の `portName`（名前がない）と `pinNumber`（割り当てていない）、メイン回路の `name`（持たない）。部品の `rotation`（省略は 0）は既定値だが、「0 は回していない」は変えようがないので意味が変わる心配がなく、部品が多いとデータが大きくなるので、省略できるままにする。
  - 採らなかった案: 一体の形式と同じく、`sheet`、`period`、`portNumber` を省略できるままにする。
- メイン回路以外のモジュールは、空でない名前を持つ（2026-10-18）。新しい形式の読み込みでは、名前が空（空白だけを含む）のモジュールを断る。一体の形式 v4 のデータで名前が空のモジュールは、変換のときに「モジュール<n>」（今の追加の既定の名前と同じ形。n は、フォルダなしの中で重ならないいちばん小さい数）にする。名前を付けたあとで、同じ名前の重なりを ` (2)` などで直す。採らなかった案: 今と同じく、空でも通す（プロジェクトパネルに名前のない行が出る）。
- 違う種類のファイルを読み込んだとき（プロジェクトの読み込みでモジュールファイルを選んだときと、その逆）は、`format` で見分け、種類が違うことと正しい操作を知らせる（例: 「これはモジュールファイルです。『モジュールを読み込む』から読み込んでください」）（2026-10-18）。モジュールファイルの読み込みは[計画 22](../module-files/plan.md)で作るので、この計画ではプロジェクトの読み込みの側を作る。
- 計画 17（保存データの version 5）は、この計画にまとめた。version 5 はなくなる。
- 形式の文書は、`docs/format/project/v1.md` と `docs/format/module/v1.md` を新しく作る。一体の形式（v1〜v4）は `docs/format/archive/` に置く（今の `docs/format/v4.md` も `archive/` に移す）。
  - 採らなかった案: 1 つの文書の中で、プロジェクトの形式とモジュールの形式を節で分ける。
- ブランチは計画ごとに分け、計画のフォルダ名にする（この計画は `project-format`）。計画を完了にするときに `main` への PR を作る（[作業の進め方](../../docs/workflow.md)の「計画を始める」「計画を完了にする」。2026-10-18）。

プロジェクトの形（2026-10-17）:

- プロジェクトは、要素の平らな並び（`modules`）を持つ。並びは、プロジェクトパネルの並び。要素は、モジュールとパス（フォルダ）の組。木構造にはしない（フォルダはパスから組み立てる）。
  - 要素は、モジュールのデータをそのまま中に持つ（インライン）。`module` に、モジュールの形式のデータ（版を含む）をそのまま入れる。`id` はモジュールのデータの中にあるので、要素には書かない（2 か所に書くと食い違うため）。
  - 参照だけの要素（`moduleId` だけで中身を持たない要素）は作らない（2026-10-17）。未解決のモジュールは、部品が `moduleId` で指しているのにプロジェクトにないモジュールとして、部品から求める（[計画 20](../unresolved-module/plan.md)）。
    - 採らなかった案: 参照だけの要素を書けるようにする（使われているモジュールを削除したときに、元のフォルダと並びに未解決の行として残せる。ただ、行の名前の持ち方や、使われなくなった行の片付けの決まりが要る。一時的に外しておく使い方は要らないと判断した）。
  - インラインのモジュールも、モジュールの版を持つ。モジュールファイルの中に並べるモジュールのデータとまったく同じ形にして、書き出しと持ち込みを、中身を移すだけで済ませるため。採らなかった案: 版を持たせず、プロジェクトの版に従う。
  - フォルダはプロジェクトが決める（モジュールのデータは、どこに置かれるかを知らない）。同じモジュールを、別のプロジェクトでは別のフォルダに置ける。
  - 採らなかった案: フォルダの木構造で保存する（形が込み入る）。
- 要素のパスは、フォルダの部分だけを持つ（例: `"adders"`。メイン回路のようにフォルダに入れないものは `""`）。モジュールの名前はモジュールのデータが持つ。名前はモジュールファイルと一緒に持ち運ばれ、フォルダは置き先のプロジェクトが決める、という分け方になる（2026-10-17）。
  - 採らなかった案: パスに名前まで含める（例: `"adders/full-adder"`。名前をプロジェクトが持つことになり、持ち込むときに名前をどこから取るかを別に決めることになる）。
- 部品が指すモジュールがプロジェクトにないデータは、この計画のアプリでは、読み込むときに断る（今の `MISSING_MODULE` と同じ扱い）。開けるようにするのは、[未解決のモジュール](../unresolved-module/plan.md)（計画 20）で行う（2026-10-17）。

## 気になるところ

- 版の流れが 2 本（プロジェクトとモジュール）になると、古いデータを読む変換も 2 本になる。今の決まり（1 版ずつの変換を順に通す）を、それぞれに当てはめる。プロジェクトの形式はほとんど変わらない見込みなので、2 本になっても手間は増えないと見て、受け入れた（開発者が決めた、2026-10-17）。
- 新しい形式にすると、古い版のアプリ（もう公開していない）は新しいデータを読めない。今は最新版だけを公開しているので問題にならない（[保存データ](../../docs/persistence.md)の「形式を変えるとき」）。
- 変換でポート番号が変わったモジュールでは、シート上の「入力 1」などの表示が、前と違うポートに付く。配線とピンの順は保たれる。
- 新しい形式では、ポート番号の重なり（同じモジュールの中で、入力どうし・出力どうしで同じ番号）を読み込みで断る（`portNumber` を必須にしたため。付け直しはしない）。一体の形式 v4 のデータは、変換の中で、今の付け直し（`fillPortNumbers`。位置の順）で直してから、split のモジュールとメイン回路を位置の順に振り直す。
- この計画だけを終えた時点では、split でピンの順を並べ替える手段がない（計画 16 で足す）。公開は、上の「決めたこと」のとおり、公開までの計画をすべて終えてから。
