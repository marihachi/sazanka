# 未解決のモジュール（計画）

状態: **計画中**

- 段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../docs/workflow.md)の「実装を始める合図」）。
- 決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../docs/documentation.md)の「計画の文書」）。

## 目的

指す先のモジュールがプロジェクトにない部品を、断らずに「未解決のモジュール」として仮に置いておき、何が足りないかを見えるようにする。足りないモジュールを持ち込めば（同じ `id`）、そのまま解決する。

あわせて、ほかの回路で使われているモジュールも、プロジェクトから削除できるようにする（置いていた部品は未解決のモジュールとして残る）。

[プロジェクト管理機能](../project-management/plan.md)（計画 1）の下位の計画。前提は[保存データをプロジェクトとモジュールに分ける](../project-format/plan.md)（計画 19）。

## 前提

- 今は、指す先のないモジュールの部品があると、読み込みで壊れたデータとして断る（`circuit/project.ts` の `checkProject` の `MISSING_MODULE`）。シート上では、名前が引けないと「(不明)」と書く（`sheet/SheetPart.tsx`）。
- 計画 19 の新しい形式では、プロジェクトに参照だけの要素（`moduleId` だけで、中身のない要素）を書ける。ただし計画 19 のアプリは、読み込むときに断る。部品は `moduleId` でモジュールを指す。
- 今は、ほかの回路で使われているモジュールは削除できず、理由をダイアログで知らせている（[編集と元に戻す](../../docs/editing.md)の「モジュール」）。削除はシートのツールバーの「モジュールを削除」。
- 未解決のモジュールの部品は、プロジェクトパネルの「別のモジュールに差し替える」（[計画 21](../project-panel/plan.md)）で、手元の別のモジュールにつなぎ直せる。
- 未解決になる場面:
  - 使われているモジュールをプロジェクトから削除したとき（この計画で作る）。
  - 外から来たデータ（共有用 JSON、モジュールのファイル）に足りないモジュールがあるとき。

## 決めたこと

開発者が決めたこと（2026-10-17。もとは計画 1 で決めたもの）。

- 指す先のないモジュールの部品を、断らずに未解決のモジュールとして開く。何が足りないかを見えるようにする。
- 何が足りないかを見せるため、参照する側（部品）に、指すモジュールの名前の写しを持たせる。識別は `id` だけで行い、名前は表示の手がかり。
- ほかの回路で使われているモジュールも、プロジェクトから削除できるようにする。使われているときは、確認を出してから削除する（どの回路で使われているかを示す）。
- 言い方は「プロジェクトから削除」（英語: Remove from project）。確認の文に「中身はプロジェクトからなくなる」「置いている部品は未解決のモジュールとして残る」の両方を書く。例: 「全加算器」をプロジェクトから削除します。中身はプロジェクトからなくなり、置いている部品（メイン回路など 3 か所）は未解決のモジュールとして残ります。
  - 採らなかった案: 「削除」だけ。「プロジェクトから外す」「アンロード」「プロジェクトから除外」。
- メイン回路は、プロジェクトから削除できない。
- プロジェクトから削除する操作は、最後はプロジェクトパネル（計画 21）にだけ置く。この計画では、今のツールバーの「モジュールを削除」で行い、文言を「プロジェクトから削除」に合わせるかは、下の「決めてほしいこと」の 5。

## 決めてほしいこと

推す案を先に書く。

1. 名前の写しの項目名と、いつ書くか
   - 推す案: 部品に `moduleName` を持たせる。保存するときに、指しているモジュールの今の名前を写す。モジュールがあるときは、表示にはモジュールの名前を使い、写しは使わない。改名しても部品を書き換える処理は要らない。未解決の部品は、読み込んだ写しをそのまま持ち続ける。
   - 案 B: アプリの中でも部品に名前を持たせ、改名のたびに、そのモジュールを指す部品をすべて書き換える。
   - 項目名のほかの候補: `moduleLabel`。
2. 未解決の部品の見た目と、ピン
   - 推す案: ピンの形（パッケージと、ピンごとの入力・出力・名前）の写しも部品に持たせ、未解決でも同じ大きさとピンで描く。つながっていた配線が外れて見えないようにするため。本体は破線などで未解決と分かるようにし、名前の写しと「見つからない」を書く。
   - 案 B: ピンの写しは持たせず、決まった大きさの箱で描く（ピンはない。つながっていた配線は外れて見える）。データは小さい。
   - ピンの写しは、ピン数の多いモジュール（128 ピン）だと大きくなる。置いた数だけ写すので、保存データが大きくなる。
3. 未解決の部品のシミュレーション
   - 推す案: 出力ピンはすべて OFF、入力は使わない。ステータスバーに「見つからないモジュールがあります」のバッジを出す。
4. 写し（名前とピン）を形式に足す時機
   - 推す案: 新しい形式（計画 19）を公開する前に、モジュールの形式 v1 に入れる。省略できる項目なので、あとで足しても版は上げなくてよいが、公開前に入れておけば、公開したデータにも最初から写しが入る（未解決になったときに名前とピンが分かる）。
   - 案 B: この計画を進めるときに、省略できる項目として足す（公開済みのデータには写しがないので、未解決になったときに名前もピンも分からない）。
5. この計画での「モジュールを削除」ボタン
   - 推す案: 文言を「プロジェクトから削除」に変え、使われているモジュールでも押せるようにする（確認を出す）。ボタンそのものは、プロジェクトパネル（計画 21）ができたらなくす。
   - 案 B: この計画ではボタンを変えず、使われているモジュールの削除は計画 21 で作る。
6. 「ファイル名」（モジュールを持ち込んだ元のファイルの名前）を持たせるか
   - 何に使うか（どこから持ち込んだかを見せる、同じファイルから持ち込み直す、など）を聞いてから決める。

## 段階（案）

決めてほしいことが決まってから、細かく書く。実装は Skill の `modify` で進める。

1. 形式と検証: 部品の写しの項目（決めてほしいことの 1、2、4 による）、参照だけの要素と、指す先のない部品を読み込みで断らないようにする。形式の文書。
2. 画面とシミュレーション: 未解決の部品の描き方、シミュレーションでの扱い、ステータスバー。
3. 使われているモジュールの削除: 確認のダイアログ、未解決として残ること、元に戻す 1 回で戻ること。
- 確かめること: テスト（読み込み、写し、シミュレーション）。ブラウザで、未解決の部品の見た目、配線が外れて見えないこと、持ち込み直して解決すること（計画 22 の前は、共有用 JSON の読み込みで確かめる）。
