# 未解決のモジュール（計画）

状態: **計画中**

- 段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../docs/workflow.md)の「実装を始める合図」）。
- 決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../docs/documentation.md)の「計画の文書」）。

## 目的

指す先のモジュールがプロジェクトにない部品を、断らずに「未解決のモジュール」として仮に置いておき、何が足りないかを見えるようにする。足りないモジュールを持ち込めば（同じ `id`）、そのまま解決する。

あわせて、ほかの回路で使われているモジュールも、プロジェクトから削除できるようにする（置いていた部品は未解決のモジュールとして残る）。

[プロジェクト管理機能](../project-management/plan.md)（計画 1）の下位の計画。前提は[保存データをプロジェクトとモジュールに分ける](../project-format/plan.md)（計画 19）と、[問題パネル](../problems-panel/plan.md)（計画 23。見つからないモジュールを出す場所）。

## 前提

- 今は、指す先のないモジュールの部品があると、読み込みで壊れたデータとして断る（`circuit/project.ts` の `checkProject` の `MISSING_MODULE`）。シート上では、名前が引けないと「(不明)」と書く（`sheet/SheetPart.tsx`）。
- 計画 19 の新しい形式では、部品は `moduleId` でモジュールを指し、名前の写し `moduleName` を持つ。プロジェクトは中身を持つモジュール（インライン）だけを並べる（参照だけの要素はない）。未解決のモジュールは、部品が指しているのにプロジェクトにないモジュールとして、部品から求める。計画 19 のアプリは、そういうデータを読み込むときに断る。
- 今は、ほかの回路で使われているモジュールは削除できず、理由をダイアログで知らせている（[編集と元に戻す](../../docs/editing.md)の「モジュール」）。削除はシートのツールバーの「モジュールを削除」。
- 未解決のモジュールの部品は、プロジェクトパネルの「別のモジュールに差し替える」（[計画 21](../project-panel/plan.md)）で、手元の別のモジュールにつなぎ直せる。
- 未解決になる場面:
  - 使われているモジュールをプロジェクトから削除したとき（この計画で作る）。
  - 外から来たデータ（プロジェクトファイル、モジュールファイル）に足りないモジュールがあるとき。

## 決めたこと

開発者が決めたこと（2026-10-17。もとは計画 1 で決めたもの）。

- 指す先のないモジュールの部品を、断らずに未解決のモジュールとして開く。何が足りないかを見えるようにする。
- 何が足りないかを見せるため、参照する側（部品）に、指すモジュールの名前の写しを持たせる。識別は `id` だけで行い、名前は表示の手がかり。
- ほかの回路で使われているモジュールも、プロジェクトから削除できるようにする。使われているときは、確認を出してから削除する（どの回路で使われているかを示す）。
- 言い方は「プロジェクトから削除」（英語: Remove from project）。確認の文に「中身はプロジェクトからなくなる」「置いている部品は未解決のモジュールとして残る」の両方を書く。例: 「全加算器」をプロジェクトから削除します。中身はプロジェクトからなくなり、置いている部品（メイン回路など 3 か所）は未解決のモジュールとして残ります。
  - 採らなかった案: 「削除」だけ。「プロジェクトから外す」「アンロード」「プロジェクトから除外」。
- 名前の写しは、部品の項目 `moduleName` に持たせる。保存するたびに、指しているモジュールの今の名前を写す。モジュールがあるときは、表示にはモジュールの名前を使い、写しは使わない。改名しても部品を書き換える処理は要らない。未解決の部品は、読み込んだ写しをそのまま持ち続ける。
  - 採らなかった案: アプリの中でも部品に名前を持たせ、改名のたびに書き換える。項目名 `moduleLabel`。
- 名前の写しは、新しい形式（[計画 19](../project-format/plan.md)）を公開する前に、モジュールの形式 v1 に入れる。公開したデータにも最初から写しが入り、未解決になったときに名前が分かるようにするため。採らなかった案: この計画を進めるときに、省略できる項目として足す。
- ピンの写しは持たせない。未解決の部品は、決まった大きさの箱で描く（ピンはない。つながっていた配線は外れて見える）。本体は未解決と分かる見た目にし、名前の写しと「見つからない」を書く。データを小さく保つ。
  - 採らなかった案: ピンの形の写しも持たせ、未解決でも同じ大きさとピンで描く（ピン数の多いモジュールを多く置くと、保存データが大きくなる）。
- 未解決のモジュールがあっても、シミュレーションは動かし続ける。未解決の部品の出力はすべて OFF にし、入力は使わない。ほかの部分はふつうに動き、INPUT も操作できる（2026-10-18）。出力のぶつかり（そのネットにつながる入力ピンを OFF にして動かし続ける）と同じ扱いにそろえる。
  - 理由: 作りかけの回路でも、問題のない部分の動きを確かめられる。出力のぶつかりは配線の途中に一時的に起きることが多く、エラーのたびに止めると編集の邪魔になるので、ぶつかりの側は止めない。それとそろえる。
  - 未解決のモジュールがあることは、[問題パネル](../problems-panel/plan.md)（計画 23）に「見つからないモジュール」として出して知らせる。
  - 採らなかった案: 未解決のモジュールがあれば、開いている回路とその中のモジュールのシミュレーションを止める（値はすべて OFF、INPUT も操作できない）。いったん決めたが、出力のぶつかりと扱いをそろえるため変えた（2026-10-18）。エラー（出力のぶつかりと未解決のモジュール）があれば、どちらも止める（今の出力のぶつかりの動きが変わり、配線の途中の一時的なぶつかりでも止まる。発振は動かさないと分からないので、エラーで止める決まりにはそろえられない）。
- この計画では、今のツールバーの「モジュールを削除」ボタンの文言を「プロジェクトから削除」に変え、使われているモジュールでも押せるようにする（確認を出す）。ボタンそのものは、プロジェクトパネル（計画 21）ができたらなくす。採らなかった案: この計画ではボタンを変えず、計画 21 で作る。
- モジュールを持ち込んだ元のファイルの名前は、持たせない。
- メイン回路は、プロジェクトから削除できない。
- プロジェクトから削除する操作は、最後はプロジェクトパネル（計画 21）にだけ置く。

## 段階（案）

実装の前に細かく書く。実装は Skill の `modify` で進める。

1. 形式と検証: 指す先のない部品を読み込みで断らないようにする。形式の文書（名前の写し `moduleName` は計画 19 で入れてある）。
2. 画面とシミュレーション: 未解決の部品の描き方（決まった大きさの箱）、未解決の部品の出力を OFF にしてシミュレーションを動かし続けること（展開 `simulation/flatten.ts` で、未解決の部品を出力 OFF の部品として扱う）、問題パネル（計画 23）に「見つからないモジュール」を出すこと。
3. 使われているモジュールの削除: ツールバーのボタンの文言を「プロジェクトから削除」にし、確認のダイアログを出す。未解決として残ること、元に戻す 1 回で戻ること。
- 確かめること: テスト（読み込み、写し、シミュレーション）。ブラウザで、未解決の部品が箱で描かれ名前の写しが出ること、未解決の部品の出力が OFF のまま、ほかの部分が動き INPUT も操作できること、持ち込み直して解決すること（計画 22 の前は、プロジェクトファイルの読み込みで確かめる）。
