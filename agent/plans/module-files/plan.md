# モジュールのファイル（計画）

状態: **計画中**

- 段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../docs/workflow.md)の「実装を始める合図」）。
- 決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../docs/documentation.md)の「計画の文書」）。

## 目的

モジュールをファイルに書き出し、別のプロジェクトに持ち込んで再利用できるようにする。

[プロジェクト管理機能](../project-management/plan.md)（計画 1）の下位の計画。前提は、[保存データをプロジェクトとモジュールに分ける](../project-format/plan.md)（計画 19）、[未解決のモジュール](../unresolved-module/plan.md)（計画 20）、[プロジェクトパネル](../project-panel/plan.md)（計画 21。書き出しと持ち込みの操作はパネルに置く）。

## 前提

- モジュールは `id` だけで識別する。`id` は UUID の形で、プロジェクトをまたいでも重ならない。同じ `id` なら同じモジュール（の別の版）と見分けられる。
- 計画 19 の新しい形式では、プロジェクトは要素（フォルダのパスと、インラインのモジュールか `moduleId` の参照）の並びを持つ。モジュールの形式は `format: "sazanka-module"` と版を持つ。
- プロジェクト全体の書き出しと読み込みは、今の共有用 JSON（ヘッダーの「書き出し」「読み込み」）。読み込むとプロジェクトを丸ごと置き換える。手元のファイルの保存と選択は `file/localFile.ts` が使える。

## 決めたこと

開発者が決めたこと（2026-10-17。もとは計画 1 で決めたもの）。

- 書き出せる単位は、プロジェクト全体（今の共有用 JSON）、モジュール 1 つ、複数のモジュール。それぞれ 1 ファイルで書き出す。
- モジュールを書き出すファイルは、1 つでも複数でも、いつも「モジュールの束」の形式にする（例: `"format": "sazanka-modules"`）。数でファイルの形が変わるとややこしいため。中身はプロジェクトの要素と同じ形の並び（パスとインラインのモジュール）で、メイン回路を持たない。持ち込むと、要素がそのままプロジェクトの並びに加わる（フォルダも持ち込める）。
  - 採らなかった案: 1 つのときはモジュールの形式（`"sazanka-module"`）そのままで書く。プロジェクトの形式で、メイン回路なしを許す。
- 束の形式は、プロジェクトとモジュールの形式とは別に v1 から数える。新しい種類を足すだけなので、ほかの形式の版には響かない。
- 追加: 今の「+」（空のモジュールを作る）に加えて、モジュールのファイルを選んでプロジェクトに足せるようにする（持ち込み）。操作はプロジェクトパネルに置く。

叩き台:

```json
{
  "format": "sazanka-modules",
  "version": 1,
  "modules": [
    { "path": "adders", "module": { "format": "sazanka-module", "version": 1, "id": "7b3e…", "name": "全加算器", ... } },
    { "path": "adders", "module": { "format": "sazanka-module", "version": 1, "id": "c91a…", "name": "半加算器", ... } }
  ]
}
```

## 決めてほしいこと

推す案を先に書く。

1. 書き出すモジュールが使うモジュール（入れ子）
   - 推す案: 書き出すときに、使っているモジュールも入れるかを選べるようにする（既定は入れる）。入れないと、持ち込み先で足りなければ未解決のモジュールになる。
   - 案 B: いつも入れる（足りないことが起きない）。
2. 持ち込んだときの、ぶつかりの扱い
   - `id` が同じモジュールがすでにある（同じモジュールの別の版）:
     - 推す案: 利用者に聞く。「置き換える（更新）」「持ち込まない」を選べる。置き換えでピンが変わるとき（ポート番号やパッケージが違うとき）は、そのことを知らせる。
   - `id` は違うが、名前が同じモジュールがある（名前の重なりの決まりは、計画 21 の「決めてほしいこと」の 2）:
     - 推す案: 持ち込むモジュールの名前の最後に ` (2)` などを付けて足す。聞かない（別のモジュールなので、置き換える理由がないため）。
   - 一度に複数がぶつかったとき。推す案: まとめて 1 回聞く（一覧で見せて、全部置き換える・全部やめるを選ぶ）。
3. メイン回路を、モジュールとして書き出せるか
   - 推す案: 書き出せない。メイン回路は `id` が `"main"` でどのプロジェクトでも同じなので、持ち込むと見分けられない。メイン回路を部品として使いたいときは、モジュールに移す操作（別の計画。作るかは決めていない）で扱う。
   - 案 B: 書き出せる。持ち込むときに新しい `id` を付けて、ふつうのモジュールにする。
4. モジュールの形式だけのファイル（手で作ったものなど）も持ち込めるようにするか
   - 推す案: 持ち込める（束の要素 1 つ、フォルダなし、として扱う）。束でなくても読めると、手で作ったデータやほかの道具から渡しやすい。
   - 案 B: 束だけを持ち込める。
5. 書き出しと持ち込みの操作の置き場所
   - 推す案: プロジェクトパネルの行の操作（「書き出し」は選んだモジュール。複数選べる）と、パネルの「追加」の中の「ファイルから」。ヘッダーの「書き出し」「読み込み」は、今までどおりプロジェクト全体。
6. 束の形式の項目名と、ファイル名
   - 推す案: `format` は `"sazanka-modules"`。保存するファイル名は `sazanka-modules-YYYY-MM-DD.json`（モジュール 1 つなら `<モジュール名>.json` にするかも決める）。

## 問題点

- 置き換え（更新）でピンが変わると、置いた先の外側の配線が別のピンにつながったり、どこにもつながらなくなったりする。新しい形式で split もポート番号で決まるので、変わるのはポート番号・パッケージ・ピンの割り当てを変えたときに限られる。それでも、置き換える前に知らせる工夫が要る。
- 置き換えで、モジュールの中がまるごと入れ替わる。持ち込む前のモジュールを持ち込み先で直していたら、その変更は消える（元に戻すで戻せる）。
