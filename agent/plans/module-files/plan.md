# モジュールのファイル保存と再利用（計画）

状態: **計画中**（実装するかどうかも含めて、決めることが残っている。下の「まだ決めていないこと」）。

- 段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../docs/workflow.md)の「実装を始める合図」）。
- 決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../docs/documentation.md)の「計画の文書」）。

## 目的

モジュールを JSON ファイルとして書き出し、別のプロジェクトに持ち込んで再利用できるようにする。

## 前提

- モジュールは、プロジェクトの中の回路（`circuits` の 2 つ目以降）。部品 `module` は、項目 `module` に回路の `id` を書いてモジュールを指す（[version 3](../../../docs/format/v3.md)）。
- 回路の `id` は、同じプロジェクトの中でだけ重ならない。ランダムな短い文字列で、読んでも意味が分からない。共有用 JSON に書き出すときも、回路の `id` は付け直さない（[version 3](../../../docs/format/v3.md)の「ID の付け方」）。
  - そのため、モジュールを別のプロジェクトへ持ち込むと、回路の `id` がぶつかりうる。
- 回路は `id` のほかに、名前（`name`）、パッケージ（`package`。モジュールだけ）、シートの大きさ（`sheet`）を持つ。フォルダのような分類はない。
- モジュールの名前は、追加では重なりを断るが、改名では断っていない（[編集と元に戻す](../../docs/editing.md)の「モジュール」）。そのため、名前では一意に決まらない。
- モジュールの外側のピンは、パッケージが `dip` / `qfp` なら中の `input` / `output` の `pinNumber` で決まり、`split` なら中の位置の順で決まる（[version 3](../../../docs/format/v3.md)の「モジュールのピン」）。
- 保存データの version 3 は公開済み。省略できる項目を足すだけなら版は上げない。今ある項目の形を変えるなら版を上げ、古い版を変換する処理を足す（[保存データ](../../docs/persistence.md)の「形式を変えるとき」）。
- アプリはブラウザだけで動く（GitHub Pages、サーバーなし）。

## 決めたこと

開発者の希望:

- モジュールは、UUID のような読めない ID ではなく、パスのような名前で参照したい。
- 指したいのはファイルシステムの場所ではなく、**プロジェクトの中のモジュール**。例: `adders/full-adder`、`gates/xor`。
  - ファイルシステムや URL を指すリンクは、ブラウザでは読み込みの制約が大きい（手元のファイルは読む許可が要り、使えるブラウザも限られる。URL は置き場所が CORS を許可している必要がある）。プロジェクトの中のパスなら、これを避けられる。

## 仕組みの案

まだ決めていないことを、推す案で埋めた形。決まったら直す。

- モジュールのパス: プロジェクトの中のモジュールに、フォルダ分けしたパス（`adders/full-adder` など）を持たせる。パスはプロジェクトの中で重ならず、モジュールの識別子になる。メイン回路はパスを持たない。
- 参照: アプリの中と保存データでは、今までどおり `module` に回路の `id` を書く。パスは回路の新しい項目 `path` に持つ（下の 1 の B）。
- モジュールのファイル: 書き出したモジュールと、それが使うモジュール（入れ子をたどる）をまとめて 1 つのファイルにする。ファイルの中では、参照をパスで書く。持ち込むときに、持ち込み先の `id` に付け直す。
- 持ち込みでパスがぶつかったら、利用者に聞く（下の 2）。

叩き台（B の場合）:

```json
{
  "circuits": [
    { "id": "main", "name": "メイン", "parts": [{ "id": "a", "kind": "module", "x": 100, "y": 100, "module": "k3f9" }], "wires": [] },
    { "id": "k3f9", "name": "full-adder", "path": "adders/full-adder", "package": { "kind": "split" }, "parts": [], "wires": [] }
  ]
}
```

モジュールのファイル:

```json
{
  "app": "sazanka",
  "version": 3,
  "type": "modules",
  "entry": "adders/full-adder",
  "modules": [
    { "path": "adders/full-adder", "package": { "kind": "split" }, "parts": [], "wires": [] },
    { "path": "adders/half-adder", "package": { "kind": "dip", "pins": 4 }, "parts": [], "wires": [] }
  ]
}
```

- `entry` は、書き出したモジュール。`modules` には、それが使うモジュールも入る。
- プロジェクト全体の共有用 JSON と区別するため、`type` を持たせる。

## 問題点

- 持ち込みで置き換えたとき、モジュールのピンが変わると、外側の配線が別のピンにつながったり、どこにもつながらなくなったりする。
  - `dip` / `qfp` は、ピンを `pinNumber` で決めるので、中の `input` / `output` を動かしても保たれる。ピン数やピン番号の割り当てを変えたときだけ変わる。
  - `split` は、中の位置の順でピンが決まるので、変わりやすい。
  - 置き換える前に、ピンの変化を見せるなどの工夫が要る。
- B では、保存データの中の参照は読めない ID のままになる。アプリの中とファイルとで、参照の書き方が 2 通りになる。
- 今のモジュールにはパスがないので、名前からパスを作る必要がある（フォルダなし。名前が重なっていたら `(2)` を付ける）。

## まだ決めていないこと

開発者が決めること（推す案を先に書く）:

1. パスと回路の `id` の関係
   - 推す案: B. アプリの中と保存データでは今の `id` を使い、パスは回路の項目 `path` に持つ。モジュールのファイルに書き出すときだけ、参照をパスで書く。
     - 利点: 名前やフォルダを変えても、参照を書き換えなくてよい。省略できる項目を足すだけなので、version 3 のまま進められる。今の仕組みをあまり変えない。
     - 欠点: 保存データの中の参照は読めないまま。参照の書き方が 2 通りになる。
   - ほかの案: A. パスを識別子そのものにする。回路の `id` をやめてパスにし、`module` もパスで書く。
     - 利点: データを読めば、どのモジュールを指しているか分かる（開発者の希望に近い）。仕組みが 1 つで済む。
     - 欠点: 名前やフォルダを変えると、そのモジュールを使うすべての部品の `module` を書き換える必要がある（アプリがまとめて書き換える）。`id` と `module` の形が変わるので、version 4 に上げ、version 3 を変換する処理を足す。
2. 持ち込みでパスがぶつかったとき
   - 推す案: 利用者に聞く。選べるのは、置き換える（同じパスは同じモジュールとみなし、持ち込み直すことで「更新」にする）、別の名前で足す（`adders/full-adder (2)` など）、持ち込まない。
   - 一度に複数がぶつかったときの聞き方も決める。
3. 相対パス
   - 推す案: 最初は、プロジェクトのルートからの絶対パスだけにする。プロジェクトの中ではパスを 1 通りに決められるので、相対パスは必須ではない。
   - 相対パス（`./half-adder`、`../gates/xor`）が役に立つのは、フォルダごと別の場所へ持ち込むとき（例: `adders/` を持ち込み先の `lib/adders/` に置く）。必要になったら足す。
4. パスに使える文字
   - 区切りは `/`。空の部分、`.`、`..` は使えないようにする（相対パスを後で足す余地を残すため）。
   - 今のモジュールの名前（日本語や空白を含みうる）を、そのままパスの部分に使えるようにするか。
5. 名前とパスの関係
   - パスの最後の部分（`full-adder`）を、今の `name` の代わりに表示するか。`name` を残して、パスとは別に持つか。
6. フォルダの見せ方と、パスを変える操作の置き場所
   - パレットやタブで、フォルダをどう見せるか（まとめて折り畳むなど）。
   - パスを変える操作を、どこに置くか（タブの名前の変更、モジュール設定、パレット）。
7. 書き出しの単位
   - 推す案: モジュール 1 つと、それが使うモジュール。
   - ほかの案: フォルダ単位。選んだ複数のモジュール。

## 段階

実装は Skill の `modify` で進める。

### 段階 1: モジュールにパスを持たせる

- フォルダ分けと、パスの表示・変更。ファイルの機能はまだ作らない。
- 形式の文書（`docs/format/v3.md`）と、今の保存データからの移し方（名前からパスを作る）。
- 確かめること: テスト（パスの検証、重なり、古いデータからのパスの作り方）。保存して読み直せること。ブラウザでの操作。

### 段階 2: モジュールのファイルの書き出しと持ち込み

- 使っているモジュールも一緒に書き出す。持ち込みでパスがぶつかったら聞く。置き換えでピンが変わるときは知らせる。
- 確かめること: テスト（入れ子、ぶつかり、ピンの変化、`id` の付け直し）。ブラウザでの操作と荒い操作。

### 段階 3: 必要なら

- 相対パス、フォルダ単位の持ち込み先の指定。
