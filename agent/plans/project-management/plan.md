# プロジェクト管理機能（計画）

状態: **計画中**

- 段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../docs/workflow.md)の「実装を始める合図」）。
- 決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../docs/documentation.md)の「計画の文書」）。

## 目的

プロジェクトの中の回路（メイン回路とモジュール）を管理する機能を作る。プロジェクトパネルで回路を一覧し、開く・追加・削除・書き出しをする。モジュールをファイルに書き出し、別のプロジェクトに持ち込んで再利用できるようにする。モジュールをフォルダで整理できるようにする。

## 前提

- 今の形式（一体の形式 v4）では、モジュールはプロジェクトの中の回路（`circuits` の 2 つ目以降）で、部品は項目 `module` に回路の `id` を書いてモジュールを指す。新しい形式（計画 19）では、プロジェクトが要素の並びでモジュールを持ち、部品は `moduleId` でモジュールを指す。
- 回路は `id` のほかに、名前（`name`。メイン回路は持たない）、パッケージ（`package`。新しい形式ではメイン回路も持つ）、シートの大きさ（`sheet`）を持つ。フォルダのような分類はない。
- モジュールの名前は、追加では重なりを断るが、改名では断っていない（[編集と元に戻す](../../docs/editing.md)の「モジュール」）。名前では一意に決まらない。
- プロジェクト全体の受け渡しは、共有用 JSON（書き出し・読み込み、`file/share.ts`）がある。読み込むとプロジェクトを丸ごと置き換える。
- アプリはブラウザだけで動く（GitHub Pages、サーバーなし）。手元のファイルの保存と選択は、共有用 JSON と同じ仕組み（`file/localFile.ts`）が使える。
- 回路の `id` は UUID の形で、プロジェクトをまたいでも重ならず、付け直さない（version 4。メイン回路の `"main"` を除く）。モジュールを別のプロジェクトへ持ち込んでも `id` はぶつからず、同じ `id` なら同じモジュール（の別の版）と見分けられる。
- 新しい形式（プロジェクト v1 とモジュール v1）を計画中（[保存データをプロジェクトとモジュールに分ける](../project-format/plan.md)、計画 19、未公開）。split のピンの順がポート番号の順になり、モジュールの中でポートを動かしても外側のピンが入れ替わらなくなる。公開するまで中身を足せるので、この計画で形式を変えるなら、新しい形式に入れれば、利用者のデータが変わるのが 1 回で済む。
- [計画 18](../main-as-module/plan.md)（計画中）で、メイン回路もパッケージとポートを持ち、シート設定とモジュール設定は「回路設定」にまとまる。

## 決めたこと

- モジュールは `id` だけで識別する（2026-10-17）。参照（部品の `moduleId`、プロジェクトの参照だけの要素の `moduleId`）は、保存データでもモジュールのファイルでも `id` で書く。名前やパスは識別に使わない（パスを持たせるなら、整理と表示のためだけのもの）。
  - 理由: version 4 で `id` がプロジェクトをまたいでも変わらなくなったので、ファイルの中でもそのまま使える。参照の書き方が 1 通りで済み、名前やパスを変えても参照を書き換えなくてよい。持ち込みで「同じモジュールか」を `id` で確実に見分けられる。
  - 欠点: 保存データとファイルの中の参照は、読めない `id` のまま。
  - 採らなかった案: パスを識別子そのものにする（パスを変えると参照をすべて書き換える。プロジェクトをまたぐと同じパスが別のモジュールを指しうる。version 4 の `id` の考え方を変える大きな変換が要る）。保存データでは `id`、ファイルの中だけパスで書く（参照の書き方が 2 通りになる）。

- モジュールをプロジェクトに追加・削除する機能を広げる（2026-10-17）。
  - 追加: 今の「+」（空のモジュールを作る）に加えて、モジュールのファイルを選んでプロジェクトに足せるようにする（持ち込み）。
  - プロジェクトから削除: ほかの回路で使われているモジュールも削除できるようにする。使われているときは、確認を出してから削除する（どの回路で使われているかを示す）。削除したモジュールを置いていた部品は、未解決のモジュールとして残る（決めてほしいことの 7）。持ち込み直せば解決する。今は、使われているモジュールは削除できず、理由をダイアログで知らせている（[編集と元に戻す](../../docs/editing.md)の「モジュール」）。
  - 言い方は「プロジェクトから削除」（英語: Remove from project）（2026-10-17）。中身が戻らない（元に戻す以外では持ち込み直すしかない）ことが、利用者にとって大事な情報のため。置いていた部品まで消えると受け取られないよう、確認の文に「中身はプロジェクトからなくなる」「置いている部品は未解決のモジュールとして残る」の両方を書く。例: 「全加算器」をプロジェクトから削除します。中身はプロジェクトからなくなり、置いている部品（メイン回路など 3 か所）は未解決のモジュールとして残ります。
    - プロジェクトから削除する操作は、プロジェクトパネルにだけ置く。シートのツールバーの「モジュールを削除」ボタンはなくす（2026-10-17）。プロジェクトの中の回路を管理する操作なので、パネルにまとめる。[計画 18](../main-as-module/plan.md)で「回路設定」の右に場所を空けて置くと決めたボタンなので、なくすときに、空けていた場所の扱いも直す。
    - 採らなかった案: 「削除」だけ（置いていた部品まで消えると受け取られやすい）。「プロジェクトから外す」「アンロード」「プロジェクトから除外」（どれも、中身がなくなることが伝わりにくい。アンロードは開発ツールの言葉で、なじみが薄い）。
- モジュールをフォルダで整理する（2026-10-17）。フォルダのパスはプロジェクトの要素が持ち（フォルダの部分だけ）、名前はモジュールのデータが持つ。パスの決まりは[計画 19](../project-format/plan.md)の「プロジェクトの形」。
- モジュールをまとめて管理する場所を作る（2026-10-17）。プロジェクトにあるモジュールの一覧を出し、そこから追加・削除・書き出しをする。どのモジュールがどこで使われているか、どれが未解決かも見られるようにする。今はタブとパレットに散らばっているので、モジュールが増えたときに管理しやすくするため。
- 管理する場所は、プロジェクトパネルにする（2026-10-17）。プロジェクトにある回路（メイン回路とモジュール）の一覧を出し、開く・追加・削除・書き出しをする。
- プロジェクトパネルは、左のサイドパネル（今のパレットの場所）に置き、パレットと表示を切り替える（2026-10-17）。
  - 採らなかった案: パレットとは別のパネルとして左の端に並べる（横幅を取る）。右側に置く。
  - 切り替えは、サイドパネルのさらに左に置く、アイコンだけの細い列で行う（VS Code の左端と同じ形）。並びは上から「プロジェクト」「部品」。採らなかった案: サイドパネルの上にタブを 2 つ置く。
  - 最後に選んでいた方を覚える（パレットの折り畳みと同じく localStorage に保存する）。
  - パレットの「モジュール」グループは残す。切り替えるとパレットとプロジェクトを同時に見られないので、モジュールを置く操作は今までどおりパレットでもできるようにする。
  - 初めて開いたとき（保存した画面の状態がないとき）は、タブを 1 つも開かずに起動し、サイドパネルは「プロジェクト」を出す。メイン回路を開くと、タブが開き、サイドパネルは「部品」に移る。
  - プロジェクトパネルから回路を開き、それで新しくタブが開いたときは、いつもサイドパネルを「部品」に移す（開いた回路にすぐ部品を置けるように）。すでに開いているタブに切り替えただけなら移らない。
  - 今の利用者も、更新したあとに初めて開いたときは、開いていたタブの記録がないので、タブなしで起動し、「プロジェクト」を出す（今までと同じ見た目で始めるための特別な扱いはしない）。
- タブバーは、開いている回路だけを並べる（2026-10-17）。プロジェクトパネルで回路を開くとタブに並び、タブで開いている回路の間を行き来する（エディタと同じ形）。
  - メイン回路のタブも、ほかの回路と同じく閉じられる。
  - メイン回路は、ほかのモジュールと違い、プロジェクトから削除できない。
  - タブを全部閉じたら、「表示するものがない」状態にする。シートは描かず、シートの所に短い文（例: 「開いている回路はありません」）を出す。シートのツールバーのボタンは押せない。シミュレーションは止める。最後のタブを閉じられないようにはしない。
  - タブに閉じるボタン（「×」）を付ける。
  - タブの並びは、開いた順。ドラッグで並べ替えられる。並びは保存データには入れず、画面の状態として localStorage に保存する（再読み込みのあとも、開いていたタブと並びが残る）。元に戻す対象にもしない。
  - 回路の並び（新しい形式ではプロジェクトの要素の並び）は、プロジェクトパネルの並びとして扱い、保存データに残す。
  - タブでできるのは、開く・閉じる・並べ替えだけ。改名と追加（今の「+」）は、プロジェクトパネルに移す。
  - プロジェクトから削除したモジュールのタブは閉じる。

## 決めてほしいこと

推す案を先に書く。

1. **この計画を進めるか、いつ進めるか**
   - 推す案: 計画 19・18・16（新しい形式の一連）が終わってから進める。形式の変更が要るなら新しい形式に入れる。
   - 案 B: 新しい形式の一連と並べて進める。形式の変更を入れやすいが、回路設定がまだない。
   - 案 C: 今は保留のまま（実装するか決めない）。

2. **持ち込んだときの、ぶつかりの扱い**
   - `id` が同じモジュールがすでにある（同じモジュールの別の版）:
     - 推す案: 利用者に聞く。「置き換える（更新）」「持ち込まない」を選べる。置き換えでピンが変わるとき（ポート番号やパッケージが違うとき）は、そのことを知らせる。
   - `id` は違うが、名前が同じモジュールがある（パスはフォルダだけなので、ぶつかりは名前で見る。同じフォルダの中だけで見るか、プロジェクト全体で見るかも決める。決め直しが要る）:
     - 推す案: 持ち込むモジュールの名前の最後に ` (2)` などを付けて足す。聞かない（別のモジュールなので、置き換える理由がないため）。
   - 一度に複数がぶつかったときの聞き方（まとめて 1 回聞くか、1 つずつか）も決める。推す案: まとめて 1 回（一覧で見せて、全部置き換える・全部やめるを選ぶ）。

3. **書き出しの単位**（2026-10-17: プロジェクト全体、モジュール 1 つ、複数のモジュールを、それぞれ 1 ファイルで書き出せるようにする、と決めた。下の細かいところが残っている）
   - モジュールを書き出すファイルは、1 つでも複数でも、いつも「モジュールの束」の形式にする（例: `"format": "sazanka-modules"`）（2026-10-17）。数でファイルの形が変わるとややこしいため。中身はプロジェクトの要素と同じ形の並び（パスとインラインのモジュール）で、メイン回路を持たない。持ち込むと、要素がそのままプロジェクトの並びに加わる（フォルダも持ち込める）。
     - 採らなかった案: 1 つのときはモジュールの形式（`"sazanka-module"`）そのままで書く。プロジェクトの形式で、メイン回路なしを許す。
     - モジュールの形式だけのファイル（手で作ったものなど）も持ち込めるようにするかは、下位の計画「モジュールのファイル」で決める。
   - 書き出すモジュールが使うモジュール（入れ子）
     - 推す案: 書き出すときに、使っているモジュールも入れるかを選べるようにする（既定は入れる）。入れないと、持ち込み先で足りなければ未解決のモジュールになる。
     - 案 B: いつも入れる（足りないことが起きない）。
   - 新しい形式（束）は、プロジェクトとモジュールの形式とは別に v1 から数える。計画 19 の時点では作らず、下位の計画「モジュールのファイル」で作る（新しい種類を足すだけなので、ほかの形式の版には響かない）。

4. **メイン回路を、モジュールとして書き出せるか**
   - 推す案: 書き出せない。メイン回路は `id` が `"main"` でどのプロジェクトでも同じなので、持ち込むと見分けられない。メイン回路を部品として使いたいときは、モジュールに移す操作（別の計画）で扱う。
   - 案 B: 書き出せる。持ち込むときに新しい `id` を付けて、ふつうのモジュールにする。

5. **モジュールの名前の重なり**（パスの決まりは計画 19 で決めた。名前の扱いが残っている。決め直しが要る）
   - 今は、モジュールの名前は追加では重なりを断るが、改名では断っていない。フォルダで整理すると、同じ名前を許す範囲（同じフォルダの中では重ならないようにするか、プロジェクト全体で重ならないようにするか、重なってもよいか）を決める必要がある。
   - 推す案: 同じフォルダの中では重ならないようにする（ファイルの置き場所と同じ考え方）。持ち込みや改名で重なったら ` (2)` などを付ける。

6. **フォルダの見せ方と、フォルダを変える操作の置き場所**（決め直しが要る）
   - 推す案: プロジェクトパネルで、フォルダを木の形で見せて折り畳めるようにする。モジュールをフォルダへ動かすのは、プロジェクトパネルでのドラッグと、行の操作（「フォルダを変える」）。タブとパレットはモジュールの名前を出す（フォルダは出さない）。パレットのモジュールのグループは、フォルダごとにまとめるかを、プロジェクトパネルの計画で決める。

7. **未解決のモジュール**（2026-10-17 に開発者が挙げた）

   指す先のモジュールがプロジェクトにない部品を、断らずに「未解決のモジュール」として仮に置いておき、何が足りないかを見えるようにする案。足りないモジュールを持ち込めば（同じ `id`）、そのまま解決する。

   - 今は、指す先のないモジュールの部品があると、読み込みで壊れたデータとして断る（`circuit/project.ts` の `checkProject` の `MISSING_MODULE`）。シート上では、名前が引けないと「(不明)」と書く（`sheet/SheetPart.tsx`）。
   - 何が足りないかを見せるため、参照する側（部品。新しい形式では `moduleId` で指す）に、指すモジュールの名前の写しを持たせる（識別は `id` だけで行い、名前は表示の手がかり）。項目名の候補: `moduleName`、`moduleLabel`。
   - 決めること（推す案を先に書く）:
     1. 未解決を許すか
        - 推す案: 許す。読み込みで断らず、未解決として開く。形式の上では、計画 19 でプロジェクトの参照だけの要素を書けるようにしてある（アプリは計画 19 の時点では断る）。部品の名前とピンの写しを足すなら、新しい形式を公開する前に入れるか、あとで省略できる項目として足す。
        - 案 B: 今までどおり断る（名前の写しは、データを読む人のためだけになる）。
     2. 名前の写しをいつ書くか
        - 推す案: 保存するときに、指しているモジュールの今の名前を写す。モジュールがあるときは、表示にはモジュールの名前を使い、写しは使わない。改名しても部品を書き換える処理は要らない。未解決の部品は、読み込んだ写しをそのまま持ち続ける。
        - 案 B: アプリの中でも部品に名前を持たせ、改名のたびに、そのモジュールを指す部品をすべて書き換える。
     3. 未解決の部品の見た目と、ピン
        - 推す案: ピンの形（パッケージと、ピンごとの入力・出力・名前）の写しも部品に持たせ、未解決でも同じ大きさとピンで描く。つながっていた配線が外れて見えないようにするため。本体は破線などで未解決と分かるようにし、名前の写しと「見つからない」を書く。
        - 案 B: ピンの写しは持たせず、決まった大きさの箱で描く（ピンはない。つながっていた配線は外れて見える）。データは小さい。
        - ピンの写しはピン数の多いモジュール（128 ピン）だと大きくなる。置いた数だけ写すので、保存データが大きくなる。
     4. 未解決の部品のシミュレーション
        - 推す案: 出力ピンはすべて OFF、入力は使わない。ステータスバーに「見つからないモジュールがあります」のバッジを出す。
     5. 未解決になる場面
        - 使われているモジュールをプロジェクトから削除したとき（決めたこと）。
        - 外から来たデータ（共有用 JSON、モジュールのファイル）に足りないモジュールがあるとき。持ち込みでは使うモジュールも一緒に書き出す（3 の推す案）ので、ふつうは起きない。
   - 「ファイル名」（モジュールを持ち込んだ元のファイルの名前）も持たせるかは、何に使うかを聞いてから決める。

## 叩き台

プロジェクトの形は[計画 19](../project-format/plan.md)の「プロジェクトの形」にある。モジュールの束（モジュールを書き出すファイル。3 で決めた）は、たとえば次の形:

```json
{
  "format": "sazanka-modules",
  "version": 1,
  "modules": [
    { "path": "adders", "module": { "format": "sazanka-module", "version": 1, "id": "7b3e…", "name": "全加算器", ... } },
    { "path": "adders", "module": { "format": "sazanka-module", "version": 1, "id": "c91a…", "name": "半加算器", ... } }
  ]
}
```

## 問題点

- 置き換え（更新）でピンが変わると、置いた先の外側の配線が別のピンにつながったり、どこにもつながらなくなったりする。新しい形式で split もポート番号で決まるようになるので、変わるのはポート番号・パッケージ・ピンの割り当てを変えたときに限られる。それでも、置き換える前に知らせる工夫が要る。
- 置き換えで、モジュールの中がまるごと入れ替わる。持ち込む前のモジュールを持ち込み先で直していたら、その変更は消える（元に戻すで戻せる）。
