# 保存データの version 5（計画）

状態: **廃案**（2026-10-17。保存データをプロジェクトとモジュールに分け、どちらも v1 から数えることにしたので、version 5 はなくなった。この計画の中身は [保存データをプロジェクトとモジュールに分ける](../project-format/plan.md)（計画 19）にまとめた。以下は廃案にした時点の記録）

- 段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../docs/workflow.md)の「実装を始める合図」）。
- 決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../docs/documentation.md)の「計画の文書」）。

## 目的

保存データと共有用 JSON の形式を version 5 に上げる。中身は次の 2 つ。

1. パッケージが split のモジュールの外側のピンの順を、中の INPUT / OUTPUT の位置の順から、ポート番号の順に変える（目的と画面の側は [split のピンの順をポート番号の順にする](../split-pin-order/plan.md)）。
2. メイン回路にもパッケージを持たせる（目的と画面の側は [メイン回路をモジュールと同じに扱う](../main-as-module/plan.md)）。

どちらも古いデータをそのままでは同じ意味で読めない（1）か、形が変わる（2）ので、版を上げて変換を足す（[保存データ](../../docs/persistence.md)の「開発者からの指示」）。版上げを 1 回で済ませるため、形式の変更をこの計画にまとめる（開発者が決めた、2026-10-17）。

## 3 つの計画の関係と順番

| 計画 | 中身 |
| ---- | ---- |
| この計画（17） | 形式の変更、版上げ、古いデータの変換、形式の文書、ピンの順の計算 |
| [メイン回路をモジュールと同じに扱う](../main-as-module/plan.md)（18） | 形式以外。メイン回路でもモジュール設定を開けるようにする、ヒントなど |
| [split のピンの順をポート番号の順にする](../split-pin-order/plan.md)（16） | 形式以外。ポート番号を変える操作、split から DIP / QFP に変えたときの割り当て順、文言 |

- 進める順は 17 → 18 → 16。17 でデータの形と計算を変え、18 でメイン回路にもモジュール設定を開けるようにし、16 でポート番号を変える操作をモジュール設定に足す（メイン回路でも使える）。
- 公開は手動（[公開](../../docs/release.md)）。17 だけを公開すると、split でピンの順を並べ替える手段がない（番号を変える操作は 16 で足す）。3 つが揃うまで公開しない。

## 取り決め（開発者からの指示、2026-10-14）

- プログラムの上でも、ポートの並びは基本的にポート番号の順を前提にする。位置の順（上から、同じ高さなら左から）を使うのは、番号を振り直すときだけ。
- この取り決めは、[用語](../../docs/glossary.md)の「回路のデータ」に「開発者からの指示」として書く（段階 1）。

## 前提

- 保存データの形式は version 4（2026-10-13 に公開）。
  - split のピンの順は、形式の文書（`docs/format/v4.md` の「モジュールのピン」）で「座標の順」と決めている。
  - メイン回路は名前とパッケージを持たない（`docs/format/v4.md` の「回路」）。モジュールのパッケージは省略できない（既定値で補うと、既定値を変えたときに古いデータのピンの位置が変わるため）。
- 位置の順を使っている所（`circuit/module.ts`）:
  1. `getPortsInPinOrder` の split の分岐: split の外側のピンの順。展開（`simulation/flatten.ts`）とシート上の配置（`getPinout`）がこれを使う。**この計画で番号の順に変える**。
  2. `assignPortNumbers`: 置いた・貼り付けたポートが複数あるとき、番号を付ける順。番号を振る処理なので位置の順のまま。
  3. `fillPortNumbers`: 読み込みで、番号がない・重なるポートに番号を付け直す順。同じく位置の順のまま。
  4. `listPortsInPositionOrder`: モジュール設定の「上から順に割り当て直す」と、split から DIP / QFP に変えたときの割り当て順（計画 16 で決める）。
- メイン回路を特別に扱っている計算: 検証（`circuit/project.ts` の `checkCircuit`。モジュールにだけ名前とパッケージを求める）、保存の形との変換（`file/storage.ts`。メイン回路の名前を書かない・捨てる）、空のプロジェクト（`emptyProject`。メイン回路にパッケージがない）。置いたポートへのピン番号の付け方（`assignPinNumbers`）は、パッケージがないものを split と同じに扱う。

## 決めたこと

開発者が決めたこと。

- split の外側のピンの順を、ポート番号の順にする。入力は入力のポート番号の順、出力は出力のポート番号の順（2026-10-14）。
  - 採らなかった案: split は位置の順のまま、取り決めの例外にする（版を上げずに済み、番号を変える操作も要らないが、ポートを動かすとピンが入れ替わる課題が残る）。
- 古いデータ（version 4 まで）は、変換（`upgradeV4`）で、split のモジュールの中の INPUT / OUTPUT のポート番号を、入力と出力で別々に、1 から位置の順（上から、同じ高さなら左から）に振り直す。そのあとは番号の順でピンが並ぶので、今の配線は同じピンにつながったまま（2026-10-14）。
  - 飛びのある番号は詰まる。例: 番号が 1、3、4 で、位置が上から入力 4、入力 1、入力 3 なら、上から 1、2、3 になる。
  - 位置の順と番号の順がもともとそろっていて飛びもないモジュール（ふつうに上から置いたもの）は、番号が変わらない。DIP / QFP のモジュールは変えない。メイン回路も振り直す（下の決めたこと）。
  - 採らなかった案: 今ある番号の組はそのままに、位置の順に配り直す（上の例なら 1、3、4。変わる番号は少ないが、決め方が込み入る）。
- メイン回路にもパッケージを持たせる（2026-10-17）。メイン回路は「外側のピンがどこにもつながっていないモジュール」とみなす。DIP / QFP にしてピン番号を割り当てても、ピンはどこにもつながらない。
- メイン回路は、今までどおりほかの回路に置けない（2026-10-17）。
- 形式の変更は、この計画（version 5）にまとめ、形式以外の画面と操作は計画 16 と 18 に分ける（2026-10-17）。
- version 5 では、メイン回路のパッケージも省略できない（モジュールと同じ）。変換（`upgradeV4`）では、メイン回路に split を書き込む（2026-10-17）。
  - 理由: モジュールのパッケージを省略できなくしたのと同じ（既定値で補うと、既定値を変えたときに古いデータの意味が変わる）。
  - 採らなかった案: 省略でき、ないときは split とみなす。
- 変換では、メイン回路のポート番号も、split のモジュールと同じく位置の順に振り直す（2026-10-17）。変換の決まりを、メイン回路とモジュールで同じにするため。メイン回路のピンはどこにもつながらないので、配線には響かない。シート上の「入力 1」などの表示が変わることはある。
  - 採らなかった案: メイン回路は振り直さない（配線を保つための振り直しが要らないため）。
- version 5 は、[保存データ](../../docs/persistence.md)の「版の状態」で「作業中（未公開）」として管理する（2026-10-17）。
- version 5 の中身は、まだ足されるかもしれない（2026-10-17）。足すものが出たら、この計画に書き足し、変換（`upgradeV4`）も直す。version 5 を公開するまでは、変換を直してよい（[保存データ](../../docs/persistence.md)の「開発者からの指示」）。
- 3 つの計画（17、18、16）は、1 本のブランチ `format-v5` で順に進め、揃ってから 1 回でマージする（2026-10-17）。3 つが揃うまで公開しないので、途中の状態を `main` に入れない。
  - 採らなかった案: 計画ごとにブランチを分け、順にマージする。


## 段階

各段階で、`npm run format`、`npm run lint`、`npx tsc -b`、`npm test`、`npx vite build` を通す。

1. 取り決め
   - [用語](../../docs/glossary.md)に取り決めを書く。
2. version 5 の形式と変換
   - `STORAGE_VERSION`（`file/storage.ts`）と `SHARE_VERSION`（`file/share.ts`）を 5 にし、`file/upgradeV4.ts` の `upgradeV4`（version 4 → 5）を作って `file/upgrade.ts` の `UPGRADES` に足す。変換は、ポート番号の振り直し方とメイン回路のパッケージの決め方を中に持つ（今のアプリのコードに頼らない）。
   - 検証（`checkProject`）: メイン回路にもパッケージを求める。
   - 空のプロジェクト（`emptyProject`）のメイン回路に split を持たせる。
   - `getPortsInPinOrder` の split の分岐を、ポート番号の順にする。
   - 形式の文書: `docs/format/v5.md` を作り（冒頭に「まだ公開していない」と書く）、`v4.md` を `docs/format/archive/` に移す。「回路」（メイン回路のパッケージ）、「モジュールのピン」（split は番号の順）、「version 4 からの変更」を書く。
   - [保存データ](../../docs/persistence.md)の版と変換の記述を直す。
   - テスト:
     - `upgradeV4`: 位置と番号がそろっているもの、ずれているもの、飛びのあるもの、番号がない・重なるもの、DIP / QFP は変えないこと、メイン回路に split が付き、ポート番号が位置の順に振り直されること。
     - いちばん古い版から version 5 まで順に通すテスト。
     - split のピンの順が番号の順になること（`module.test.ts`、展開の `flatten`）。
     - **変換の前後で、置いた先の配線が同じピンにつながったままなこと**（version 4 の回路を変換して展開し、シミュレーションの結果が変わらないこと）。
     - 検証が、パッケージのないメイン回路を断ること。
   - ブラウザで: version 4 の保存データと共有用 JSON を読み込むと、配線が今までどおりつながり、シミュレーションの結果が変わらないこと。新規作成と、書き出したものの読み込みができること（[保存データ](../../docs/persistence.md)と[ブラウザでの動作確認](../../docs/browser-check.md)の「保存の確かめ方」）。

実装は Skill の `modify` で進める。

## 気になるところ

- [保存データをプロジェクトとモジュールに分ける](../project-format/plan.md)（計画 19）を、version 5 と同じときに公開すると決めた（2026-10-17）。計画 19 が揃うまで、version 5 も公開しない。この計画との分担は、計画 19 の「決めてほしいこと」の 5。

- 版を上げると、古い版のアプリ（もう公開していない）は新しいデータを読めない。今は最新版だけを公開しているので問題にならない（[保存データ](../../docs/persistence.md)の「形式を変えるとき」）。
- 変換でポート番号が変わったモジュールでは、シート上の「入力 1」などの表示が、前と違うポートに付く。配線とピンの順は保たれる。
- `fillPortNumbers`（読み込みで番号がない・重なるポートに付け直す）は位置の順のまま。version 5 のデータで番号が重なっていたら、split のピンの順は、付け直したあとの番号の順になる。
- この計画だけを終えた時点では、split でピンの順を並べ替える手段がない（計画 16 で足す）。公開しないこと。
