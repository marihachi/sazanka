# 保存データの version 4（計画）

状態: **計画中**（ほかの形式の変更とまとめて版を上げる。まとめる変更が決まるまで実装しない）。

- 段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../docs/workflow.md)の「実装を始める合図」）。
- 決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../docs/documentation.md)の「計画の文書」）。

## 目的

- 保存データと共有用 JSON で、部品の位置（`x`、`y`）と配線の点（`points` の `x`、`y`）を、px ではなくマス単位（グリッド上の点）で持つ。シートの大きさ（`sheet`）はすでにマス単位なので、単位がそろう。
- 回路・部品・配線の ID を、プロジェクトをまたいでも重ならないものにし、一度付けたら付け直さないようにする。
- 使っていないメイン回路の `name` を保存しない。

## 背景

- version 3 では、位置は px（1 マスは 20px）。アプリで置いた部品と引いた配線は、`snap` を通るのですべて 20 の倍数になる。
- 読み込みの検証は数値かどうかしか見ていない。手で書いたデータには、20 の倍数でない値が入りうる。
- version 3 は公開済みで、今ある項目や値は変えない（`docs/format/v3.md`）。単位を変えるには版を上げる。
- version 3 の ID（`docs/format/v3.md` の「ID の付け方」）:
  - アプリの中では、ランダムな 8 文字（`circuit/circuit.ts` の `newId`。約 41 ビット）。重ならないのは、回路の ID はプロジェクトの中、部品と配線の ID は回路の中だけ。
  - 共有用 JSON に書き出すときは、部品と配線の ID を回路ごとに `part-1`、`wire-1` からの連番に付け直し、読み込むときにランダムな ID に付け直す（`file/share.ts` の `renameIds`）。そのため、共有用 JSON の中では、別の回路どうしで ID が重なる。
  - モジュールを別のプロジェクトへ持ち込むと（[モジュールのファイル保存と再利用](../module-files/plan.md)）、回路の ID がぶつかりうる。

## 決めたこと

- 部品の位置と配線の点を、どちらもマス単位で保存する。
- 項目名は `x` / `y` のまま。単位は形式の仕様に書く。
- version 4 の検証では、位置は整数でなければ断る。アプリで置けないマスの途中の位置を読み込まないため。
- version 3 からの変換では、位置を 20 で割り、いちばん近いマスに丸める。部品と配線を同じ規則で丸めるので、縦横の向きと、ピンの先とのつながりは保てる。
- 版を上げる時期: ほかの形式の変更とまとめて上げる。何とまとめるかは、まだ決まっていない。
- INPUT / OUTPUT の名前のキー `label` を改名する。画面とドキュメントで「ラベル」を「ポート名」と呼ぶことにしたため（[メイン回路の INPUT / OUTPUT もポートと呼ぶ](../toplevel-port/plan.md)）。「ラベル」は、配線と配線を名前でつなぐ機能のために空けておく。
  - 新しいキーの名前は `portName`（開発者が決めた。用語の「ポート名」と対応する）。採らなかった案: `name`（短いが、回路の `name` と紛らわしい）。
  - version 3 からの変換では、`label` を新しいキーに移す。
  - コードの `Part.label` と、それに合わせた名前（`setLabel`、`findDuplicateLabels` など）も、新しいキーに合わせて改名する。
- ID は、プロジェクトをまたいでも重ならないものにし、付け直さない（開発者が決めた）。
  - 理由: モジュールを別のプロジェクトへ持ち込むときに、ID を付け直さずに済ませるため。部品の ID だけで、どの回路のどの部品かも決まる。
  - 新しい ID を付けるのは、新しい物を作るときだけ（部品を置く、貼り付ける、配線を分ける、モジュールを足すなど）。書き出し、読み込み、持ち込みでは付け直さない。
  - 共有用 JSON の書き出しで、部品と配線の ID を `part-1`、`wire-1` からの連番に付け直すのをやめる。読み込みでの付け直しもやめる。
  - メイン回路の ID は `"main"` のまま（開発者が決めた）。どのプロジェクトにもある特別な ID として扱い、「プロジェクトをまたいでも重ならない」の対象から外す。メイン回路は別のプロジェクトへ持ち込まないので、ぶつからない。ほかの回路・部品・配線は `"main"` を ID に使えない。
  - 形式の仕様には「プロジェクトをまたいでも重ならない文字列」とだけ書き、UUID の形とは決めない（開発者: UUID でなくてもよい）。
  - 展開後の部品 ID の付け方（`外側の部品ID/内側の部品ID`。`simulation/flatten.ts`）は変えない。同じモジュールを何か所に置くと、中の部品の ID は同じなので、前置きは要る。
- メイン回路は `name` を持たない（開発者が決めた）。
  - 理由: メイン回路は改名できず、タブなどに出す名前は表示言語の文言（`メイン` / `Main`。`i18n/messages.ts` の `circuitName`）から引くので、`name` を使っていない。version 3 では新規作成で `'メイン'` が固定で入り、英語で使っていてもそのまま保存される。
  - 書き出しと保存では、メイン回路の `name` を書かない。
  - version 4 の検証では、メイン回路（`id` が `"main"` の回路）の `name` を見ない。あっても断らずに捨てる。
  - version 3 からの変換では、メイン回路の `name` を消す。
  - 検証のエラーに入れる回路の名前（`circuit/project.ts` の `checkProject` が返す `circuit`）は、メイン回路なら表示言語の「メイン」/「Main」にする。version 3 では `def.name` を入れているので、表示言語に関係なく「メイン」と出る。
- 次の 3 つは、エージェントの案を開発者が了承した。
  - ID の作り方: `crypto.randomUUID()`（122 ビット）を使う。プロジェクトをまたぐと、今の 8 文字（約 41 ビット）では重なるおそれを無視しきれないため。
  - version 4 の検証: ID が文字列で、プロジェクトの中で（回路・部品・配線のすべてで）重ならないことを確かめる。重なっていたら断る。UUID の形かどうかは見ない。
  - version 3 からの変換: メイン回路以外のすべての ID を新しい ID に振り直し、部品の `module` の参照も書き換える。version 3 の ID は回路をまたいで重なりうる（`part-1` など）ため。付け直すのは、この変換の 1 回だけ。

## 実装の方針（エージェントが決めたこと）

- アプリの中は px のままにし、保存・書き出し・読み込みのときだけマスと px を変換する。
  - 描画、当たり判定、ネットの計算（`geometry/`、`sheet/`、`editing/edit.ts`）は px で書かれている。中までマスにすると影響が大きい。中をマスにするなら、版上げとは別のリファクタリングとして計画する。
  - 変換は `circuit/project.ts` に置く。読み書きのたびに通す `withoutSwitchStates` と同じ並び。新しいファイルは作らない。
  - 読み込み: 版の変換（`upgradeProject`）→ 検証（`checkProject`。マス単位の形で確かめる）→ px に直す。
  - 保存・書き出し: px をマスに直す（20 で割る）。
- `file/upgradeV3.ts` の `upgradeV3`（version 3 → 4）は、マスの大きさ 20 を自分の中に持つ。今のコードの `GRID` には頼らない（[保存データ](../../docs/persistence.md)の「形式を変えるとき」）。
- メイン回路の `name`: アプリの中の型（`CircuitDef.name` を省略できるようにするか、アプリの中では持ち続けて読み書きのときだけ外すか）は、実装のときに決めてここに書く。
- ID:
  - `newId` の中身を `crypto.randomUUID()` に変える。呼ぶ側は変えない。
  - `upgradeV3` は、新しい ID を作る関数を引数で受け取る（`parseProject` の `newId` と同じ渡し方）。テストで決まった ID を渡せるようにするため。
  - `file/share.ts` の `renameIds` を消す。
  - localStorage の `sazanka.views`（回路 ID ごとの表示）は、変換でモジュールの ID が変わると引けなくなり、既定の表示に戻る。メイン回路の表示は残る。付け替えない（開発者が決めた。変換は一度きりで、戻るのは表示位置だけのため）。採らなかった案: `upgradeV3` が古い ID と新しい ID の対応を返し、表示にも当てはめる。

## 段階

1. 形式の仕様: `docs/format/v4.md` を作り、`docs/format/v3.md` を `docs/format/archive/` に移す。リンクを直す。
   - 確かめること: リンク切れがないこと。
2. 変換と読み書き: `upgradeV3` を作って `UPGRADES` に足す。`STORAGE_VERSION` と `SHARE_VERSION` を 4 にする。マスと px の変換と、検証（整数、ID の重なり）を入れる。ID の付け直し（`renameIds`）をやめ、`newId` を変える。メイン回路の `name` を書かず、読み込みでは見ない。
   - テスト: `upgradeV3` のテスト（ID の振り直しと `module` の参照の書き換え、メイン回路の `name` を消すことを含む）、version 1 から 4 まで順に適用するテスト、保存と共有用 JSON の往復のテスト（ID が変わらないこと）、ID が重なるデータを断るテスト。
   - 確かめること: `npm run lint`、`npx tsc -b`、`npm test`、`npx vite build`。
3. ドキュメントと動作確認: `persistence.md`（ID の付け直しの記述）、`browser-check.md`、`screenshot.md`（例の JSON）を直す。
   - ブラウザで確かめること: version 3 の保存データと共有用 JSON を読み込み、書き出して読み直しても同じ回路になること（ID も同じ）。モジュールを含む回路がシミュレーションで動くこと。

実装は Skill の `modify` で進める。
