# 作業の進め方

## 言語

開発者とのやりとり、コードのコメント、ドキュメントは日本語で書く。UI の文言は、日本語と英語の両方を書く（利用者が表示言語を選べるため。書き方は[文言と表示言語](i18n.md)）。

開発者の画面に出るものは、すべて日本語にする。返答の本文だけでなく、ツールを呼ぶときの説明や、確認用のスクリプトが出す文言も含む。(開発者からの指示)

## Node のバージョン

- Node は、サポート期間中のすべての LTS で動くようにする。サポートが終わった Node のための書き換えはしない。(開発者からの指示)
- CI（`.github/workflows/`）は、サポート期間中でいちばん古い LTS で動かす。いちばん古い LTS で動けば、それより新しい LTS でもたいてい動くため。そのサポートが終わったら、次の LTS に上げる。

## 変更したあとの確認

1. `npm run format` で整形する（Biome）。
2. `npm run lint`、`npx tsc -b`、`npm test`、`npx vite build` を通す。

- `npm run build` は、型チェックとビルドをまとめて行う。`npm run check` は整形と Lint をまとめて確かめ、`npm run format:check` は整形されているかだけを確かめる。
- `npm run lint` と `npm run check` は、Biome のあとに `.agents/skills/` と `.claude/skills/` が同じかも確かめる（[Skill の追加・編集](skills.md)の「一致の確認」）。
- Markdown は Biome の対象外。ドキュメントは手で整える。
- 改行コードは LF にそろえている（`.gitattributes` と `biome.json`）。`core.autocrlf=true` の環境でも、`.gitattributes` があるので CRLF にならない。
- Windows では、`npm test` がまれに全テストファイルの読み込みに失敗し、「no tests」で終わることがある。原因は分かっていない（作業フォルダのドライブ名が `c:` と `C:` で切り替わった直後に起きやすい）。個々のテストが失敗したのではなく、全ファイルがまとめて読めなかったときは、まず再実行する。たいていは通る。

### 開発者からの指示

- 変更したら、上の確認をひととおり通す。
- 画面や操作に関わる変更をしたら、ヘッドレスブラウザで動きを確かめる。テストとビルドが通るだけで済ませない。やり方は Skill の `browser-check`、このアプリ固有のことは[ブラウザでの動作確認](browser-check.md)にある。
  - クリック、ダブルクリック、ドラッグ、文字の入力は、人の速さと間隔でする。一瞬で操作すると、人の操作では起きない失敗をしたり、人の操作でだけ起きる不具合を見逃したりするため。
  - React で描画するコードを変えたときは、フレームレートが下がっていないかも測る。重さは機能の確認では気付けず、あとから原因を探すのが難しいため。純粋な計算処理は対象にしない。重くなりやすいのは描き直しの方だから。当てはまるファイルは[ブラウザでの動作確認](browser-check.md)の「フレームレートを測る」にある。
  - 作業の区切り（一連の置き換えや機能の追加が終わったとき）と、開発者に頼まれたときは、荒い操作のテスト（連打、ドラッグ中の割り込み、画面の外へのドラッグ、おかしな入力など）もする。対象は、その作業で触った範囲。
  - 確かめられなかったものは、報告にそう書く。

## コミット・push・PR

手順は Skill の `commit` にある。

以下は開発者からの指示です。

- コミットと push は、開発者に頼まれたときだけ行う。
- 次のときは、頼まれなくてもコミットと push をしてよい。
  - 計画を始めるとき（下の「計画を始める」）。
  - 計画の実装で、段階を終えたとき。作業用のブランチの実装（下の「実装を始める合図」）。
  - 計画の文書（計画の一覧を含む）を `main` で直したとき。段階の記録やレビューの記録だけでなく、計画を作るときや、決めたことを書き足すときも含む。
  - 計画を完了にするとき（下の「計画を完了にする」）。
  - `main` を `next` に、`next` を計画のブランチに取り込むとき（下の「ブランチ」）。
  - 開発者に指示されて `next` を `main` に取り込むとき（下の「`next` を `main` に取り込む」。マージと、そのあとの公開済みにする変更（作業中の版があるときだけ）と取り込み）。
- コミットを頼まれても、ブランチを勝手に作らない。今のブランチにコミットする。ブランチを分けた方がよさそうなときは、コミットする前に開発者に聞く。計画のブランチは、「計画を始める」の手順で作る。
- 計画の文書は、作成も変更も `main` で行う（[ドキュメントの書き方](documentation.md)の「計画の文書」）。
- 計画の PR は、エージェントが作る（GitHub CLI の `gh pr create`）。最初の段階の実装を push するときに、ドラフトで作り（`--draft`）、実装を終えてレビューできるようになったら、レビュー待ちにする（`gh pr ready`）。開発者のレビューで了承を得たら、エージェントが squash でマージする（`gh pr merge --squash`。下の「計画を完了にする」）。`next` から `main` への一番上の PR は、開発者に指示されたときだけ、エージェントがふつうのマージでマージする（下の「`next` を `main` に取り込む」）。
- 上位の計画（下位の計画に分けたもの。[ドキュメントの書き方](documentation.md)の「計画の文書」）の PR は、エージェントがマージしない。上位の計画は、ふつう自分の PR を持たず、実装は下位の計画の PR でマージする。上位の計画の PR があっても、マージするかは開発者に聞く（開発者が決めた、2026-10-24）。

## ブランチ

以下は開発者からの指示です。

- `main` は、公開している版。公開するのは `main` にある内容（[公開](release.md)）。
- `next` は、`main` に取り込む前の作業を保持するブランチ。計画の実装は、ここに集める。
  - 理由: `main` を、公開している版のまま保つため。今の版の不具合を直して公開するときも、`main` から直せる。
- 計画のブランチは、計画ごとに 1 本、`next` から作る。名前は計画のフォルダ名にそろえる（例: `project-format`）。計画の PR は `next` に向ける。
- `next` から `main` への PR を、一番上の PR にする。差のないブランチ同士の PR は作れないので、最初の計画の PR が `next` にマージされたあとで作る。説明には、`next` に入った計画の一覧を書く。マージは、公開するときに、開発者の指示でエージェントが行う（下の「`next` を `main` に取り込む」）。
- ブランチは git でマージせず、PR でマージする。例外は、下の取り込み。
- `main` の変更（`main` で直した計画の文書や決まりなど）は `next` に、`next` は作業中の計画のブランチ（PR を作ったものを含む）に、定期的に取り込む。エージェントが聞かずに行ってよい。
  - 取り込む時機: `main` にコミットして push したあと（続けて計画のブランチにも）と、計画のブランチを作る前。
  - fast-forward できるとき（取り込む先に、取り込む元にないコミットがないとき）は、そのまま進めて push する（例: `git push origin origin/main:next`）。できないときは、マージして push する。
  - マージでぶつかったら、自分で解かずに止めて、開発者に見せる。
  - 理由: 取り込まずにおくと、最後に `next` を `main` へマージするときにぶつかりやすくなるため。計画のブランチで、古い決まりや計画の文書のまま作業しないようにするため。
- ほかのブランチ（`main` など）で直すときは、別の作業フォルダ（`git worktree`）を使わず、いつもの作業フォルダでそのブランチに切り替えて作業する。別の作業フォルダの変更は、開発者がエディターから見られないため。今のブランチにコミットしていない変更が残っていて切り替えられないときだけ、別の作業フォルダを使ってよい。そのときは、そう報告する。

## `next` を `main` に取り込む

以下は開発者からの指示です（2026-10-24）。

`next` を `main` に取り込むのは、公開するとき。開発者が「`next` をマージして」のように指示したら、エージェントが次の順に行う。指示がなければ、一番上の PR はマージしない。取り込んだあとの公開（Deploy の実行）は開発者が行う（[公開](release.md)）。

1. 一番上の PR（`next` → `main`）を、ふつうのマージ（Create a merge commit。`gh pr merge <番号> --merge`）でマージする。squash や rebase はしない。ブランチは消さない（`--delete-branch` を付けない）。
   - 理由: squash や rebase だと、`next` の履歴が `main` の祖先にならず、次の一番上の PR に今回のコミットがまた出てぶつかる。`next` は強制 push と削除がルールセットで禁止されているので、作り直せない。
2. `main` で、作業中（未公開）だった形式の版を公開済みにする。[保存データ](persistence.md)の「版の状態」を「公開済み」にして公開した日を書き、形式の文書（`docs/format/`）の冒頭にも公開した日を書く。コミットして push する。作業中の版がなければ（今回の取り込みで形式の版が変わっていなければ）、この手順は飛ばす。
3. `main` を `next` に取り込む（上の「ブランチ」の取り込み。ふつうのマージなら fast-forward できる）。`next` は作り直さず、このまま次の公開に向けて使い続ける（次の計画のブランチも、ここから作る）。
4. 次の一番上の PR は、次の計画の PR が `next` にマージされたあとで作る（上の「ブランチ」）。
5. したこと（マージしたコミット、公開済みにした版（なければ、なかったこと）、取り込んだ結果）を報告し、Deploy を実行して公開するよう開発者に伝える。

## 合意してから進める

判断が要るものは、案を示して開発者の合意を得てから始める。

- 示すもの: 案（複数あれば候補と、推す案とその理由）、影響が及ぶ範囲、選ばなかった案の理由。名前なら候補を複数挙げる。
- 合意が要るものと、エージェントが決めてよいものの分け方は、下の「開発者からの指示」にある。
- 進めている途中で案を変えたくなったら、勝手に変えずにもう一度示す。
- 迷ったら、決め打ちせずに聞く。
- 計画を立てる手順は Skill の `plan` にある。

### 開発者からの指示

- 合意が要るのは、次のもの。
  - 保存データと共有用 JSON の形式（項目名や値の名前を含む）。
  - 画面の作りと操作の割り当て、画面に出る文言。
  - フォルダやファイルの構成（分け方、置き場所、ファイル名）。
  - ライブラリの追加、Skill の追加・変更・削除。
- プログラムの実装の中のことは、エージェントが決めてよい。
  - 型、関数、変数、定数の名前。
  - 関数の分け方、引数と戻り値の形、データの渡し方。
  - ファイルの中のコードの並べ方。
  - 決めた内容は、計画の文書に書く（[ドキュメントの書き方](documentation.md)の「計画の文書」）。計画がない作業では、報告に書く。
- どちらか迷ったら聞く。
- 実装の途中で、計画で決めていないことに出会い、案が複数あってどれが良いか確信が持てないときは、開発者に聞く。確信が持てるときは決めて進め、決めた内容と理由を計画の文書（計画がない作業では報告）に書く。
- 取り決め（ドキュメントに書く方針や決まり）の変更は、案を示さずにその場で直してよい。ただし開発者が決めた規則（[AGENTS.md](../../AGENTS.md) の「規則の扱い」）は、開発者が意向を示したとき（「〜しましょうか」でもよい）だけ直す。
- 開発者の指示ややり方に気になる点（危うさ、もっと良い方法、ほかの決まりとの食い違い）があれば、従う前にその旨を伝える。開発者の提案が最善とは限らず、ほかの方法に開発者が気付けないことがあるため。伝えたうえで、どうするかは開発者が決める。

## 実装を始める合図

以下は開発者からの指示です。

- 実装（ソースコード、画面、ファイル名など、アプリの実装の変更）は、開発者から始めることをはっきり指示されてから始める。計画や調査を頼まれたときは、実装を始めない。
- 合図にするのは、始めることを直接言っている指示だけ。例: 「開始して」「実装を始めて」「作ってください」「その内容で実装して」。
- 曖昧な答えは合図にしない。例: 「その内容でいいよ」「OK です」「それでいきましょう」「いいですね」「〜しましょうか」。これらは計画への合意で、実装を始める指示ではない。
- 「進めて」のように、何を進めるのかが文脈で分かれるものも、実装を始めることがはっきりしなければ合図にしない。
- ファイル名の変更も実装に含む。名前への合意だけでは改名しない。
- 計画の実装は、開始の合図があれば、段階の区切りで止めずに最後の段階まで進める。最後に PR でレビューを受けるため。
  - 段階を終えたら、確認を通してから、次の順で進める（どれも聞かずに行ってよい。上の「コミット・push・PR」）。
    1. 作業用のブランチで、実装をコミットして push する。最初の段階なら、`next` へのドラフトの PR を作る（上の「コミット・push・PR」）。説明には、計画の文書へのリンクと、進み具合（段階の一覧と、終えた段階の印）を書く。2 つめ以降の段階なら、PR の説明の進み具合を直す。
    2. `main` に切り替え、計画の文書にその段階の記録（決めたこと、進み具合、確かめたことなど）を書き、コミットして push する。
    3. `main` を `next` に、`next` を作業用のブランチに取り込む（上の「ブランチ」）。
    4. 作業用のブランチに戻って、次の段階へ進む。
  - 迷うこと（計画で決めていないことで、どれが良いか確信が持てない、計画を変えたくなった、など）があれば、止めて聞く。
  - 計画にない段階の作業（ほかの計画の実装など）は、合図を待つ。
- 合図を待つときは、結果、次にすること、決めてほしいことを示して返答を終える。
- 合図があるか迷ったら、始めずに聞く。
- 合図が要るのは実装の変更だけ。取り決めの変更には要らない（上の「合意してから進める」）。ただし、Skill を新しく作るときは合図が要る。
- 実装を進める手順は、振る舞いを変える変更（機能の追加・変更、不具合修正）なら Skill の `modify`、振る舞いを変えない組み替えなら Skill の `refactor` にある。

## 計画を始める

以下は開発者からの指示です。

1. `main` で、計画の状態（文書の冒頭と一覧）を「進行中」にし、コミットして push する。
   - 理由: 一覧の状態は `main` でだけ直す（[ドキュメントの書き方](documentation.md)の「計画の文書」）。ブランチで作業しているあいだも、`main` の一覧で進行中と分かるようにするため。
2. `main` を `next` に取り込む（上の「ブランチ」）。
3. `next` から、計画のブランチを作る（上の「ブランチ」）。

- 前提のある計画は、前提の計画の PR が `next` にマージされてから始める（`next` に前提の実装が入っていないため）。前提のない計画は、ほかの計画の途中でもブランチを作って始めてよい。

## 計画を完了にする

以下は開発者からの指示です。

- 計画のすべての段階を終えても、すぐには「完了」にしない。次の流れで進める（状態の書き方は[ドキュメントの書き方](documentation.md)の「計画の文書」）。
  1. 作業用のブランチで、実装のコミットを済ませる。計画の文書への書き足し（実装で変わったこと、確かめたことなど）は `main` で行い、コミットして push する（状態は「進行中」のまま変えない）。
  2. 作業用のブランチを push し、ドラフトの PR の説明を書き直してから、レビュー待ちにする（`gh pr ready`）。PR の説明には、計画の文書へのリンクと、変えたことの要約、確かめたことと確かめていないこと、残っていることを書く。
  3. 開発者に PR のレビューを頼む。レビューで直すことが出たら、作業用のブランチで直してコミットし、push する。
  4. 開発者の了承を得たら、`main` に切り替え、計画の状態（文書の冒頭と一覧）を「完了」にしてコミットし、push する。続けて、計画の PR を squash でマージする（`gh pr merge --squash --delete-branch`）。
  5. `next` から `main` への一番上の PR がまだなければ、計画の PR が `next` にマージされたあとで作る（上の「ブランチ」）。
  6. 計画の PR をマージしたら（GitHub の作業用のブランチは消える）、手元の作業用のブランチも消す。`git fetch --prune` のあと、`git branch -vv` で追いかけ先が `gone` になったブランチを探す。中身が `next` に入っていることを確かめてから（`git diff origin/next <ブランチ>` が空）、`git branch -D` で消す。PR はまとめた 1 つのコミット（squash）でマージされるので、`git branch -d` では消せない。

## Claude Code

- Edit / Write でファイルを編集するたびに、フック（`.claude/settings.json` → `.claude/hooks/format.mjs`）が Biome で整形する。Lint の指摘は直さないので、`npm run lint` で確かめる。
- シェルからの書き込み（sed、スクリプトなど）にはフックが効かない。その場合は自分で整形する。
