# 作業の進め方

この文書は、全体が開発者からの指示です。記述ごとに印は付けない（[AGENTS.md](../../AGENTS.md) の「規則の扱い」）。

この文書は、4 つに分けて書く。

- 定義: ものごとがどういうものか（Node のバージョン、ブランチ、取り込み、合図など）。手順と規則は書かない。
- 規則: してよいこと、してはいけないこと、いつするか（〜しない、〜のときだけ、など）。いくつもの手順にかかわるものをここに書く。手順は書かない。
- 作業: 計画を始める、完了にするなど、いくつもの操作を組み合わせた作業の手順。細かい操作は「操作」の節を、規則は「規則」の節を参照する。
- 操作: ブランチを切り替える、取り込むなど、作業の中から参照して使う細かい手順。規則は「規則」の節を参照する。
- その手順でしか使わない規則は、「規則」に書かず、手順の中に書いてよい。

## 定義

### Node のバージョン

- Node は、サポート期間中のすべての LTS で動くようにする。サポートが終わった Node のための書き換えはしない。
- CI（`.github/workflows/`）は、サポート期間中でいちばん古い LTS で動かす。いちばん古い LTS で動けば、それより新しい LTS でもたいてい動くため。そのサポートが終わったら、次の LTS に上げる。

### ブランチ

- `main` は、公開する版。公開するのは `main` にある内容（[公開](release.md)）。

#### ベースブランチ

- ブランチを作る元で、PR を向ける先（計画を立てずに直接入れる変更なら、入れる先）を、ベースブランチと呼ぶ。計画では `main`、`format-next`、上位の計画のブランチのどれか。作業中の計画のブランチには、ベースブランチの変更を取り込む（「定義」の「取り込み」）。
- 計画のベースブランチは、次のように決める。上から順に見て、最初に当てはまるもの。上位の計画では、2 と 3 を、自分と下位の計画のどれかに当てはまるかで見る。
  1. 下位の計画なら、上位の計画のブランチ。
  2. 保存データ、プロジェクトファイル、回路ファイルの形式を変える計画なら、`format-next`。
  3. ベースブランチが `format-next` の計画を前提にしている計画なら、形式を変えなくても `format-next`（前提の実装が `format-next` にしかないため）。
  4. それ以外は、`main`。
- 計画を立てずに直接入れる小さな変更（下の「計画のブランチ」）のベースブランチも、上の 2 と 4 で決める。形式を変える変更なら `format-next`、変えないなら `main`。

#### 計画のブランチ

- 計画のブランチは、計画ごとに 1 本、ベースブランチから作る。名前は計画のフォルダ名にそろえる（例: `project-format`）。計画の PR はベースブランチに向ける。
- 計画を立てるまでもない小さな変更（既定の値を変えるだけ、など）は、計画のブランチを作らずに、ベースブランチに直接コミットすることがある（してよいときは「規則」の「ブランチの扱い」）。入れる先は、上の「ベースブランチ」で決める。

#### 形式変更のブランチ（`format-next`）

- `format-next` は、保存データの形式を変える作業を、形式の版を公開するまで `main` に入れずに集めておくブランチ。
  - 理由: 形式を変えると、公開したあとは古い版のアプリで新しいデータを開けなくなり、変換も直せなくなる（[保存データ](persistence.md)）。形式の変更は、版としてまとめてから公開したい。形式を変えない計画は、それを待たずに公開できるようにする。
- `format-next` から `main` への PR を、形式変更の PR と呼ぶ。説明には、`format-next` に入った計画の一覧を書く。

#### 上位の計画と下位の計画

- 計画は、下位の計画を持てる。下位の計画を持つ計画を、上位の計画と呼ぶ（[ドキュメントの書き方](documentation.md)の「計画の文書」）。上位の計画も、ふつうの計画と同じく自分のブランチと PR を持ち、自分の段階（実装）を持ってもよい。ブランチは作業用のブランチとして扱い、ルールセットで守らない。
- 下位の計画のベースブランチは、上位の計画のブランチ（上の「ベースブランチ」）。下位の計画のブランチはそこから作り、下位の計画の PR もそこへ向ける。
- 上位の計画の PR の説明には、自分の段階に加えて、下位の計画の一覧と進み具合を書く。

### 取り込み

あるブランチの変更を、別のブランチに入れること。次の 2 つがある。どちらも「操作」の「取り込み方」で行う。

- ブランチどうしの取り込み: `main` を `format-next` に、ベースブランチを作業中の計画のブランチに入れる（「操作」の「ブランチどうしの取り込み」）。
- PR の取り込み: 計画の PR と、形式変更の PR。

### 合図

- 合図は、実装を始めてよいという開発者の指示。実装は、ソースコード、画面、ファイル名など、アプリの実装の変更のこと。ファイル名の変更も実装に含む。取り決め（ドキュメントに書く方針や決まり）の変更は、実装に含まない。
- 合図にするのは、始めることを直接言っている指示だけ。例: 「開始して」「実装を始めて」「作ってください」「その内容で実装して」。
- 曖昧な答えは合図にしない。例: 「その内容でいいよ」「OK です」「それでいきましょう」「いいですね」「〜しましょうか」。これらは計画への合意で、実装を始める指示ではない。
- 「進めて」のように、何を進めるのかが文脈で分かれるものも、実装を始めることがはっきりしなければ合図にしない。

## 規則

### 言語

開発者とのやりとり、コードのコメント、ドキュメントは日本語で書く。UI の文言は、日本語と英語の両方を書く（利用者が表示言語を選べるため。書き方は[文言と表示言語](i18n.md)）。

開発者の画面に出るものは、すべて日本語にする。返答の本文だけでなく、ツールを呼ぶときの説明や、確認用のスクリプトが出す文言も含む。

### 確認

- 変更したら、「操作」の「変更したあとの確認」をひととおり通す。
- 画面や操作に関わる変更をしたら、ヘッドレスブラウザで動きを確かめる。テストとビルドが通るだけで済ませない。やり方は Skill の `browser-check`、このアプリ固有のことは[ブラウザでの動作確認](browser-check.md)にある。
  - クリック、ダブルクリック、ドラッグ、文字の入力は、人の速さと間隔でする。一瞬で操作すると、人の操作では起きない失敗をしたり、人の操作でだけ起きる不具合を見逃したりするため。
  - React で描画するコードを変えたときは、フレームレートが下がっていないかも測る。重さは機能の確認では気付けず、あとから原因を探すのが難しいため。純粋な計算処理は対象にしない。重くなりやすいのは描き直しの方だから。当てはまるファイルは[ブラウザでの動作確認](browser-check.md)の「フレームレートを測る」にある。
  - 作業の区切り（一連の置き換えや機能の追加が終わったとき）と、開発者に頼まれたときは、荒い操作のテスト（連打、ドラッグ中の割り込み、画面の外へのドラッグ、おかしな入力など）もする。対象は、その作業で触った範囲。
  - 確かめられなかったものは、報告にそう書く。

### コミット・push・PR

手順は Skill の `commit` にある。

- コミットと push は、開発者に頼まれたときだけ行う。
- 次のときは、頼まれなくてもコミットと push をしてよい。
  - 計画を始めるとき（「作業」の「計画を始める」）。
  - 計画の実装で、段階を終えたとき。作業用のブランチの実装（「作業」の「段階を終えたとき」）。
  - 計画の文書（計画の一覧を含む）を `main` で直したとき。段階の記録やレビューの記録だけでなく、計画を作るときや、決めたことを書き足すときも含む。
  - 計画を完了にするとき（「作業」の「計画を完了にする」）。
  - `main` を `format-next` に、ベースブランチ（`main`、`format-next`、上位の計画のブランチ）を計画のブランチに取り込むとき（「操作」の「ブランチどうしの取り込み」）。
  - 開発者に指示されて `format-next` を `main` に取り込むとき（「作業」の「`format-next` を `main` に取り込む」。マージと、そのあとの公開済みにする変更（作業中の版があるときだけ）と取り込み）。
- コミットを頼まれても、ブランチを勝手に作らない。今のブランチにコミットする。ブランチを分けた方がよさそうなときは、コミットする前に開発者に聞く。計画のブランチは、「作業」の「計画を始める」の手順で作る。
- 計画の文書は、作成も変更も `main` で行う（[ドキュメントの書き方](documentation.md)の「計画の文書」）。
- 計画の PR は、エージェントが作る（GitHub CLI の `gh pr create`）。最初の段階の実装を push するときに、ドラフトで作り（`--draft`）、実装を終えてレビューできるようになったら、レビュー待ちにする（`gh pr ready`）。開発者のレビューで了承を得たら、エージェントが取り込む（「作業」の「計画を完了にする」）。`format-next` から `main` への形式変更の PR は、開発者に指示されたときだけ、エージェントが取り込む（「作業」の「`format-next` を `main` に取り込む」）。
- PR の取り込み方（fast-forward を優先し、できなければマージコミット）は、「規則」の「取り込み」にある。

### ブランチの扱い

- ブランチは git でマージせず、PR でマージする。例外は、ブランチどうしの取り込みと、PR を fast-forward で取り込むときの push（「定義」の「取り込み」）。
- ほかのブランチ（`main` など）で直すときは、別の作業フォルダ（`git worktree`）を使わず、いつもの作業フォルダでそのブランチに切り替えて作業する。別の作業フォルダの変更は、開発者がエディターから見られないため。今のブランチにコミットしていない変更が残っていて切り替えられないときだけ、別の作業フォルダを使ってよい。そのときは、そう報告する。
- 手元のブランチを最新にするときは、`git pull` を使わず、`git fetch` のあと `git merge --ff-only origin/<ブランチ>` で取り込む。`git pull` は、裏で動くほかの `git fetch`（エディターの自動取得など）と重なると、別のブランチの内容を取り込むことがあるため。
- 計画のブランチを作らずにベースブランチへ直接コミットするのは、開発者が指示したときだけ（例: 「直接入れていい」）。`format-next` に入れた変更は、形式変更の PR の説明の「`format-next` に直接入れた変更」に、内容とコミットを書き足す。
- ベースブランチが `main` の計画（上位の計画とその下位の計画を含む）で、途中で形式を変える必要が出てきたら、形式を変える前に止めて、開発者に聞く。`main` に形式の変更を入れられないため。選べるのは次の 2 つ。
  - 形式の変更は、この計画ではしない。別の計画（ベースブランチは `format-next`）に回す。
  - この計画のベースブランチを `format-next` に変える。上位の計画の中で起きたなら、上位の計画全体を変える（上位の計画の PR の向け先を `format-next` に変え、`format-next` を上位の計画のブランチに取り込む）。PR がまだなければ、作るときに `format-next` へ向ける。計画の文書にも、ベースブランチを変えたことを書く。
- 形式変更の PR は、最初の計画の PR が `format-next` にマージされたあとで作る（差のないブランチ同士の PR は作れないため）。マージは、形式の版を公開するときに、開発者の指示でエージェントが行う（「作業」の「`format-next` を `main` に取り込む」）。指示がなければ、形式変更の PR はマージしない。
- `format-next` は消さず、作り直さない。取り込んだあとも、次の公開に向けて使い続ける。
  - 理由: `format-next` は強制 push と削除がルールセットで禁止されているので、作り直せない。
- 上位の計画の PR は、自分の最初の段階を push するときか、最初の下位の計画の PR が上位の計画のブランチにマージされたときの、早いほうで作る（差のないブランチ同士の PR は作れないため）。

### 取り込み

- ブランチどうしの取り込みは、`main` にコミットして push したあとと、計画のブランチを作る前に行う。エージェントが聞かずに行ってよい。
  - 理由: 取り込まずにおくと、最後に `format-next` を `main` へ、計画のブランチをベースブランチへマージするときにぶつかりやすくなるため。計画のブランチで、古い決まりや計画の文書のまま作業しないようにするため。
- fast-forward できるときは fast-forward で、できないときはマージコミットで取り込む。squash と rebase は使わない（リポジトリの設定でも、PR のマージ方法はマージコミットだけを選べるようにしている）。
  - 理由: fast-forward なら、マージコミットが増えず、履歴が一続きになるため。

### 合意してから進める

判断が要るものは、案を示して開発者の合意を得てから始める。

- 示すもの: 案（複数あれば候補と、推す案とその理由）、影響が及ぶ範囲、選ばなかった案の理由。名前なら候補を複数挙げる。
- 合意が要るものと、エージェントが決めてよいものの分け方は、下の「合意が要るものと、エージェントが決めてよいもの」にある。
- 進めている途中で案を変えたくなったら、勝手に変えずにもう一度示す。
- 迷ったら、決め打ちせずに聞く。
- 計画を立てる手順は Skill の `plan` にある。

#### 合意が要るものと、エージェントが決めてよいもの

- 合意が要るのは、次のもの。
  - 保存データ、プロジェクトファイル、回路ファイルの形式（項目名や値の名前を含む）。
  - 画面の作りと操作の割り当て、画面に出る文言。
  - フォルダやファイルの構成（分け方、置き場所、ファイル名）。
  - ライブラリの追加、Skill の追加・変更・削除。
- プログラムの実装の中のことは、エージェントが決めてよい。
  - 型、関数、変数、定数の名前。
  - 関数の分け方、引数と戻り値の形、データの渡し方。
  - ファイルの中のコードの並べ方。
  - 決めた内容は、計画の文書に書く（[ドキュメントの書き方](documentation.md)の「計画の文書」）。計画がない作業では、報告に書く。
- どちらか迷ったら聞く。
- 実装の途中で、計画で決めていないことに出会い、案が複数あってどれが良いか確信が持てないときは、開発者に聞く。確信が持てるときは決めて進め、決めた内容と理由を計画の文書（計画がない作業では報告）に書く。
- 取り決め（ドキュメントに書く方針や決まり）の変更は、案を示さずにその場で直してよい。ただし開発者が決めた規則（[AGENTS.md](../../AGENTS.md) の「規則の扱い」）は、開発者が意向を示したとき（「〜しましょうか」でもよい）だけ直す。
- 開発者の指示ややり方に気になる点（危うさ、もっと良い方法、ほかの決まりとの食い違い）があれば、従う前にその旨を伝える。開発者の提案が最善とは限らず、ほかの方法に開発者が気付けないことがあるため。伝えたうえで、どうするかは開発者が決める。

### 実装を始める合図

- 実装は、開発者の合図（「定義」の「合図」）があってから始める。計画や調査を頼まれたときは、実装を始めない。名前への合意だけでは改名しない。
- 計画の実装は、開始の合図があれば、段階の区切りで止めずに最後の段階まで進める。最後に PR でレビューを受けるため。段階を終えたときは、「作業」の「段階を終えたとき」の順で進める。
  - 迷うこと（計画で決めていないことで、どれが良いか確信が持てない、計画を変えたくなった、など）があれば、止めて聞く。
  - 計画にない段階の作業（ほかの計画の実装など）は、合図を待つ。
- 合図を待つときは、結果、次にすること、決めてほしいことを示して返答を終える。
- 合図があるか迷ったら、始めずに聞く。
- 合図が要るのは実装の変更だけ。取り決めの変更には要らない（上の「合意してから進める」）。ただし、Skill を新しく作るときは合図が要る。
- 実装を進める手順は、振る舞いを変える変更（機能の追加・変更、不具合修正）なら Skill の `modify`、振る舞いを変えない組み替えなら Skill の `refactor` にある。

### Claude Code

- Edit / Write でファイルを編集するたびに、フック（`.claude/settings.json` → `.claude/hooks/format.mjs`）が Biome で整形する。Lint の指摘は直さないので、`npm run lint` で確かめる。
- シェルからの書き込み（sed、スクリプトなど）にはフックが効かない。その場合は自分で整形する。

## 作業

### 計画を始める

1. 始めてよいかを確かめる。
   - 前提のある計画は、前提の計画の PR がベースブランチにマージされてから始める（ベースブランチに前提の実装が入っていないため）。前提のない計画は、ほかの計画の途中でもブランチを作って始めてよい。
   - 下位の計画は、上位の計画を始めたあとに始める（下位の計画のベースブランチは、上位の計画のブランチのため）。
2. 計画の状態（文書の冒頭と一覧）を「進行中」にする（「操作」の「`main` で計画の文書を直す」）。
   - 理由: 一覧の状態は `main` でだけ直す（[ドキュメントの書き方](documentation.md)の「計画の文書」）。ブランチで作業しているあいだも、`main` の一覧で進行中と分かるようにするため。
3. ベースブランチに切り替える（「操作」の「ブランチを切り替える」）。
4. 計画のブランチを作る（「定義」の「ブランチ」の「計画のブランチ」）。

### 段階を終えたとき

計画の実装で、段階を終えたときに行う。どれも聞かずに行ってよい（「規則」の「コミット・push・PR」）。

1. 確かめる（「操作」の「変更したあとの確認」）。
2. 作業用のブランチで、実装をコミットして push する。
3. PR を直す。最初の段階なら、ベースブランチ（`main` か `format-next`）へのドラフトの PR を作る（「規則」の「コミット・push・PR」）。説明には、計画の文書へのリンクと、進み具合（段階の一覧と、終えた段階の印）を書く。2 つめ以降の段階なら、PR の説明の進み具合を直す。
4. 計画の文書に、その段階の記録（決めたこと、進み具合、確かめたことなど）を書く（「操作」の「`main` で計画の文書を直す」）。
5. 最後の段階なら、下の「計画を完了にする」へ進む。そうでなければ、作業用のブランチに切り替えて（「操作」の「ブランチを切り替える」）、次の段階へ進む。

### 計画を完了にする

計画のすべての段階を終えても、すぐには「完了」にしない。次の順で進める（状態の書き方は[ドキュメントの書き方](documentation.md)の「計画の文書」）。上位の計画は、自分の段階をすべて終え、下位の計画がすべて完了してから始める。

1. 作業用のブランチで、実装のコミットを済ませ、push する。
2. 計画の文書に、実装で変わったこと、確かめたことなどを書き足す（「操作」の「`main` で計画の文書を直す」）。状態は「進行中」のまま変えない。
3. ドラフトの PR の説明を書き直してから、レビュー待ちにする（`gh pr ready`）。PR の説明には、計画の文書へのリンクと、変えたことの要約、確かめたことと確かめていないこと、残っていることを書く。
4. 開発者に PR のレビューを頼む。レビューで直すことが出たら、作業用のブランチに切り替え（「操作」の「ブランチを切り替える」）、直してコミットし、push する。開発者の了承を得るまで繰り返す。
5. 計画の PR を取り込む（「操作」の「取り込み方」）。
6. GitHub の作業用のブランチを消す。マージコミットで取り込むなら、手順 5 で `gh pr merge <番号> --merge --delete-branch` とする。fast-forward なら、push のあとに `git push origin --delete <ブランチ>`。
7. 計画の状態（文書の冒頭と一覧）を「完了」にする（「操作」の「`main` で計画の文書を直す」）。ベースブランチが `main` の計画なら、この中のブランチどうしの取り込みで、取り込んだ実装が `format-next` に入る。
   - 理由: 手順 5 より先に `main` に「完了」をコミットすると、ベースブランチが `main` の計画では、`main` が PR のブランチより先に進み、fast-forward で取り込めなくなるため。
8. ベースブランチが `format-next` の計画で、形式変更の PR（`format-next` → `main`）がまだなければ作る（「規則」の「ブランチの扱い」）。
9. 手元の作業用のブランチを消す（「操作」の「手元の作業用のブランチを消す」）。

### 計画を中止にする

計画を中止にするのは、開発者に指示されたとき。次の順で行う。

1. 計画の状態（文書の冒頭と一覧）を「中止」にし、理由と日付を書く（[ドキュメントの書き方](documentation.md)の「計画の文書」。「操作」の「`main` で計画の文書を直す」）。
2. 計画の PR があれば、マージせずに閉じる（`gh pr close`）。閉じるときのコメントに、中止の理由を書く。
3. 計画のブランチは消さずに残す。実装を記録として残し、再開したくなったときに使えるようにするため。

### `format-next` を `main` に取り込む

`format-next` を `main` に取り込むのは、形式の版を公開するとき。開発者が「`format-next` をマージして」のように指示したら、エージェントが次の順に行う（いつ取り込んでよいか、ブランチの扱いは「規則」の「ブランチの扱い」）。取り込んだあとの公開（Deploy の実行）は開発者が行う（[公開](release.md)）。

1. 形式変更の PR（`format-next` → `main`）がドラフトのままなら、レビュー待ちにする（`gh pr ready <番号>`）。
2. 形式変更の PR を取り込む（「操作」の「取り込み方」）。ブランチは消さない（`--delete-branch` を付けない。「規則」の「ブランチの扱い」）。
   - squash や rebase で取り込むと、`format-next` の履歴が `main` の祖先にならず、次の形式変更の PR に今回のコミットがまた出てぶつかる（squash と rebase を使わないことは「規則」の「取り込み」）。
3. 作業中（未公開）だった形式の版があれば、公開済みにする。なければ（今回の取り込みで形式の版が変わっていなければ）、この手順は飛ばす。
   1. `main` に切り替える（「操作」の「ブランチを切り替える」）。
   2. [保存データ](persistence.md)の「版の状態」を「公開済み」にして公開した日を書き、形式の文書（`docs/format/`）の冒頭にも公開した日を書く。
   3. コミットして push する。
4. `main` を `format-next` に取り込む（「操作」の「ブランチどうしの取り込み」）。手順 2 を fast-forward で取り込み、手順 3 を飛ばしたなら、2 つは同じなので要らない。マージコミットで取り込んだなら fast-forward できる。`format-next` に入れる次の計画のブランチは、ここから作る。
5. 次の形式変更の PR は、次の計画の PR が `format-next` にマージされたあとで作る（「規則」の「ブランチの扱い」）。
6. したこと（マージしたコミット、公開済みにした版（なければ、なかったこと）、取り込んだ結果）を報告し、Deploy を実行して公開するよう開発者に伝える。

## 操作

### 変更したあとの確認

1. `npm run format` で整形する（Biome）。
2. `npm run lint`、`npx tsc -b`、`npm test`、`npx vite build` を通す。
3. 画面や操作に関わる変更なら、ブラウザで動きを確かめる（「規則」の「確認」）。

- `npm run build` は、型チェックとビルドをまとめて行う。`npm run check` は整形と Lint をまとめて確かめ、`npm run format:check` は整形されているかだけを確かめる。
- `npm run lint` と `npm run check` は、Biome のあとに `.agents/skills/` と `.claude/skills/` が同じかも確かめる（[Skill の追加・編集](skills.md)の「一致の確認」）。
- Markdown は Biome の対象外。ドキュメントは手で整える。
- 改行コードは LF にそろえている（`.gitattributes` と `biome.json`）。`core.autocrlf=true` の環境でも、`.gitattributes` があるので CRLF にならない。
- Windows では、`npm test` がまれに全テストファイルの読み込みに失敗し、「no tests」で終わることがある。原因は分かっていない（作業フォルダのドライブ名が `c:` と `C:` で切り替わった直後に起きやすい）。個々のテストが失敗したのではなく、全ファイルがまとめて読めなかったときは、まず再実行する。たいていは通る。

### ブランチを切り替える

1. `git status -s` で、コミットしていない変更がないかを確かめる。残っていて切り替えられないときは、「規則」の「ブランチの扱い」に従う（別の作業フォルダを使い、そう報告する）。
2. `git switch <ブランチ>` で切り替える。
3. `git fetch` してから、`git merge --ff-only origin/<ブランチ>` で手元を最新にする（`git pull` を使わないことは「規則」の「ブランチの扱い」）。

### 手元のブランチを進める

切り替えずに push して進めたブランチは、手元のブランチも進める。進めないと、手元のブランチが古いまま残り、開発者がエディターで見たときに紛らわしいため。手元にそのブランチがなければ要らない。

1. 今そのブランチにいなければ、`git fetch origin <ブランチ>:<ブランチ>` で進める（例: `git fetch origin format-next:format-next`）。今そのブランチにいれば、この方法では進められないので、`git merge --ff-only origin/<ブランチ>` で進める。

### `main` で計画の文書を直す

計画の文書（計画の一覧を含む）は、この手順で直す。聞かずにコミットと push をしてよい（「規則」の「コミット・push・PR」）。

1. `main` に切り替える（上の「ブランチを切り替える」）。
2. 計画の文書を直す。
3. コミットして push する。
4. ブランチどうしの取り込みを行う（下の「ブランチどうしの取り込み」）。`main` にほかの変更がなければ、計画の文書だけの変更なので、取り込まずに終わる。

### 取り込み方

ブランチどうしの取り込みと、PR の取り込みの両方で使う（「定義」の「取り込み」）。

1. `git fetch` してから、fast-forward できるか（取り込む先に、取り込む元にないコミットがないか）を `git merge-base --is-ancestor origin/<取り込む先> origin/<取り込む元>` で確かめる（できるなら終了コードが 0）。確かめずに push しない。断られて手戻りになるため。
2. fast-forward できるなら、`git push origin origin/<取り込む元>:<取り込む先>` で、取り込む先を進める（例: `git push origin origin/main:format-next`）。PR なら、GitHub が、PR のコミットが取り込む先に入ったことに気付き、PR の状態を自動で「Merged」にする（マージのボタンで取り込んだときと同じ扱いになり、手で閉じなくてよい）。続けて、手元の取り込む先のブランチを進める（上の「手元のブランチを進める」）。
3. できないなら、マージコミットで取り込む。
   - ブランチどうしなら、取り込む先に切り替えてから（上の「ブランチを切り替える」）、`git merge origin/<取り込む元>` でマージし、push する。
   - PR なら、`gh pr merge <番号> --merge` で取り込み、手元の取り込む先のブランチを進める（上の「手元のブランチを進める」）。
   - マージでぶつかったら、自分で解かずに止めて、開発者に見せる。

### ブランチどうしの取り込み

行う時機と、聞かずに行ってよいことは、「規則」の「取り込み」にある。

1. 取り込む組を、次の順に並べる。組ごとに、手順 2 と 3 を行う。
   1. `main` → `format-next`（`main` で直した計画の文書や決まり、`main` に入れた計画の実装など）。
   2. ベースブランチ（`main`、`format-next`、下位の計画なら上位の計画のブランチ）→ 作業中の計画のブランチ（PR を作ったものを含む）。上位の計画のブランチがあるときは、ベースブランチ → 上位の計画のブランチ → 下位の計画のブランチの順。
2. `git fetch` してから、`git diff --name-only origin/<取り込む先>...origin/<取り込む元> -- . ':(exclude)agent/plans'` で、取り込む元の変更が計画の文書（`agent/plans/`。計画の一覧を含む）だけかを確かめる。何も出なければ計画の文書だけなので、その組は取り込まない。その変更は、次にほかの変更を取り込むときに一緒に入る。
   - 理由: 計画の文書は `main` でだけ直し、作業用のブランチでは `main` のものを読む（[ドキュメントの書き方](documentation.md)の「計画の文書」）ので、取り込まなくても困らない。段階の記録などのたびに取り込むと、マージのコミットが増えるため。
3. 上の「取り込み方」で取り込む。

### 手元の作業用のブランチを消す

計画の PR を取り込んで、GitHub の作業用のブランチを消したあとに行う。

1. `git fetch --prune` で、GitHub で消えたブランチの追いかけ先を片付ける。
2. `git branch -vv` で、追いかけ先が `gone` になったブランチを探す。
3. 中身がベースブランチに入っていることを確かめる（`git merge-base --is-ancestor <ブランチ> origin/<ベースブランチ>` の終了コードが 0）。
4. `git branch -D <ブランチ>` で消す（`git branch -d` は、今いるブランチに入っているかで確かめるので、ベースブランチにいないと断られる）。
