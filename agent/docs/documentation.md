# ドキュメントの書き方

エージェント向けドキュメント（`AGENTS.md` と `agent/docs/`）の書き方と、見直す範囲、Skill にするものの決め方。

## 何を書くか

気付いたことは、その都度書く。

書くもの:

- 規則と、その理由や背景、設計の意図、既知の制約。
- 開発者と決めた取り決め。
- 実装で注意したこと、選んだ理由、落とし穴とその避け方。
- 触ると壊れるもの（合わせて直す必要があるもの、守らないと動かなくなる前提）。
- コードを読めば分かることのうち、重要なもの。例: (開発者からの指示)
  - 複数のファイルにまたがる処理の流れ（例: 編集がどう元に戻す対象になるか）。
  - 読み始める場所（入口のファイルや関数）。
  - 変えると別の場所も直す必要がある値や名前（保存データのキー、ピン番号の決め方など）。

書かないもの:

- 1 つのファイルの中で完結する処理の中身。分かりにくいなら、ドキュメントではなくコードのコメントに書く（[コードの書き方](coding-style.md)の「コメント」）。
- 今後の判断に役立たない過去の経緯（以前の名前、採らなかった案、直した不具合）。

文章は短く、1 文に 1 つのことを書く。結論を先に書き、理由は後に添える。言葉は[用語](glossary.md)にそろえる。

## 表記

ドキュメントと Skill の表記。文章の整え方の手順は Skill の `doc-polish` にある。

- 文体は常体（〜する、〜である）。
- ひらがなで書く: とき、こと、できる、すべて、など、ため、ください。
- 漢字で書く: 分かる。
- 和文と半角英数字の間に半角スペースを入れる（例: 「1 つ」「Skill の」）。
- 括弧は全角の（）。
- コロンは半角の「: 」（例: 「- 言葉: 意味」）。
- ファイル名、関数名、コマンド、キーはインラインコードにする。
- 「事柄」「出来事」「等倍」のような一語は、上の決まりで言い換えない。
- 作業の手順（[作業の進め方](workflow.md)の取り込みや計画の始め方など）は、できるだけ番号付きの逐次的な手順で書く。条件で分かれるところは、その手順の中に「〜なら」と書く。(開発者からの指示)
- いくつもの手順で使う手順は、1 か所に手順として書き、使う側の手順からはその節を参照する（例: [作業の進め方](workflow.md)の「操作」）。同じ手順を所々に書き写さない。(開発者からの指示)
- 作業の決まりの制約（〜しない、〜のときだけ、など）は、定義とは分けて制約として 1 か所に書き、手順の中からはそこを参照する（例: [作業の進め方](workflow.md)の「制約」）。手順の中に書き写さない。その手順でしか使わない制約は、手順の中に書いてよい。(開発者からの指示)
- 決まりや記述に、いつ決めたか・変えたかの日付を書かない（例: 「開発者が決めた、2026-10-17」とはせず「開発者が決めた」と書く）。日付が要るのは、決まりで書くと決めているもの（形式の版を公開した日、計画を中止にした日など）だけ。

## どこに書くか

- コードと同じく、責務ごとにファイルを分ける（[コードの置き場所の決め方](code-placement.md)）。ある実装を変えるときに、関係するファイルだけを読めば済むようにするため。
- 1 つのファイルに別の責務が混ざってきたら分け、元のファイルから 1 行で案内する。
- 節に書き足すときは、その節に別の話が混ざってきていないかを見る。混ざってきたら、小見出しで分ける。1 行ずつ書き足していくと、どの行も正しいまま別の話が混ざり、気付きにくいため。
- ファイルを作ったら、`AGENTS.md` の一覧に載せる。どの作業でも要るものは「作業前に必ず読むドキュメント」、特定の実装を触るときだけ要るものは「触るときに読むドキュメント」に入れる。
- 開発者が決めた規則は、その規則が関わる節の中に書く。書き方と使い分けは [AGENTS.md](../../AGENTS.md) の「規則の扱い」にある。
- 保存データの形式の文書（`docs/format/`）には、データの形と意味（どの項目がどの値を取り、何を表すか）、読み込むときの検証（どんなデータを正しいとし、どんなデータを断るか。断らずに受け入れるものも含む）、アプリが書くデータの性質（並び順、省略のしかたなど。読み書きする人の助けになるため）だけを書く。検証も形式の一部なので、検証を変えるときは形式の版の決まり（[保存データ](persistence.md)の「形式を変えるとき」）に従う。配線やピンのつながり方、値の伝わり方、画面での見せ方、アプリの動き（ファイル名の付け方、持ち込み方など）は、エージェント向けのドキュメントに書く（開発者が決めた）。
- 特定のエージェントにだけ当てはまる内容（Claude Code のフックなど）は、エージェント名の見出し（例: `## Claude Code`）を立てて分ける。
- `agent/docs/` の中では、ファイル名を重ねない（Skill からファイル名で参照するため。[Skill の追加・編集](skills.md)）。
- 1 つのファイルが長くなり、責務が 2 つ以上あるなら、分けられないか考える。読むファイルが長いと、その作業に要らない部分まで読むことになるため。分けるかどうかと分け方は、開発者に示して決める。(開発者からの指示)

## いつ見直すか

- 作業のたびに、触った部分のドキュメントが今のコードと合っているかを確かめる。合わない記述は直し、役目を終えた記述は消す。
- 大きく作り変えたあとや、開発者に頼まれたときは、全体を見直す。手順は Skill の `doc-review` にある。
- 画面や操作を変えたら、利用者向けの[操作マニュアル](../../docs/manual/README.md)も合わせて直す。

## 見直しの範囲

ドキュメントを今のコードと取り決めに合わせるとき（Skill の `doc-review` を含む）に、直す対象。リンクで辿れても、ここにないものは直さない。

| 置き場所                   | 中身                                 | 見直すか                                                             |
| -------------------------- | ------------------------------------ | -------------------------------------------------------------------- |
| `AGENTS.md`、`agent/docs/` | エージェント向けドキュメント         | 見直す。全ファイルを `AGENTS.md` の一覧に載せ、ファイル名を重ねない  |
| `docs/format/` の各形式の最新の版 | 保存データとファイルの形式の仕様 | 見直す                                                        |
| `docs/manual/`             | 利用者向けの操作マニュアル           | 見直す                                                               |
| `agent/plans/`             | 計画の文書                           | 見直さない。計画中・進行中の計画は、下の「計画の文書」の決まりで直す |
| `docs/format/` の古い版と `integrated/` | 古い版の形式の仕様、一体の形式の仕様 | 見直さない（[保存データ](persistence.md)の「形式を変えるとき」） |

- 見直さないものも、置き場所が変わってリンクやパスが切れたときは、その置き換えだけはする。
- Skill は `.agents/skills/` と `.claude/skills/` にある（[Skill の追加・編集](skills.md)）。`agent/` とは別の場所なのは、エージェントの仕組みが置き場所を決めているため。

## 計画の文書

- 計画を文書にするときは、`agent/plans/<計画の名前>/plan.md` に置き、[計画の一覧](../plans/README.md)に番号を振って載せる。番号の決まりは一覧にある。フォルダ名には番号を付けない。
- 文書の題名の末尾に、計画の番号を書く（例: `# 問題パネル（計画 23）`）。一覧を見なくても番号が分かるようにするため。完了・中止した計画には書き足さない。
- 文書の冒頭に状態を書く。状態は「計画中」「進行中」「完了」「中止」のどれか。中止は、行わないと決めた計画（ほかの計画にまとめたものも含む）。中止にした理由と日付を冒頭に書き、文書は記録として残す（開発者が決めた）。一覧の状態もそろえる。
- 一覧には、先に終える計画の番号を「前提」の列に書く（開発者が決めた）。計画の文書の中にも、前提の計画と順番を書く。
- 計画は、下位の計画に分けてよい。下位の計画を持つ計画を、上位の計画と呼ぶ。上位の計画の文書には、目的と全体で決めたことと、下位の計画の一覧と順番を書く（自分の段階があれば、それも書く）。下位の計画の文書の冒頭には、上位の計画を書く。一覧の「前提」は先に終える計画だけに使い、下位の計画であることは「内容」に書く（「上位」の列は作らない。開発者が決めた）。上位の計画も、ふつうの計画と同じくブランチと PR を持つ。違いは[作業の進め方](workflow.md)の「ブランチ」の「上位の計画と下位の計画」にある。上位の計画は、自分の段階と下位の計画がすべて終わってから完了にする。
- 計画の一覧と計画の文書は、`main` でだけ直す。実装の途中の記録（決めたこと、段階の進み具合、確かめたこと）も、作業用のブランチではなく `main` で直す（開発者が決めた）。始めるときと完了にするときの手順は、[作業の進め方](workflow.md)の「計画を始める」「計画を完了にする」にある。
  - 理由: 同じ計画の文書を `main` と作業用のブランチの両方で直すと、マージのときにぶつかる（一覧は新しい計画を先頭に足すので、特にぶつかりやすい）。また、実装の途中で決めたことがブランチにしかないと、`main` でほかの計画を読み直すときに見えない。
  - 作業用のブランチにある計画の文書は直さない。計画の文書だけの変更は、作業用のブランチと `format-next` に取り込まない（[作業の進め方](workflow.md)の「ブランチどうしの取り込み」）ので、ブランチにある計画の文書は古いことがある。作業用のブランチで計画の文書と一覧を読むときは、`git fetch` してから `main` のもの（`git show origin/main:agent/plans/<フォルダ>/plan.md`）を読む。
  - 例外: 作業用のブランチでファイルを移して、計画の文書からのリンクが切れたときは、そのリンクの張り替えだけは、移したのと同じブランチで行う（`main` にはまだ移した先がないため）。
- 完了した計画は、移さずにその場に残す。ほかの文書からのリンクが切れないようにするため。
- 「完了」にする時機は、[作業の進め方](workflow.md)の「計画を完了にする」にある。
- 完了した計画は記録として扱う。今の仕様と構成は、エージェント向けのドキュメントと形式の文書（`docs/format/`）に書く。完了にするときに、実装で変わったことを計画にも書き足し、それ以降は直さない。
- 計画中・進行中の計画は、関わるドキュメントから案内する（例: 保存形式を変える計画を、[保存データ](persistence.md)の「形式を変えるとき」から案内する）。完了か中止にしたら、案内を消す。

### 開発者からの指示

- 計画の文書は、その都度更新する。決まったこと、変わったこと、段階の進み具合を、開発者とのやりとりで決まったときや段階を終えたときに書き足す。
- プログラムの実装について、エージェントが開発者に聞かずに決めた内容（型や関数の名前、データの渡し方など）も、計画の文書に書く。決めた理由と、採らなかった案も添える。
- 完了した計画も消さずに残す。完了したかどうかを区別できるようにする。
- 計画の中で決めたことや変えたことがあったら、その都度、関係する計画（前提にしている計画、前提にされている計画、同じものを扱う計画）を読み直し、古くなった記述や食い違いがないかを確かめて直す。前に決めたことを前提にした推す案、ほかの計画への参照（「計画 N の決めてほしいことの M」など）、叩き台、段階、確かめることも見る。直したものは報告に書く。

## Skill にするもの

手順は Skill に書く。ドキュメントは「どうなっているか」、Skill は「やるときに何を順に踏むか」を書く。同じ手順をドキュメントに重ねて書かない。

- Skill があった方が良いと気付いたら、開発者に提案する。目印は、同じ手順を何度も説明している、毎回同じ順で作業している、忘れると手戻りになる確認がある、など。
- 提案には、使う場面、手順の概要、名前の候補を複数含める。手順がまだどこにも書かれていなければ、その場で書き出して見せる。
- Skill の置き場所と書き方は [Skill の追加・編集](skills.md) にある。

### 開発者からの指示

- Skill は勝手に作らず、提案してから作る。
- Skill には、このアプリ固有の内容を書かない（ほかのプロジェクトでも使えるようにするため）。アプリ固有の内容はドキュメントに書き、Skill からはファイル名と見出しで参照する。
