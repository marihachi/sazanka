# 保存データ

プロジェクトの保存データとプロジェクトファイル、利用者ごとの設定の保存。形式の仕様は `docs/format/` にある。今のアプリが読み書きするのは、[プロジェクトの形式 version 1](../../docs/format/project/v1.md)と[回路の形式 version 1](../../docs/format/circuit/v1.md)（まだ公開していない）。一体の形式（最後は [version 4](../../docs/format/integrated/v4.md)）のデータも、変換して読める。

## 前提

アプリは公開済み。利用者の手元には、それぞれの版で保存したデータと、書き出したプロジェクトファイル（一体の形式では「共有用 JSON」と呼んでいた）が残っている。プロジェクトファイルは他人の手元にも渡るので、保存データ以上に古い版が回ってくる。

## 版の状態

形式の版ごとの、公開したかどうか。公開したかで、変換を直してよいかが変わる（下の「開発者からの指示」）。

| 形式                                   | 版  | 状態             | 公開した日 |
| -------------------------------------- | --- | ---------------- | ---------- |
| 一体の形式（プロジェクトと回路）     | 4   | 公開済み（最後） | 2026-10-13 |
| プロジェクトの形式                     | 1   | 作業中（未公開） | -          |
| 回路の形式                       | 1   | 作業中（未公開） | -          |

- 一体の形式は v4 で終わり、プロジェクトの形式と回路の形式に分けた。一体の形式のデータは、v4 にしてから、プロジェクトの形式 v1 と回路の形式 v1 に変えて読む。

- 版を上げる作業を始めたら、その版を「作業中（未公開）」として足す。公開したら「公開済み」にし、日付を書く。形式の文書（`docs/format/project/v<N>.md`、`docs/format/circuit/v<N>.md`）の冒頭にも、公開したかと日付を書く（開発者が決めた、2026-10-17）。
- 公開の手順で確かめることは[公開](release.md)にある。
- プロジェクトの形式と回路の形式は、それぞれ版を持ち、別々に上げる。保存データとプロジェクトファイルは、どちらもプロジェクトの形式のデータそのもので、版も同じ。

## 形式を変えるとき

- 版を上げるのは、今の版で古いデータを読むのに変換が要る変更（項目の意味や形が変わるなど）のとき。部品の種類や、省略できる項目を足すだけなら上げない。
  - 上げなくてよいのは、公開しているのが最新版だけで、新しいデータが古い版で開かれることがほぼないため。古い版を開けるようにする（版ごとの URL を残す、オフラインで動かすなど）なら、この判断を見直す。そのときは、追加だけでも版を上げることと、古い版が新しいデータを上書きしないようにすることが要る。今は、古い版のアプリで新しいデータを開くと、「壊れている」か「新しい版のデータ」として断り、空のプロジェクトを自動保存で上書きしてしまう。
- 版を上げるときにすること:
  1. プロジェクトの形式なら `PROJECT_FORMAT_VERSION`、回路の形式なら `CIRCUIT_FORMAT_VERSION`（どちらも `file/upgrade/index.ts`）を上げる。
  2. 1 版分の変換（`file/upgrade/project/v<N>.ts` か `file/upgrade/circuit/v<N>.ts`。ファイル名は「version N へ変える変換」）を作り、読み込みの入口（`upgradeStoredProject`）から順に通す。
- 読み込みの入口は `file/upgrade/index.ts` の `upgradeStoredProject`。保存データ（`readStored`）とプロジェクトファイル（`parseProject`）の両方が、検証（`checkProject`）の前にこれを呼ぶ。変換の決まりは、下の「開発者からの指示」にある。
  - 新しい形式は `format` で見分ける。`"sazanka-project"` なら、プロジェクトと中の回路の版を見て、今より新しければ断る（今は v1 しかないので変換はない）。`"sazanka-circuit"` と `"sazanka-circuits"` は、種類が違うとして断る（`CIRCUIT_FILE`）。
  - `format` がなく、いちばん外に `version` と `project` があれば一体の形式。`upgradeIntegratedProject` で version 4 まで順に変えてから、`upgradeToProjectV1`（`file/upgrade/project/v1.ts`）でプロジェクトの形式 v1 に変える。回路 1 つずつは `upgradeToCircuitV1`（`file/upgrade/circuit/v1.ts`）が変える。
  - 版の番号だけでは見分けない。一体の形式の version 1 と、プロジェクトの形式の version 1 があるため。
- 今の版は、プロジェクトの形式も回路の形式も 1。一体の形式は version 4 で終わり。
- 一体の形式の変換は `file/upgrade/integrated/` にある。古い形式を読むためだけに残しているので、直さない。
  - version 1 → 2 は `upgradeV1.ts` の `upgradeV1`。変え方は [version 2](../../docs/format/integrated/v2.md) の「version 1 からの変更」にある。
    - `upgradeV1` は、version 1 のアプリが描いていた配線の形（`routeV1`）を点の並びにする。古い形の決め方は、ここにだけ残している。
    - 部品の確かめ方、ピンの数、ピンの先の位置は、version 2 の時点のもの（形式の文書の表）を `upgradeV1.ts` の中に持つ。今のアプリの配置を直しても、ここは直さない。
  - version 2 → 3 は `upgradeV2.ts` の `upgradeV2`。変え方は [version 3](../../docs/format/integrated/v3.md) の「version 2 からの変更」にある。
    - 種類の名前の対応表（`KIND_NAMES_V3`）を中に持つ。今のアプリの種類の名前を変えても、ここは直さない。
    - モジュールの回路には `split`（version 2 までのモジュールの形）を書き込む。ピンの位置が変わらないので、配線は書き換えない。
  - version 3 → 4 は `upgradeV3.ts` の `upgradeV3`。変え方は [version 4](../../docs/format/integrated/v4.md) の「version 3 からの変更」にある。
    - 1 マスの大きさ（20px）を中に持つ。今のアプリの `GRID` を変えても、ここは直さない。
    - モジュールの回路の ID を付け直すので、新しい ID を作る関数（`newId`）を引数で受け取る。読み込みの入口と、それを呼ぶ `readStored` と `parseProject` も受け取って渡す。テストでは決まった ID を渡す。
    - モジュールの ID が変わるので、そのモジュールの表示（`sazanka.views`）は引けなくなり、既定の表示に戻る。付け替えない（開発者が決めた）。
- 一体の形式 v4 → プロジェクトの形式 v1 の変え方は、[プロジェクトの形式 v1](../../docs/format/project/v1.md)と[回路の形式 v1](../../docs/format/circuit/v1.md)の「一体の形式 version 4 からの変更」にある。
  - 変換の中に、一体の形式の既定値（シート 300×200、CLOCK の周期 100）と、ポート番号の付け方（ないものと重なるものに付ける。split とメイン回路は位置の順に振り直す）を持つ。今のアプリの `DEFAULT_SHEET`、`DEFAULT_CLOCK_PERIOD`、`assignPortNumbers` には頼らない。
  - split のモジュールとメイン回路のポート番号を位置の順に振り直すので、split のピンの順がポート番号の順になっても、外側の配線は今までと同じピンにつながる。
  - 名前の空のモジュールに付ける「モジュール<n>」は、表示言語によらず日本語のまま（データの変換なので）。
- 部品の種類や項目を足したら、検証（`project.ts` の `checkProject`。部品は `part.ts` の `isPart`）も合わせる。置ける種類の判定（`part.ts` の `isPlaceablePartKind`）は `PART_SPECS` と `SPECIAL_KINDS` を見るので、`PART_SPECS` に足した種類はそのまま検証を通る。
- 回路のパッケージ、シートの大きさ、フォルダのパス、作者名（`project.ts` の `CircuitDef` の `package`、`sheet`、`path`、`author`）と、ポート番号（`Part.portNumber`）は、型では省略できるが、読み込むデータでは省略を許さない（`checkProject`）。アプリで作る回路とポートにも必ず持たせる。型で省略できるのは、テストで回路や部品を手短に作れるようにするため。持たないものは、split、`DEFAULT_SHEET`、空文字として扱い、保存するときもそう書く（`storage.ts` の `toStoredProject`）。
- 保存データで省略できない項目は、アプリで部品や回路を作る所と変える所（置く、貼り付け、モジュールの追加、新規作成、回路設定での変更など）で、なくならないようにする。作る所や変える所、省略できない項目を足したら、保存したデータが検証を通るかを確かめる。(開発者からの指示)
  - 部品をパレットから置くときは `editing/edit.ts` の `newPart` で作る（CLOCK の周期を持たせる）。INPUT / OUTPUT のポート番号は、置いたあと・貼り付けたあとに `assignPortNumbers` で付ける。
  - 回路やプロジェクトを変えるときは、変えない項目を残す（`{ ...p, circuits: … }`、`{ ...def, … }`）。回路の一覧だけで作り直すと、`folders` などが消える。
  - どの種類の部品も、置いた形のまま保存して検証を通ることを、テストで確かめている（`storage.test.ts`）。

### 開発者からの指示

- 保存データ、プロジェクトファイル、回路ファイルの形式を、古いデータがそのままでは読めなくなる形に変えるときは、必ず版を上げ、古い版を読み込む処理を足す。
- プロジェクトの形式と回路の形式は、それぞれ版を持つ（2026-10-17 に開発者が了承した）。保存データとプロジェクトファイルは、どちらもプロジェクトの形式のデータそのもの（版は同じ）。下の「1 版ずつの変換を順に通す」「一度作った変換は直さない」「版ごとに文書を 1 つ」は、プロジェクトとモジュールのそれぞれに当てはめる。
- 一体の形式（v1〜v4）の変換は、一体の形式の変換としてコードを分けて置き、古い形式を読むためだけに残す。直さない。これから足す変換は、プロジェクトと回路の版を上げる変換として置く。変換のファイル名は、何に変えるか（`v<N>.ts` は「version N へ変える変換」）で付ける（置き方は[ソースの構成](structure.md)の `file/upgrade/`）。
- 古い版の読み込みは、1 版ずつの変換を順に適用する形にする（1 → 2 → 3 …）。
  - 版を上げるときは、1 版分の変換（`upgradeV<N>`: version N → N+1）を 1 つ足し、順に適用する並びに加える。古い版から今の版へ一気に変える変換は書かない。
  - 各変換は、変換前と変換後の版の形だけを知る。今のアプリの型・検証・配置・種類の名前には頼らない。要る決め方（ピンの位置など）は、その版の時点のものを変換の中に持つ。今のコードが変わっても、古い変換の結果が変わらないようにするため。
  - 一度作った変換は、あとから直さない。変換の中の決め方は、その版の形式の文書と同じに保つ。
    - ただし、変換先の版を公開する前なら、その変換を直してよい（2026-10-17 に足した）。公開する前は、その版のデータが利用者の手元にないため。公開したら、直さない。
  - 変換ごとのテストと、いちばん古い版から今の版まで順に適用したテストを書く。
- 形式の仕様は、形式と版ごとに 1 つの文書で書く。形式ごとにフォルダを分ける: 一体の形式は `docs/format/integrated/`、プロジェクトの形式は `docs/format/project/`、回路の形式は `docs/format/circuit/`（2026-10-19）。
  - 形式を変えたら、今の版の文書も直す。版を上げずに足したもの（部品の種類など）は、その文書の「version 1 の中で変えたもの」に書き足す。
  - 版を上げたら、同じフォルダに新しい版の文書（例: `project/v2.md`）を作る。古い版の文書は、そのフォルダに残す（ほかへ移さない）。古い版の文書は、古い版を読む処理を書くときに参照するので書き換えない。
- [プロジェクト管理機能](../plans/project-management/plan.md)の計画がある（進行中）。モジュールのファイルへの書き出しと持ち込み、未解決のモジュールなど、保存形式に関わる変更を含む。モジュールは `id` だけで識別すると決めた。保存形式やモジュールの参照を変えるときは、この計画とぶつからないかを見て、進め方は開発者に聞く。

## 保存の形とアプリの中の形

保存データとプロジェクトファイルの中のプロジェクト（`file/storage.ts` の `StoredProject`。プロジェクトの形式のデータ）は、アプリの中の形（`Project`）と次のところが違う。読み書きのときに `storage.ts` の `toStoredProject` / `fromStoredProject` で変える。プロジェクトファイル（`projectFile.ts`）も同じ関数を使う。

- 回路は、保存の形ではプロジェクトの要素（フォルダのパス `path` と回路のデータ `circuit` の組）の並び（`circuits`）に並べ、アプリの中では回路にパスを持たせた並び（`circuits`）にする。並びは同じ順のまま変える。アプリの中もプロジェクトの形式と同じ形にするかは、未解決のモジュール（[計画 20](../plans/unresolved-module/plan.md)）を作るときに見直す（描画、ネット、シミュレーションが回路の並びを前提にしているため）。
- モジュールの部品は、保存の形では指す回路の名前の写し（`circuitName`）を持ち、アプリの中では持たない。保存するたびに今の名前を写し、読み込むときは使わない（回路の名前を引く）。未解決のモジュールで、何が足りないかを見せるためのもの（計画 20）。
- 部品と配線は、保存の形では 1 つの一覧（`elements`）に `kind` で見分けて並べ、アプリの中では `parts` と `wires` に分ける。読み込むときは種類で分け（`kind` が `"wire"` なら配線）、それぞれの中の順は保つ。保存するときは、種類の決まった順（`storage.ts` の `ELEMENT_ORDER`。開発者が決めた順）に並べ、同じ種類の中はアプリの中の順を保つ。データを読みやすくするため。種類を足したら `ELEMENT_ORDER` にも足す（漏れると型エラーになる）。
  - 一覧を分けないのは、部品か配線かという分け方が実際の種類の分類（計算するもの、端子、表示、つながり）と合わず、種類を足すたびにどちらに入れるかで迷うため。分類は種類の性質として、部品の種類の仕様の側に持つ。
  - アプリの中を分けたままにしているのは、描画やネットの計算が部品と配線を別々に扱っているため。アプリの中もまとめるかは、別の計画で考える。
- 部品と配線は、保存の形では ID を持たず、アプリの中では持つ。読み込むたびに、部品と配線に `newId` で新しい ID を付ける。
  - 部品と配線の ID は、保存データの中でどこからも参照されない（モジュールの参照は回路の ID、配線のつながりは位置、モジュールのピンは `pinNumber` かポート番号の順で決まる）。アプリの中で、選択・編集・シミュレーション・元に戻すのために見分けるのに使うだけなので、保存しない。
  - 読み込むたびに変わっても困らない。選択、元に戻すの履歴、シミュレーションの状態（フリップフロップや CLOCK の ON/OFF）は、もともと保存も引き継ぎもしない。表示の位置は回路の ID で引く。
  - セッションをまたいで同じ部品を指したくなったら（モジュールを置き換えるときに同じポートを見分けるなど）、部品の ID を保存データに戻し、版を上げる。
- 配線は、保存の形では種類（`kind`。今は `"wire"` だけ）を持ち、アプリの中では持たない（`StoredWire` と `Wire`）。アプリの中の型に種類を持たせていないのは、今は 1 種類しかないため。種類を足すときに、`Wire` にも持たせる。
- 部品の位置と配線の点は、保存の形ではマス単位の整数、アプリの中では px（`geometry/layout.ts` の `GRID` 倍）。描画、当たり判定、ネットの計算が px で書かれているので、アプリの中は px のままにしている。
  - 検証（`checkProject`）は、保存の形（マス単位）で行う。位置が整数でなければ断る。
- メイン回路は、保存の形では名前を持たず、アプリの中では空文字を持つ。画面に出す名前は表示言語の文言から引く（`i18n/messages.ts` の `getCircuitName`）。読み込むときは、名前があっても捨てる。
- 置き場所は、あとのリファクタリングで見直す（開発者が決めた）。`project.ts` には置けない（`GRID` は `geometry/` にあり、`circuit/` からは使えない。[ソースの構成](structure.md)の「依存の向き」）。

## ID

- 保存する ID は回路の ID だけ。プロジェクトをまたいでも重ならないものにし、一度付けたら付け直さない（形式の文書の「ID の付け方」）。モジュールを別のプロジェクトへ持ち込んでも、付け直さずに済ませるため。
- 部品と配線の ID は保存しない（上の「保存の形とアプリの中の形」）。
- 新しい ID は `circuit/circuit.ts` の `newId` で作る。UUID version 4 の形。`crypto.randomUUID()` は安全な接続（https か localhost）でしか使えないので、`crypto.getRandomValues()` で組み立てる。
- メイン回路の ID は、どのプロジェクトでも `"main"`（`MAIN_ID`）。
- 検証は、回路の ID が重ならないことを確かめる（`project.ts` の `findDuplicateId`）。

## 保存データ

- プロジェクトは、変わるたびに localStorage の `sazanka.project` に自動で保存する（`App.tsx` の `useEffect` から `storage.ts` の `saveProject` を呼ぶ）。形はプロジェクトの形式のデータそのもの。一体の形式で保存したもの（`{ version, project }`）も読める。
- 読み込むときは、プロジェクトファイルと同じ検証（`checkProject`）を通す。壊れていたら空のプロジェクトで開き、ダイアログで利用者に知らせる。壊れたデータをそのまま使うと、表示や計算の途中で例外が起きて画面が出なくなるため。
- localStorage を使えない環境では、保存データなしとして扱い、保存の失敗は無視する。
- 読み込みの処理は、localStorage に触る `loadProject` と、文字列を受け取って結果を返す `readStored` に分けている。`readStored` はテストできる。
- 壊れたデータは退避しない。空のプロジェクトを自動保存で上書きする。(開発者からの指示)

## プロジェクトファイル

- ヘッダーの「書き出し」「読み込み」で使う（`file/projectFile.ts`、操作は `file/useProjectFile.ts`）。形はプロジェクトの形式のデータそのもの（保存データと同じ。外側の包みはない）。一体の形式で書き出したもの（`{ app: 'sazanka', version, project }`）も読める。
- 受け渡しはファイルだけ（文字列のコピーと貼り付けはしない）。書き出しと読み込みは、アプリのダイアログを出さずに直接行う。
  - 書き出しは、`project-YYYY-MM-DD.sazanka.json`（端末の日付）を既定の名前にして保存する。
  - 手元のファイルとのやりとりは `file/localFile.ts` にまとめている（保存の `saveJsonFile`、ファイルを選ぶ `pickFile`、読む `readTextFile`）。
  - 保存は、`showSaveFilePicker` が使えるブラウザ（Chrome、Edge など Chromium のもの。安全な接続のときだけ）では、保存場所とファイル名を選ぶ画面を出す。使えないブラウザ（Firefox、Safari）では `<a download>` で保存する（保存場所を聞くかはブラウザの設定による）。どちらでも書き出せるので、特定の環境を前提にしない決まりとはぶつからない。
  - `showSaveFilePicker` があっても、保存の画面を開けない環境や、選んだファイルに書き込めない環境がある（VS Code の中のブラウザでは、画面は開けるが `createWritable` が `NotAllowedError` になる）。取り消し以外の例外のときは、ダウンロードで保存する（`saveJsonFile`）。
    - ただし、Electron で作ったアプリの中のブラウザ（ユーザーエージェントに `Electron/` を含む。VS Code の中のブラウザなど）では、初めから保存の画面を使わずにダウンロードで保存する（`isElectron`）。書き込めないと分かってからダウンロードに切り替えると、ダウンロードでも保存先を聞かれ、保存の画面が 2 回出るため（開発者が決めた）。取り消し（`AbortError`）のときは、何もしない。
  - ファイルは UTF-8 として読む。先頭の BOM は `File.text()` が外す。
- 読み込むと、元に戻す・やり直しの履歴を消す（履歴はプロジェクトごとのもの。開発者が決めた）。読み込みは元に戻せない。
- 回路ファイル（`format` が `"sazanka-circuits"`）や回路のデータを選んだときは、種類が違うと知らせる（`CIRCUIT_FILE`）。
- 書き出しでも読み込みでも、回路の ID は付け直さない（上の「ID」）。
- 他人から受け取る文字列なので、読み込むときは形を検証してから使う（`checkProject`）。
- 作者名は、回路ごとに持つ（`CircuitDef.author`。入れていなければ空文字）。プロジェクトは作者名を持たない。作者名を入れる欄は、[計画 18](../plans/main-as-module/plan.md)で回路設定に足す（今はない）。

## 保存しないもの

- INPUT と CLOCK の ON/OFF（部品の `on`）は、保存データにもプロジェクトファイルにも含めない（`project.ts` の `withoutSwitchStates`）。シミュレーション中のほかの状態も保存しないので、それとそろえる。(開発者からの指示)
  - アプリの中では部品に `on` を持ち、シミュレーションで使う。外すのは保存・書き出し・読み込みのときだけ。
  - 初めのころのデータには `on` が入っている。読み込むときに外すので、検証には足さない。形式の仕様にも書かない。
- フリップフロップの状態など、シミュレーション中の状態も保存しない。開き直すと、回路は初めの状態から動く。
- 元に戻すの履歴も保存しない。

## 消さないもの

- モジュールのピンが減ると、減ったピンの位置にあった配線の端は、どこにもつながらなくなる。配線は削除せずに残す。ピンが元に戻れば、またつながる。
- version 1 のデータを読み込むときは、存在しないピンを指す配線を捨てる（位置が決まらないため）。(開発者からの指示)

## 利用者ごとの設定

回路とは別のキーに置く。読めなければ既定値で動かし、エラーにはしない。版は付けていない。

| キー                       | 中身                                                      | 読めないとき                         |
| -------------------------- | --------------------------------------------------------- | ------------------------------------ |
| `sazanka.preferences`      | 環境設定（1 秒に進める tick 数、方眼、角の丸め、アクセントカラー、表示言語） | 項目ごとに既定値（表示言語は `auto`） |
| `sazanka.paletteCollapsed` | パレットで折り畳んでいるグループの ID                     | 空（すべて開く）。知らない ID は無視 |
| `sazanka.views`            | 回路 ID ごとの表示（位置と倍率）                          | 回路ごとに捨て、既定の表示で開く     |

- 環境設定の 1 秒に進める tick 数（`ticksPerSecond`）は、前は 1 tick を進める間隔（`tickMs`、ms）で保存していた。`ticksPerSecond` がなく `tickMs` があれば、`1000 / tickMs` を丸めて読む（`storage.ts` の `readTicksPerSecond`）。保存し直すと `tickMs` は消える。
- パレットの折り畳みは、グループの ID（`parts/view.ts` の `PaletteGroupId` と、モジュールのグループの `'module'`）で保存している。見出しの文字（文言の表の `palette.groups`）は変えてよいが、ID は変えない。変えると、利用者が折り畳んでいた状態が失われる。
- 表示は回路 ID ごとに保存している。回路を削除したら、その ID の分を消す。新規作成と読み込みでは、ID が同じでも中身は別の回路なので、すべて消す。
