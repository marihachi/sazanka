# リファクタリング

責務の考え方、どう分けるか、どこに寄せるかの判断基準は、`code-placement.md`（`AGENTS.md` の一覧から辿る） にある。今の構成は `structure.md` にある。始める前にそれらを読む。ここには進め方を書く。

振る舞いを変えない組み替えだけを扱う。機能の追加・変更や不具合修正は Skill の `modify` で進める。計画は Skill の `plan` で立てる。そのときにリファクタリングで調べることは、下の「計画で調べること」にある。

## 手順

1. **計画を確かめる**。合意済みの計画があるかを確かめる。なければ Skill の `plan` で計画を立て（調べることは「計画で調べること」）、示して止まる。
2. **合図と範囲を確かめる**。開発者の指示が、始めることをはっきり言っているかと、始めてよい範囲を確かめる（決まりは `workflow.md` の「実装を始める合図」）。曖昧なら始めずに聞く。
3. **振る舞いを変えずに移す**。移動・改名と、機能の変更を混ぜない。1 ファイルずつ移し、そのたびにテストを通す。途中で計画を変えたくなったら、勝手に変えずに止めて示す。
4. **付随して直すものを拾う**。
   - ファイル先頭の責務のコメント（近い責務が別ファイルにあるなら、その置き場所も）。
   - テストのファイル名と置き場所（決まりは `coding-style.md` にある）。
   - `structure.md` の記述。
   - フォルダ内・フォルダ間の依存の向き。依存の向きについての決まりがあるかと、その守り方は `code-placement.md` にある。
5. **確認する**。`workflow.md` にある確認（整形、Lint、型、テスト、ビルド）を通す。画面に関わる部分を動かしたなら、ブラウザでも確かめる（Skill の `browser-check`）。
6. **報告する**。移したものと、見たが移さなかったものを分けて伝える。移さなかった理由も書く。

## 計画で調べること

Skill の `plan` でリファクタリングの計画を立てるときに、手順の中で行う。

1. **範囲と目的をはっきりさせる**。どのフォルダ・どの関心を対象にするか、今どこが読みにくいのか。目指すのは読みやすさで、コードの短さや共通化の多さは目的にしない。
2. **今の構成を把握する**。`structure.md` と、ファイル先頭の責務のコメント（書くと決めている場所は `code-placement.md` にある）を読む。直近に手が入った箇所も、`git diff` と `git log` で見ておく。
3. **責務の混ざりを洗い出す**。ファイルごとに「直すことになる理由」を挙げ、1 つにまとまらないものを見つける。概念の近さではなく、直す理由と「何を知る必要があるか」で見る。
4. **新しい構成案を立てる**。ファイルごとに、置くもの（型・関数・定数）と import するものを挙げる。

## 注意

- 移動の前後で結果が変わらないことを確かめたいときは、移動前のコードと突き合わせる使い捨てのテストを書いてよい。確認できたら消す。
- 開発者が手で直した箇所を、整理のついでに元に戻してしまわないよう気を付ける。
- ファイル名と中身がずれたら、どちらかを直す。ファイル名を変えるときは、止めて候補を示し、選んでもらう。
