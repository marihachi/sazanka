# コミットと push

コミットと push を、取り違えなく行う手順。いつコミット・push してよいか、どのブランチに置くかの決まりは、`workflow.md`（`AGENTS.md` の一覧から辿る）の「コミット」と、そこから辿る節（計画を始める、計画を完了にする、など）にある。始める前にそれらを読む。

## 手順

1. **してよいかを確かめる**。
   - `workflow.md` の「コミット」に、聞かずにコミット・push してよい例外がある。今の作業がそのどれかに当てはまるかを見る。
   - 当てはまらなければ、コミットと push のそれぞれに、開発者のはっきりした了承があるかを確かめる（「コミットして」「push して」、コミット・push してよいかの問いへの「ok」など）。
   - 了承がなければ、何をコミット・push するかを示して聞き、止まる。
2. **ブランチを確かめる**。今のブランチが、決まりの上でそのコミットを置く所かを見る（`workflow.md` に、ブランチごとに直してよいもの・いけないものがある）。違えば、コミットする前に切り替えるか、別の作業フォルダ（`git worktree`）で作業する。
3. **変更を見る**。`git status` と差分で、次のものが混ざっていないかを見る。混ざっていたら、入れるものだけを選んで加える。
   - 今回の作業と関係のない変更（ほかの作業の途中のもの、開発者が手で直しているもの）。
   - 生成物、作業用の一時ファイル。
   - 決まりの上で、そのブランチで直してはいけない所。
4. **確認を通す**。コードを変えたなら、`workflow.md` の「変更したあとの確認」を通す。通らなければコミットしない。
5. **コミットする**。メッセージは、直近のログ（`git log`）の書き方に合わせる（言語、1 行目の書き方、本文の書き方、署名の行）。1 行目には、何をしたかを短く書く。
6. **push する**。手順 1 で push まで了承か例外があるときだけ行う。push 先のリモートとブランチを確かめてから行う。
7. **push のあとの手順を行う**。`workflow.md` に、push のあとに続けて行うこと（ほかのブランチへの取り込み、PR の作成など）があれば行う。
8. **報告する**。コミットの ID、push したか（と push 先）、まだコミットしていない変更が残っているかを書く。例外として聞かずに行ったときは、そう書く（どの例外に当てはめたか）。

## 注意

- 了承の取り違え: コミット・push してよいかを聞いたあとの返事が、別の点への答えだけなら、了承とみなさない。もう一度聞く。
- 例外に当てはまるか迷ったら、例外とみなさずに聞く。
- 「コミットして」だけなら、push はしない。push してよいかは、別に確かめる。
- 別の作業フォルダ（`git worktree`）で作業したら、push のあとに片付ける（`git worktree remove`）。片付けないと、そのブランチを元の作業フォルダで切り替えられなくなる。
- 長いコミットメッセージは、シェルのクォートで壊れやすい。ファイルや標準入力（`git commit -F -` とヒアドキュメントなど）で渡す。
- push が断られたら（先に進んだリモートがあるなど）、強制の push をしない。取り込んでから push し直すか、開発者に聞く。
