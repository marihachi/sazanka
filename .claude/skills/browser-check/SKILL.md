# ヘッドレスブラウザでの動作確認

画面や操作に関わる変更をしたら、テストとビルドが通るだけで済ませず、実際にブラウザで動かして確かめる。どうしても確かめられなかった場合は、報告にそう明記する。

このアプリ固有の事柄（起動のコマンド、開く URL、状態の用意の仕方、要素の探し方、気を付けること）は、`browser-check.md`（`AGENTS.md` の一覧から辿る） にある。何を確かめるかは、触った実装のドキュメントの「触ったら確かめること」にある。始める前にそれらを読む。

確認のたびに使い捨てのスクリプトを書いて走らせる。スクリプトはリポジトリに置かない（作業用のフォルダに置く）。ブラウザを操作する仕組みも、プロジェクトの依存には加えず、作業用のフォルダに入れる。

## 手順

1. 開発サーバーを、`browser-check.md` にあるコマンドとポートで起動する（バックグラウンドで）。ポートが埋まっていたら、別のポートに変えて自分で立て直す。すでに動いているサーバーにつなぐと、自分の変更を見ている保証がない（開発者が別の作業で立てていることがある）。
2. スクリプトでヘッドレスブラウザを起動し、`browser-check.md` にある URL を開く。使えるブラウザは開発環境によって異なるので、その環境にあるものを確かめてから使う。
   - 例: Node が使える環境なら、作業用のフォルダに `puppeteer-core` を入れ、その環境にインストール済みのブラウザ（実行ファイルのパスを指定する）を動かす。スクリーンショットだけなら、ブラウザのヘッドレスモードをコマンドで呼ぶだけでも足りる。
3. 確かめたいことに応じて、操作・読み取り・スクリーンショットを行う。操作は下の「人の操作をまねる」に従う。雛形は [script-template.mjs](script-template.mjs)（人の操作をまねる関数も入っている）。
   - 確認のスクリプトが複数あるときは、並べて（同時に）流す。下の「並べて流す」に従う。
4. フレームレートが悪化していないかを測る。下の「フレームレートを測る」に従い、変える前（直前のコミット）と比べる。ほかの確認とは同時に流さず、終わってから単独で測る。
5. 終わったらサーバーとブラウザを止める。

## フレームレートを測る

画面や操作に関わる変更をしたら、見た目や動きが正しくても、重くなっていないかを毎回確かめる。重さは機能の確認では気付けず、あとから原因を探すのが難しいため。

- 変える前と後で、同じ条件で測って比べる。変える前は、直前のコミットを別の作業フォルダ（`git worktree` など）に取り出して動かすと、手元の変更に触れずに済む。
- 遅い端末を想定して CPU を遅くする（Puppeteer なら CDP の `Emulation.setCPUThrottlingRate`）。速い端末では差が出にくい。
- 何もしていないときと、画面がよく描き変わる操作（ドラッグ、時間で動くものなど）の間の、fps（`requestAnimationFrame` の回数）と重い処理（`longtask`）の合計を見る。
- 開発用のサーバーの版は、フレームワークの開発用の処理が重なって重く出る。公開する版の重さは、ビルドしたもので測る。
- 下がっていたら、どこで時間を使っているかを CPU プロファイルで調べ、報告に数字を添える。
- このアプリで測る条件（CPU をどれだけ遅くするか、どんな回路で何を操作するか）と目安は `browser-check.md` の「フレームレートを測る」にある。

## 並べて流す

人の操作をまねる確認は待ち時間が長いので、1 本ずつ流すと時間がかかる。確認のスクリプトどうしが独立していれば、同時に流して、いちばん長い 1 本の時間で終わらせる。

- スクリプトごとに別のブラウザを起動する。新しいプロファイルで開くので、保存データ（localStorage など）はスクリプトどうしで混ざらない。開発サーバーは 1 つを共有してよい。
- シェルならバックグラウンドで起動して待つ（例: `node a.mjs > a.txt & node b.mjs > b.txt & wait`）。出力はスクリプトごとのファイルに分け、終わってからまとめて見る。
- 同時に流すと CPU を取り合うので、時間で判定する確認（一定時間で表示が切り替わるか、など）は余裕を持った待ち時間にする。それでも不安定なら、そのスクリプトだけ単独で流し直す。
- フレームレートの計測は、ほかと同時だと数字が乱れるので、並べずに最後に単独で流す。

## 人の操作をまねる

確認の操作は、人がする速さと間隔でする。一瞬のうちに操作すると、人の操作では起きない食い違いで失敗したり、人の操作でだけ起きる不具合を見逃したりするため。雛形の関数（`click`、`doubleClick`、`drag`、`type`、`hover`）を使えば、次の値になる。

- **クリック**: 対象の上へポインターを動かしてから、押して 60ms ほど置いて離す。要素の `click()` を `evaluate` の中で呼んだり、合成したイベントを送ったりしない。
- **ダブルクリック**: 1 回目と 2 回目のクリックの間を 100ms あける。
- **ドラッグ**: 押したあと 100ms ほど置き、1 歩 5〜10px ほど、1 歩ごとに 16ms（1 フレーム）ほど待ちながら動かす。離す前にも 100ms ほど置く。
- **文字の入力**: 1 文字ごとに 50ms ほどあける（`page.keyboard.type` の `delay`）。
- **操作と操作の間**: 200〜300ms あける。続けて押すボタンも同じ。
- **ポインターを載せる**: 対象へ動かしたあと、ツールチップなら出るまでの時間より長く待つ。
- 例外: ブラウザのドラッグ＆ドロップ（`dataTransfer` を使うもの）は、ヘッドレスブラウザでは実際のポインター操作で起こせない。`DataTransfer` を持たせた `DragEvent` を `dragstart` → `dragover` → `drop` の順に送るしかないので、そのときだけ合成イベントを使い、報告にそう書く。

## 荒い操作を試す

作業の区切りに、触った範囲へ行う。普段の確認が期待どおりに動くかを見るのに対し、こちらは人の無茶な操作で壊れないかを見る。ここでは人の速さをまねなくてよい。連打などは、むしろ速く行う。

### 試す操作

触った範囲に当てはまるものを選ぶ。アプリでの具体的な例は `browser-check.md` にある。

- **連打**: 追加・確定・元に戻すなどのボタン、Enter。
- **割り込み**: ダイアログが開く途中の Esc。ドラッグ中の Esc・右クリック・ホイール・ショートカット。
- **はみ出し**: ドラッグできるものを画面の外まで動かして離す。
- **入力**: 空欄、とても大きな数、全角の数字、改行の入った貼り付け、とても長い文字列（表示が崩れないかも見る）。
- **画面**: ドラッグ中やダイアログを開いている間の、画面の幅の変更。とても狭い幅（320px）。
- **速さ**: 3 回続けてのクリック、クリックとダブルクリックの混ざった操作。

### 合否の決め方

次のどれかが起きたら不合格。

- ページの例外やコンソールのエラーが出る。
- 画面が操作できない状態のまま戻らない（ダイアログが閉じない、ドラッグが終わらないなど）。
- 保存したデータが壊れる。再読み込みして、同じ状態で開けるかで確かめる。
- 元に戻すで、操作の前に戻せない。
- 同じものが二重にできる（確定ボタンの連打で 2 つできるなど）。

期待と違っても壊れていないものは、不合格にせず「気になる動き」として報告する。

## 確かめ方の例

- **見た目**: スクリーンショットを撮って、画像として確認する。
- **操作**: ボタンや部品をクリックする、文字を入力する、キーを押す。
- **状態**: 表示されている文言、ボタンが押せるかどうか、色、一覧の中身を読む。
- **回数や間隔の測定**: 値が変わる間隔（ms）、一定時間の DOM の書き換え回数、フレームの要求回数。描画を間引く仕組みが効いているかは、これで測る。
- **エラー**: ページの例外、コンソールのエラー、失敗した通信（404 など）を集めて最後に出す。想定していない読み込み失敗に気付ける。

## ハマりやすい点

- **保存データを直接書いて状態を用意するときは、アプリの自動保存に上書きされないようにする**。最初の読み込みが終わってから書き、書いたら再読み込みする。アプリが絶えず保存し続けている（時間で動くものがある）ときは、書いてから再読み込みするまでの間にも上書きされるので、次の読み込みの最初に書き換える（Puppeteer なら `page.evaluateOnNewDocument` で書き、読み込んだら `removeScriptToEvaluateOnNewDocument` で外す）。
- **新しいプロファイルでは保存データ（localStorage など）が空になる**。スクリプトを分けて走らせると、前の確認の状態は残らない。続けて確かめたいときは、同じスクリプトの中で続けるか、状態を書いてから始める。
- **見えていない要素には、ポインターの操作が当たらない**。スクロールする領域の下の方にあるものは、見える位置まで出してから操作する。
- **確認の結果が NG のときは、まず確認の手順を疑う**。期待値の前提（設定の値、どのタブを開いているか）、要素の探し方、操作の間隔を見直してから、不具合として扱う。
- **ハッシュの付くクラス名は、部分一致で探す**。役割の属性（`role`、`aria-*`、`data-*`）で探せるなら、その方が確実。
