# 保存データの version 3（計画）

状態: **計画中**（段階はまだどれも始めていない）。段階ごとに、開発者の合図を受けてから実装する（[作業の進め方](../../agent/workflow.md)の「実装を始める合図」）。決まったことや変わったことがあれば、その都度この文書を直す（[ドキュメントの書き方](../../agent/documentation.md)の「計画の文書」）。

version 3 の形式は、公開するまで変えてよい。公開する時期は開発者が決める。

## 目的

- モジュールの外側のピン番号を、入力か出力かを問わず 1 から通しで振る。ピンを出す辺も番号から決める。実際の IC と同じ考え方にする。
- 128 ピン程度のモジュール（マイコンなど）も作れるようにする。左右だけでは足りないので、上下の辺にもピンを出す。
- モジュールごとにパッケージ（フットプリント: 出し方とピン数）を持たせる。どのポートにも割り当てていない番号は NC にする。
- 保存データと共有用 JSON の版を 3 に上げる。旧データの配線は書き換えず、つながりをそのまま保つ。
- あわせて、部品の種類の項目名を `kind` から `partKind` に変え、種類の名前をキャメルケースにそろえる。モジュールを指す項目名も `custom` から `module` に、回路の部品の一覧の項目名を `components` から `parts` に変える。

## 背景

- 配線は部品を指さず、端の位置がピンの先と重なるかでつながる（[保存データ](../../agent/persistence.md)、`docs/format/v2.md`）。そのため、モジュールのピンの位置が変わると、旧データの配線が黙って外れる。
- 配線の端を延ばして直す変換は採らない。入力ピンは同じ縦の線に並ぶので、延ばした線の端が隣のピンの配線に重なり、別々だった配線がつながってしまう。
- そこで、配置をモジュールごとにデータに持たせる。旧データのモジュールには旧形式の出し方（`split`）を書き込み、形を変えない。

## 保存データ（version 3）

```json
{
  "version": 3,
  "project": {
    "circuits": [
      {
        "id": "main",
        "name": "メイン",
        "parts": [{ "id": "p1", "partKind": "module", "module": "k3x9", "x": 2900, "y": 1900 }],
        "wires": []
      },
      {
        "id": "k3x9",
        "name": "半加算器",
        "footprint": { "styleKind": "dip", "pins": 8 },
        "parts": [
          { "id": "a", "partKind": "input", "x": 2800, "y": 1900, "label": "A", "pinNumber": 1 },
          { "id": "s", "partKind": "output", "x": 3000, "y": 1900, "label": "S", "pinNumber": 8 }
        ],
        "wires": []
      }
    ]
  }
}
```

### 部品の種類

- 項目名を `kind` から `partKind` に変える。`kind` だけでは何の種類か漠然としているため。`footprint` の `styleKind` と同じく、何の種類かを前に付ける。
- 種類の名前は、次の表のとおりに変える。

| version 2   | version 3    |
| ----------- | ------------ |
| `INPUT`     | `input`      |
| `OUTPUT`    | `output`     |
| `CLOCK`     | `clock`      |
| `HIGH`      | `high`       |
| `AND`       | `and`        |
| `OR`        | `or`         |
| `NOT`       | `not`        |
| `NAND`      | `nand`       |
| `NOR`       | `nor`        |
| `XOR`       | `xor`        |
| `XNOR`      | `xnor`       |
| `RS`        | `rsLatch`    |
| `RSEN`      | `rsEnLatch`  |
| `DLATCH`    | `dLatch`     |
| `DFF`       | `dFlipFlop`  |
| `TFF`       | `tFlipFlop`  |
| `JKFF`      | `jkFlipFlop` |
| `CUSTOM`    | `module`     |
| `BUF`（内部用。保存しない） | `buf` |

- アプリの中の項目名（`Component.kind` → `partKind`）と種類の名前も同じにする。保存データとアプリの中で名前を分けると、読み替える場所が増えるため。
- モジュールを指す項目名を `custom` から `module` に変える（アプリの中の `Component.custom` も）。`custom` は、モジュールの内部名が `CUSTOM` だったころの名残のため。`moduleId` にしないのは、モジュールを ID ではなくパスで指す案（[モジュールのファイル保存](../../design/module-files.md)）になっても名前がずれないようにするため。
- 回路の部品の一覧の項目名を `components` から `parts` に変える（アプリの中の `Circuit.components` も）。`parts[].partKind` と言葉をそろえるため。React のコンポーネント（画面の部品）と紛らわしくなくなる利点もある。
- 型と定数の名前も見直す。名前は段階 2 で決める。今の考え:
  - 部品の型を `Component` から `Part` にする。
  - 仕様の一覧 `PARTS`（`parts/specs.ts`）を `PART_SPECS` にし、`specs.ts` の中の `Part` 型も仕様の名前にする。`circuit.parts` と紛らわしくならないようにし、`PART_VIEWS` とも並べるため。
  - 今の `PartKind`（仕様の一覧にある種類だけ）は、項目名の `partKind`（部品の種類すべて）と別のものを指すので、名前を変える（例: `PartKind` → `SpecPartKind`、`ComponentKind` → `PartKind`）。
  - `parts/` フォルダは、部品の種類ごとの定義の置き場所として、名前を変えない。
- 種類のフォルダの名前も合わせる（例: `parts/dff/` → `parts/dFlipFlop/`）。
- 画面に出る名前（「AND」「D-FF」など）は見せ方（`view.ts` の `label`）が持つので、変わらない。

### `footprint`

モジュールの回路だけが持つ。メイン回路は持たない。

出し方の項目を `kind` にしないのは、漠然としていて、部品の種類と紛らわしいため。

| `styleKind` | 項目         | 意味                                                         |
| ------- | ------------ | ------------------------------------------------------------ |
| `dip`   | `pins`（数） | 2 辺に出す。`pins` は 4 以上の偶数                           |
| `qfp`   | `pins`（数） | 4 辺に出す。`pins` は 8 以上の 4 の倍数                      |
| `split` | なし         | 入力は左、出力は右（version 2 までの形）。新しいモジュールでも選べる |

- `pins` の上限は 256。
- NC のピンに名前（電源の表記など）を書けるようにするときは、`footprint` に省略できる項目として足す。版は上げない。

### `pinNumber`

- モジュールの中の `input` / `output` が持つ、外側のピン番号。1 から `pins` までの整数。
- `footprint` が `dip` / `qfp` のときだけ使う。`split` では使わない。
- 割り当てなし、範囲外、重なりがあっても、読み込みは断らない。画面で知らせる（下の「ピン番号の割り当て」）。

### 読み込むときの検証（`checkProject` に足すもの）

- モジュールの回路が `footprint` を持ち、`styleKind` が `dip` / `qfp` / `split` のどれかであること。
- `pins` が、`styleKind` に合った数で、上限以下であること。
- `pinNumber` があるなら、整数であること。

`footprint` を省略できる項目にしないのは、既定値で補うと、あとで既定値を変えたときに、今回と同じく旧データの配線が外れるため。

## 出し方

長さはマス単位。

| `styleKind` | 並べ方                                                                                   | ピンの間隔 | 大きさ                              | モジュール名 |
| ------- | ---------------------------------------------------------------------------------------- | ---------- | ----------------------------------- | ------------ |
| `dip`   | 左を上から下へ 1〜N/2、右を下から上へ N/2+1〜N                                           | 2          | 幅 3、高さ (N/2 - 1) × 2 + 2        | 本体の上     |
| `qfp`   | 左（上から下）→ 下（左から右）→ 右（下から上）→ 上（右から左）。各辺 N/4 本            | 2          | 正方形。1 辺 (N/4 - 1) × 2 + 2      | 本体の中     |
| `split` | 入力は左、出力は右。それぞれ中の位置の順（上から、同じ高さなら左から）                   | 1          | 幅 4、高さはピンの多い方の数 + 1    | 本体の上     |

- N は `pins`。番号は左上の 1 番から反時計回りに振る（実際の IC と同じ）。
- `split` は今のモジュールの形そのもの。旧データは、これでピンの位置が変わらない。
- 128 ピンの QFP は 1 辺 64 マスで、シート（300 × 200 マス）に収まる。
- 外側のピンの横に、ピン番号を出す。
- 配置は、部品の種類ごとの配置（`parts/module/layout.ts`）が `footprint` から作る。配置を引く側に渡す道は、段階 2 で決める（今は `portsOf` の結果に入れる案。避けるなら、`layoutOf` に部品とプロジェクトを渡す形）。

### 入力か出力かの見分け

`dip` / `qfp` では、辺から入力か出力かが分からないので、見た目で見分ける印が要る。印は改めて検討する。それまでは仮の印で進める。

- 仮の印: ピンの先の印の色。入力は青、出力は赤。
- ON / OFF の表示（線の色）とぶつからないよう、色を付けるのはピンの先の印だけにする。
- 検討するときの注意: 赤は、出力のぶつかり（`conflict`）の配線と、危険な操作のボタンにも使っている。

## ピン番号の割り当て

`dip` / `qfp` のモジュールの中での決まり。

- 自動の割り当て: 次のときに、空いているいちばん小さい番号を入れる。空きがなければ割り当てない。
  - モジュールの中に `input` / `output` を置いたとき。
  - 貼り付けたとき。番号がほかと重なっていたら付け直す。
- 割り当ては置く操作の一部にする。元に戻すも 1 回で済む。
- メイン回路に貼り付けた `input` / `output` からは、`pinNumber` を外す。
- 中で動かしても、番号は変わらない。
- 割り当てなし・範囲外・重なりのポートは、外側にピンとして出さない。重なりは、どちらも出さない（どちらを出すか決められないため）。中の部品に印を付け、ステータスバーで知らせる。
- ピン数を超えるポートを足しても、ピン数は自動で広げない。形が変わるのは、利用者がピン数を変えたときだけにする。
- NC: どのポートにも割り当てていない番号。線を引き、`NC` と書く。つながりは作らない（ネットにピンの先として加えない）。
- 電源ピン（VCC / GND）は今回は作らない。電源にしたい番号は NC のままにしておけば、実際の IC の配置を写せる。

## シミュレーションとの関係

- シミュレーションと展開は、今の「入力の何番目、出力の何番目」でつなぐ仕組み（`PinRef.pin`、`simulation/flatten.ts`）のまま使う。
- 外に見せるピン番号とは別のもの。`dip` / `qfp` では、入力と出力の並びを、それぞれピン番号の順にする（NC と、外に出さないポートは除く）。
- 配線は位置でつながるので、この並びは保存しない。

## 読み込みの変換

古い版の変換を順に適用する形（1 → 2 → 3）と、変換が今のアプリのコードに頼らないようにすることは、別の計画（[古い版の変換を順に適用する形にする](../upgrade-chain/plan.md)）で行う。この計画の段階 2 より前に終える。

### `upgradeV2`（2 → 3、`file/upgradeV2.ts`）

- 回路の `components` を `parts` に、部品の項目名 `kind` を `partKind` に、`custom` を `module` に移し、種類の名前を上の表のとおりに読み替える。
- モジュールの回路（2 つ目以降）に `{ "styleKind": "split" }` を書き込む。
- 配線は書き換えない。
- 保存データの `STORAGE_VERSION`（`file/storage.ts`）と、共有用 JSON の `SHARE_VERSION`（`file/share.ts`）を、どちらも 3 に上げる。

### 確かめ方

- 変換ごとにテストする（その版の入力と、次の版の出力）。
- 順に適用した結果もテストする。version 1 のデータ（モジュールの出力につないだ配線を含む）を読み込むと、version 3 の形で、つながりが変わらないこと。
- `upgradeV2` は、変換を順に適用する入口の並びに加える。

## 段階

各段階の区切りで止め、次の段階の合図を待つ。

### 準備（済み）

- 未コミットだった、モジュールの配置の変更（幅 3、2 マスおき）を戻した。段階 1 は今の形を基準に見た目が変わらないことを確かめるため。この形は段階 3 の DIP に引き継ぐ。

### 段階 1: ピンの描き方を辺に合わせる

振る舞いを変えない組み替え（Skill の `refactor`）。

- `parts/layout.ts` の `PinSide` に `top` / `bottom` を足す。
- `geometry/layout.ts`: ピンの先の位置を求める処理（`pinTip`）を上下に対応させる。部品の占める範囲とはみ出し補正を、ピンの辺から決める形にする。
- `sheet/ComponentView.tsx`: ピンの線とピン名を、入力か出力かではなく辺で描き分ける。
- 確かめること: テスト。シートの SVG が変更前と同じこと（全種類の部品とモジュールを置いた回路で比べる）。はみ出し補正の結果が同じこと。

### 段階 2: version 3 の形と部品の種類

振る舞いを変える変更（Skill の `modify`）。

- 部品の種類の項目名（`partKind`）、モジュールを指す項目名（`module`）、部品の一覧の項目名（`parts`）、種類の名前の置き換え、型と定数の名前の見直し（コード、種類のフォルダ、テスト、ドキュメント）。
- `footprint` と `pinNumber` の型と検証。
- `footprint` から配置を作る道（上の「出し方」の最後の項目）。この段階で使うのは `split` だけ。
- `upgradeV2` を作り、入口の並びに加える。版を 3 に上げる。始める前に、[古い版の変換を順に適用する形にする](../upgrade-chain/plan.md)を終えておく。
- 新しいモジュールは、この段階では `split` で作る。見た目は今と同じ。
- 確かめること:
  - テスト: `upgradeV2` のテストと、順に適用した結果のテスト（version 1 / version 2 のデータが、つながったまま読める）。新しい項目名と種類の名前の検証。
  - ブラウザ: 書き出しと読み込み。version 2 の保存データと共有用 JSON を読み込める。

### 段階 3: DIP とピン番号

振る舞いを変える変更（Skill の `modify`）。

- DIP の配置、ピン番号の自動の割り当て、NC、入力か出力かの仮の印、外側のピン番号の表示、割り当ての問題の知らせ（中の部品の印とステータスバー）。
- 新しいモジュールは DIP の 8 ピンで作る。
- 確かめること:
  - テスト: 配置（番号と位置）、割り当て（置く・貼り付け・空きがない・重なり）。
  - ブラウザ: 見た目、配線のつながり。

### 段階 4: QFP

振る舞いを変える変更（Skill の `modify`）。

- 上下のピン、上下の辺のピン名の向き（縦書きか、短くするか）、モジュール名を本体の中へ。
- 確かめること: 上下のピンへの配線、128 ピンでの描画の重さ（フレームレート。[ブラウザでの動作確認](../../agent/browser-check.md)の「フレームレートを測る」）。

### 段階 5: プロパティ欄

振る舞いを変える変更（Skill の `modify`）。

- 編集できるようにするもの:
  - モジュールの出し方（`dip` / `qfp` / `split`）とピン数。
  - 中の `input` / `output` のピン番号。
- 形が変わる操作（出し方やピン数を変える）では、外の配線が外れることがあると、確認のダイアログで知らせる。
- `split` から `dip` / `qfp` に変えるときは、今の並び順（入力、出力の順）でピン番号を自動で割り当てる。
