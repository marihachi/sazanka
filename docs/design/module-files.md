# モジュールのファイル保存と再利用（仕様の検討）

状態: **検討中**。ここに書いた案は、まだ決まっていない。決まったら、形式の仕様（[docs/format/](../format/)）とエージェント向けのドキュメントに反映し、この文書は決定の記録として残すか、役目を終えたら消す。

## 目的

- モジュールを JSON ファイルとして保存し、別のプロジェクトで再利用できるようにする。
- モジュールは、UUID のような読めない ID ではなく、パスのような名前で参照したい（開発者の希望）。
  - 指したいのはファイルシステムの場所ではなく、**プロジェクトの中のモジュール**（開発者の希望）。例: `adders/full-adder`、`gates/xor`。

## 今の仕組み（前提）

- モジュールは、プロジェクトの中の回路（`circuits` の2つ目以降）。
- 部品 `CUSTOM` は、`custom` に回路の `id` を書いてモジュールを指す。
- ID の範囲:
  - 回路の `id` は、同じプロジェクトの中でだけ重ならない（ランダムな短い文字列で、読んでも意味が分からない）。
  - 部品と配線の `id` は、同じ回路の中でだけ重ならない。
  - そのため、モジュールを別のプロジェクトへ持ち込むと、回路の `id` がぶつかりうる。部品 ID とモジュール名の組み合わせでも一意にはならない（名前は自由に変えられ、重なることもある）。
- モジュールには、表示用の名前（`name`）だけがあり、フォルダのような分類はない。
- アプリはブラウザだけで動く（GitHub Pages、サーバーなし）。

## 考え方: モジュールのパス

プロジェクトの中のモジュールに、フォルダ分けされたパスを持たせる。

```
adders/half-adder
adders/full-adder
gates/xor
```

- パスは、プロジェクトの中で重ならない。これがモジュールの識別子になる。
- パスの最後の部分（`full-adder`）が、そのモジュールの名前として表示される。
- メイン回路はモジュールではないので、パスを持たない。
- 部品 `CUSTOM` は、パスでモジュールを指す（例: `adders/half-adder`）。
- パスはプロジェクトの中だけの名前なので、ファイルの置き場所やブラウザの制約（ファイルを読む許可、CORS など）とは関係しない。

ファイルシステムや URL を指すリンクは、ブラウザでは読み込みに制約が大きい（手元のファイルは読む許可が要り、使えるブラウザも限られる。URL は置き場所が CORS を許可している必要がある）。プロジェクトの中のパスなら、これを避けられる。

## 考えること

### 1. パスと、今の回路の ID の関係

2つのやり方がある。

- **A. パスを識別子そのものにする**: 回路の `id` をやめてパスにし、`custom` もパスで書く。
  - 利点: データを読めばどのモジュールを指しているか分かる。仕組みが1つで済む。
  - 欠点: モジュールの名前やフォルダを変えると、そのモジュールを使っているすべての部品の `custom` を書き換える必要がある（アプリがまとめて書き換える）。
- **B. アプリの中では今の `id` を使い、パスは別の項目に持つ**: `custom` は今までどおり `id` を指し、ファイルに保存するときだけパスで書く。
  - 利点: 名前を変えても参照を書き換えなくてよい。今の仕組みをあまり変えない。
  - 欠点: 保存データの中の参照は読めないまま。アプリの中とファイルとで、参照の書き方が2通りになる。

### 2. ファイルの単位と、持ち込み方

- **書き出す単位**: 1つのモジュールを書き出すとき、そのモジュールが使っているモジュールも一緒に入れる（入れ子をたどる）。入れないと、持ち込んだ先で中身が欠ける。
- **持ち込むとき**: ファイルの中のモジュールを、パスのままプロジェクトに足す。
  - 同じパスのモジュールがすでにあるとき、どうするかを決める必要がある。
    - **置き換える**: 同じパスは同じモジュールとみなし、新しい中身に差し替える。持ち込み直すことで「更新」になる。
    - **別の名前で足す**: `adders/full-adder (2)` のように別のパスにする。
    - **持ち込まない**。
  - 既定は「利用者に聞く」がよさそう。一度に複数がぶつかったときの聞き方も決める。
- **置き換えたときのピン**: 置き換えでモジュールのピンの数や並びが変わると、外側の配線が別のピンにつながったり、存在しないピンを指したりする。置き換える前に、ピンの変化を見せるなどの工夫が要る。

### 3. 相対パス

- プロジェクトの中ではパスを1通りに決められるので、相対パス（`./half-adder`、`../gates/xor`）は必須ではない。
- 相対パスが役に立つのは、フォルダごと別の場所へ持ち込むとき（例: `adders/` を持ち込み先の `lib/adders/` の下に置く）。そのとき、中の参照がそのまま使える。
- 最初は、プロジェクトのルートからの絶対パスだけにし、必要になったら相対パスを足す案がよさそう。

### 4. パスに使える文字と、名前の変更

- パスに使える文字を決める。区切りは `/`。空の部分、`.` と `..` は使えないようにする（相対パスを後で足す余地を残すため）。
- 今のモジュールの名前（日本語や空白を含みうる）を、そのままパスの部分に使えるようにするか決める。
- 名前やフォルダを変える操作を、どこに置くか（タブの名前の変更、パレット）。

### 5. 今の保存データからの移行

- 今のモジュールにはパスがないので、名前からパスを作る（フォルダなし、名前が重なっていたら `(2)` を付ける）。
- A を選ぶ場合、回路の `id` と `custom` の形が変わるので、保存データと共有用 JSON の版を上げ、古い版を読み込む処理を足す必要がある（[保存データ](../agent/persistence.md)）。B なら、パスの項目を足すだけで済む見込み。

## データの形の叩き台

1 で A を選んだ場合の叩き台（B の場合は、`path` を足して `custom` は `id` のまま）:

### プロジェクト

```json
{
  "circuits": [
    { "id": "main", "name": "メイン", "components": [{ "id": "a", "kind": "CUSTOM", "x": 100, "y": 100, "custom": "adders/full-adder" }], "wires": [] },
    { "path": "adders/full-adder", "components": [...], "wires": [] },
    { "path": "adders/half-adder", "components": [...], "wires": [] }
  ]
}
```

### モジュールのファイル

```json
{
  "app": "sazanka",
  "version": 2,
  "type": "modules",
  "entry": "adders/full-adder",
  "modules": [
    { "path": "adders/full-adder", "components": [...], "wires": [] },
    { "path": "adders/half-adder", "components": [...], "wires": [] }
  ]
}
```

- `entry` は、書き出したモジュール。`modules` には、それが使うモジュールも入る。
- プロジェクト全体の共有用 JSON と区別するため、`type` を持たせる。

## 決めること

1. **パスと ID の関係**: A（パスを識別子にする）か B（ID はそのまま、パスを足す）か。
2. **持ち込みでパスがぶつかったとき**: 置き換え / 別の名前で足す / 持ち込まない、をどう選ばせるか。置き換えを「更新」として扱うか。
3. **相対パス**: 最初は絶対パスだけにするか。
4. **パスの文字**: 日本語や空白を使えるか。
5. **フォルダの見せ方**: パレットやタブで、フォルダをどう見せるか（まとめて折り畳むなど）。
6. **書き出しの単位**: モジュール1つ（と、使っているモジュール）か、フォルダ単位か、選んだ複数か。

## 段階的に進める案

1. **モジュールにパスを持たせる**: フォルダ分けと、パスでの参照。ファイルの機能はまだ作らない。
2. **モジュールのファイルの書き出しと持ち込み**: 使っているモジュールも一緒に書き出し、持ち込みでパスがぶつかったら聞く。
3. **必要なら**: 相対パス、フォルダ単位の持ち込み先の指定。
