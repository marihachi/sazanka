# ソースの構成とリファクタリング

`src/` の今の構成と、コードをどこに置くかの決め方。

## 今の構成

`src/` は次のように分けている（プロジェクトの方針）。

- `engine/` … 回路のデータと計算処理。React や DOM に依存させない。
  - `component.ts` … 部品のデータと、部品の種類ごとの仕様（置ける種類の一覧、ピン、遅延）
  - `circuit.ts` … 回路1つ分のデータ（部品と配線）
  - `project.ts` … プロジェクト（メイン回路と複数のモジュール）の構造と、データの検証
  - `module.ts` … モジュールのピンの決め方と、回路同士の依存
  - この4つは、後に挙げたものが前に挙げたものだけを使う（`component` ← `circuit` ← `project` ← `module`）。
  - `sim.ts` … 回路の評価（1 tick ずつ進める）
  - `flatten.ts` … モジュールの展開
  - `edit.ts` … 回路の編集
  - `layout.ts` … 部品の大きさとピンの座標
  - `share.ts` … 共有用 JSON
  - `util.ts` … 型を問わない小さな判定
- `components/` … 画面の部品。`app/` を import しない（表示に必要なものは props で受け取る）。回路を直接書き換えず、「移動した」「接続した」などの出来事をコールバックで知らせる。元に戻す対象にするかどうかは `app/` 側で決める（[編集と元に戻す](editing.md)）。
  - 各コンポーネントと、その CSS。`parts.ts` … 部品の表示名とドラッグの受け渡し。`classNames.ts` … クラス名の連結
- `app/` … 画面全体の組み立てと状態。
  - `App.tsx` … 画面の組み立てと編集操作
  - `storage.ts` … localStorage への保存
  - `history.ts`、`useProjectHistory.ts`、`switchStates.ts` … 元に戻す / やり直し
  - `useSimulation.ts` … 時間を進めるシミュレーションと、一時停止・1段送り。`useShortcuts.ts` … キーボード操作。`hints.ts` … ヒントの文言
- `style.css` … 色の変数とページ全体のスタイル。どのコンポーネントからも使うものだけを置く。
- `assets/` … SVG。

CSS は、コンポーネント固有のものならコンポーネントごとに CSS Modules で分けて `components/` に置き（例: `TabBar.tsx` と `TabBar.module.css`）、そのコンポーネントから `styles` として import する（プロジェクトの方針）。共通の `style.css` は `main.tsx` で各コンポーネントより先に読み込む。

- CSS のクラス名はケバブケース、TS からの参照はキャメルケース（`vite.config.ts` の `localsConvention`）。存在しないクラス名を参照しても型エラーにならず `undefined` になるだけなので、追加・改名のときは両方を見比べること。
- ほかのコンポーネントのクラスは直接使わない。見た目を共有したいときは、コンポーネントとして切り出す（例: ツールバーなどのボタンのアイコンは `Icons.tsx` の `ToolIcon`）。

フォルダ同士の依存の向きは `app` → `components` → `engine` の一方向に保つ。フォルダの中のファイル同士も同じ考え方で一方向にする（[依存が一方向になるように分ける](#依存が一方向になるように分ける)）。

テストは、React に依存しない処理について、対象のファイルと同じフォルダに、同じ名前で置く（`sim.ts` なら `sim.test.ts`）。対象のファイルを分けたり名前を変えたりしたら、テストも合わせる。

## コードの置き場所の決め方

普段のコーディングとリファクタリングする際とで考え方を切り替える。

- 「題材」とは、そのファイルで何について書くかを指す。
- 「構成」とは、フォルダの分け方と、各フォルダの中のファイルの一覧と、各ファイルがどの題材を引き受けるかの割り当てのこと。1つのファイルは1つ以上の題材を持ち、同じ題材が2つのファイルにまたがらないようにする。

### 普段のコーディング

- 題材が近いファイルに足してよい。ぴったりの置き場所を探して手が止まるくらいなら、近いところに書いて先へ進む。普段は置き場所の検討でコストをあまり払いたくない。

### リファクタリングする際

- リファクタリングは、開発者に頼まれたときに行う。作業の中で構成の乱れに気付いたら、エージェントから提案してよい。提案だけにとどめ、合意なしに始めない。
- 目指すのは、できるだけ読みやすいコードにすること（開発者の方針）。置き場所に限らず、名前・関数の分け方・書き方も含めて、初めて読む人が追いやすいかを基準に判断する。
  - コードの短さや、共通化・抽象化の多さは目的にしない。共通化で読む場所が増えたり、処理の流れが追いにくくなったりするなら、重複を残す方を選ぶ。
  - 案が複数あって迷ったら、読みやすい方を選ぶ。
- コードの置き場所は、個々に考えるのではなく、フォルダ全体の構成として決める。

#### 構成を決めるとき

- 題材を並べてみて、遠いものが混ざっていないか確かめる。
- 同じ題材についてのものなら、型・定数・処理の別を問わず1つのファイルに置く。1つのファイルに複数の題材を持たせるなら、近いものだけにする。
  - 例: 部品の型・種類の一覧・ピンの数は、どれも「部品」についての事柄なので `component.ts` にまとめている。型と処理で分けたりはしない。
  - 例: 保存データの検証（バリデーション）は、プロジェクトのデータと題材が近いので、同じ `project.ts` に置いている。ここに画面の都合が混ざってきたら、遠い題材なので分ける。
- 数行のものは、題材の合うファイルがあればそちらに寄せる。読む側にとっては import が1行増えるだけで、得るものが少ないため。寄せ先がなければ単独のファイルでよい。
  - ただし、汎用的な関数（型を問わない判定など）は、このアプリの題材に属さないので、寄せずに `util.ts` に置く（開発者の方針）。今の使う側が1つの題材に偏っていても同じ。
- `engine/` の各ファイルは、先頭のコメントにそのファイルの題材を書く（開発者の方針）。近い題材が別のファイルにあるなら、その置き場所も添える（例: `circuit.ts` の「部品の種類の仕様は component.ts」）。題材を足したり移したりしたら、このコメントも直す。
- ファイル名と中身がずれたら、どちらかを直す。名前を決めるときは候補を複数挙げて、開発者に選んでもらう。
- 構成が変わったら、上の「今の構成」に反映する。

#### 依存が一方向になるように分ける

- フォルダの中のファイル同士の依存が一方向になるよう、層に分ける。土台は、そのフォルダが扱う対象そのもの（`engine/` なら回路とプロジェクトのデータ）。上の層ほど、それを使ってする仕事（評価、編集、保存、共有）になり、下のファイルだけを使う。
  - データの側が、保存や表示の都合を知らないようにするため。知っていると、保存形式を変えるたびにデータの定義まで直すことになる。
- 互いに import し合う形（循環）になったら、境界の引き方が間違っている合図。まず、題材の境界を引き直して一方向にできないかを検討する。どう引き直しても分けられないなら、1つのファイルにまとめる。
- 複数のファイルから使うデータや型は、使う側の1つではなく、それを作るファイルか、どちらでもない中立なファイルに置く（例: 座標を表す `Point` は、それを計算する `layout.ts`）。

#### コードを移すとき

- 決めた構成を、ファイルごとに、置くもの（型・関数・定数）と import するものを挙げて開発者に示し、合意してから移動を始める。
- 振る舞いを変えない。移動・改名と、機能の変更は混ぜない。
- 移動の前後で結果が変わらないことを確かめたいときは、移動前のコードと突き合わせる使い捨てのテストを書いてよい。確認できたら消す。
