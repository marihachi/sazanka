# ドキュメントの書き方

エージェント向けドキュメント（`AGENTS.md` と `docs/agent/`）の書き方と、Skill にするものの決め方。

## 何を書くか

気付いたことは、その都度書く。

書くもの:

- 規則と、その理由や背景、設計の意図、既知の制約。
- 開発者と決めた取り決め。
- 実装で注意したこと、選んだ理由、落とし穴とその避け方。
- 触ると壊れるもの（合わせて直す必要があるもの、守らないと動かなくなる前提）。
- コードを読めば分かることのうち、重要なもの。例: (開発者からの指示)
  - 複数のファイルにまたがる処理の流れ（例: 編集がどう元に戻す対象になるか）。
  - 読み始める場所（入口のファイルや関数）。
  - 変えると別の場所も直す必要がある値や名前（保存データのキー、ピン番号の決め方など）。

書かないもの:

- 1 つのファイルの中で完結する処理の中身。分かりにくいなら、ドキュメントではなくコードのコメントに書く（[コードの書き方](coding-style.md)の「コメント」）。
- 今後の判断に役立たない過去の経緯（以前の名前、採らなかった案、直した不具合）。

文章は短く、1 文に 1 つのことを書く。結論を先に書き、理由は後に添える。言葉は[用語](glossary.md)にそろえる。

## どこに書くか

- コードと同じく、責務ごとにファイルを分ける（[コードの置き場所の決め方](code-placement.md)）。ある実装を変えるときに、関係するファイルだけを読めば済むようにするため。
- 1 つのファイルに別の責務が混ざってきたら分け、元のファイルから 1 行で案内する。
- ファイルを作ったら、`AGENTS.md` の一覧に載せる。どの作業でも要るものは「作業前に必ず読むドキュメント」、特定の実装を触るときだけ要るものは「触るときに読むドキュメント」に入れる。
- 開発者が決めた規則は、その規則が関わる節の中に書く。書き方と使い分けは [AGENTS.md](../../AGENTS.md) の「規則の扱い」にある。
- 特定のエージェントにだけ当てはまる内容（Claude Code のフックなど）は、エージェント名の見出し（例: `## Claude Code`）を立てて分ける。
- ファイル名は重ねない（Skill からファイル名で参照するため。[Skill の追加・編集](skills.md)）。
- 1 つのファイルが長くなり、責務が 2 つ以上あるなら、分けられないか考える。読むファイルが長いと、その作業に要らない部分まで読むことになるため。分けるかどうかと分け方は、開発者に示して決める。(開発者からの指示)

## いつ見直すか

- 作業のたびに、触った部分のドキュメントが今のコードと合っているかを確かめる。合わない記述は直し、役目を終えた記述は消す。
- 大きく作り変えたあとや、開発者に頼まれたときは、全体を見直す。手順は Skill の `doc-review` にある。

## Skill にするもの

手順は Skill に書く。ドキュメントは「どうなっているか」、Skill は「やるときに何を順に踏むか」を書く。同じ手順をドキュメントに重ねて書かない。

- Skill があった方が良いと気付いたら、開発者に提案する。目印は、同じ手順を何度も説明している、毎回同じ順で作業している、忘れると手戻りになる確認がある、など。
- 提案には、使う場面、手順の概要、名前の候補を複数含める。手順がまだどこにも書かれていなければ、その場で書き出して見せる。
- Skill の置き場所と書き方は [Skill の追加・編集](skills.md) にある。

### 開発者からの指示

- Skill は勝手に作らず、提案してから作る。
- Skill には、このアプリ固有の内容を書かない（ほかのプロジェクトでも使えるようにするため）。アプリ固有の内容はドキュメントに書き、Skill からはファイル名と見出しで参照する。
