# 作業の進め方

- 開発者とのやりとり、UI の文言、コードコメントは日本語。開発者の画面に出るものはすべて含む。返答の本文だけでなく、ツールを呼ぶときに付ける説明や、確認用スクリプトが出す文言のように、作業の途中で表示されるものも日本語で書く。
- 変更後は `npm run format` で整形し（Biome）、`npm run lint`、`npx tsc -b`、`npm test`、`npx vite build` を通す。`npm run build` は型チェックとビルドをまとめて行う。整形と Lint をまとめて確かめるなら `npm run check`、整形されているかだけなら `npm run format:check`。
  - Markdown は Biome の対象外なので、整形されない。ドキュメントは手で整える。
- 改行コードは LF に統一している（`.gitattributes` と `biome.json`）。Windows などで `core.autocrlf=true` の環境では、`.gitattributes` がないと Git から取り出したファイルが CRLF になり、整形チェックに引っかかる。
- 画面や操作に関わる変更をしたら、ヘッドレスブラウザで動作を確かめる（開発者の方針）。テストとビルドが通るだけで済ませない。やり方は下の「ヘッドレスブラウザでの動作確認」にまとめている。
  - どうしても確かめられなかった場合は、報告にそう明記する。
- コミットは開発者に頼まれたときだけ行う。
- Windows では、`npm test` がまれに、全テストファイルの読み込みに失敗して「no tests」で終わることがある。再実行すると通る。原因は未特定（作業ディレクトリのドライブ名が `c:` と `C:` で切り替わった直後に起きやすいが、意図して再現はできていない）。個別のテストが失敗しているのではなく全ファイルがまとめて読み込めない場合は、まず再実行する。

## ヘッドレスブラウザでの動作確認

確認のたびに使い捨てのスクリプトを書いて走らせる。スクリプトはリポジトリに置かない（作業用のフォルダに置く）。ブラウザを操作する仕組み（Chrome DevTools Protocol を使うものなど）も、プロジェクトの依存には加えず、作業用のフォルダに入れる。

1. 開発サーバーを起動する（`npx vite --port 5199 --strictPort` をバックグラウンドで）。ポートが埋まっていたら、別のポートに変えて自分で立て直す。すでに動いているサーバーにつなぐと、自分の変更を見ている保証がない（開発者が別の作業で立てていることがある）。
2. スクリプトでヘッドレスブラウザを起動し、`http://localhost:5199/` を開く。使えるブラウザは開発環境によって異なるので、その環境にあるものを確かめてから使う。
   - 例: Node が使える環境なら、作業用のフォルダに `puppeteer-core` を入れ、その環境にインストール済みのブラウザ（実行ファイルのパスを指定する）を動かす。スクリーンショットだけなら、ブラウザのヘッドレスモードをコマンドで呼ぶだけでも足りる。
3. 確かめたいことに応じて、操作・読み取り・スクリーンショットを行う。
4. 終わったらサーバーとブラウザを止める。

確かめ方の例:

- **見た目**: スクリーンショットを撮って、画像として確認する。
- **操作**: ボタンや部品をクリックする、文字を入力する、キーを押す。
- **状態**: 表示されている文言、ボタンが押せるかどうか、配線やランプの色、タブの一覧を読む。
- **回数や間隔の測定**: 値が変わる間隔（ms）、一定時間の DOM の書き換え回数、フレームの要求回数。描画を間引く仕組みが効いているかは、これで測る。
- **エラー**: ページの例外、コンソールのエラー、失敗した通信（404 など）を集めて最後に出す。想定していない読み込み失敗に気付ける。

ハマりやすい点:

- **回路を用意するときは localStorage に直接書く**。画面で組み立てるより速い。ただし、最初のページ読み込みが終わるのを待ってから書き込むこと。待たずに書くと、アプリ側の自動保存に上書きされて空のまま始まる。書き込んだら再読み込みする。
- **部品の座標は、シートの表示範囲に合わせる**。シートは横 300 マス・縦 200 マスあり、開いた直後はその真ん中（`x` が 2500 前後、`y` が 1900 前後）が見えている（`components/view.ts` の `centerView`）。原点に近い座標（`x: 200` など）に置くと画面の外になり、クリックしても何にも当たらない。座標は部品同士が重ならないよう、`GRID`（20）の何倍かずつ離す。
- **CSS Modules のクラス名はハッシュが付く**ので、完全一致では探せない。`wire` を含み `wire-hit` を含まない、のように部分一致で見る。
- **新しいプロファイルで開くと localStorage は空**（メイン回路だけ）になる。スクリプトを分けて走らせると、前の確認の状態は残らない。

## 公開

- main に push すると、GitHub Actions（`.github/workflows/deploy.yml`）がテストとビルドをして GitHub Pages に公開する。公開先は `https://marihachi.github.io/sazanka/`。
  - Pages の公開元は、リポジトリの設定で「GitHub Actions」にしてある。ワークフローからは有効化しない（開発者の方針）。
  - ワークフローでは整形チェックをしない（開発者の方針）。整形は手元で済ませる。
- Pages ではリポジトリ名のフォルダの下に置かれるので、`vite.config.ts` の `base` を `/sazanka/` にしている。リポジトリ名や公開先が変わったら、`base` と、「このアプリについて」の GitHub へのリンク（`Dialogs.tsx`）も合わせて直す。
- ビルド結果の JS は、ライブラリ（`node_modules` のもの）とアプリのコードを別のチャンクに分けている（`vite.config.ts` の `advancedChunks`、開発者の方針）。ライブラリは変更が少ないので、アプリだけを直して公開したときに、ブラウザのキャッシュが効く。
- 公開後なので、保存データと共有用 JSON の形式を変えるときは、版を上げる必要があるかを確かめる（[保存データ](persistence.md)）。

## Claude Code

- Edit / Write でファイルを編集するたびに、フック（`.claude/settings.json` → `.claude/hooks/format.mjs`）が Biome で整形する。Lint の指摘は直さないので、`npm run lint` で確かめる。シェルからの書き込み（sed、スクリプトなど）には効かないので、その場合は自分で整形する。
