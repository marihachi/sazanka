# コードの置き場所の決め方

コードをどのファイルに置くか、構成をどう変えるかの考え方。今の構成は[ソースの構成](structure.md)にある。普段のコーディングと、リファクタリングのときとで、考え方を切り替える（下の「普段のコーディング」と「リファクタリング」）。

- 責務: そのファイルが受け持つ仕事。責務は「そのファイルを直すことになる理由」で見分ける。直す理由が 1 つにまとまるなら、責務も 1 つ。
- 構成: フォルダの分け方、各フォルダの中のファイル、各ファイルの責務の割り当て。

## 普段のコーディング

- 新しいコードは、責務の近いファイルに足してよい。ぴったりの置き場所を探して手が止まるくらいなら、近いところに書いて先へ進む。
- 構成の乱れに気付いたら、直さずに開発者へ提案する。

## リファクタリング

- 進め方（計画で調べること、構成案の示し方、移す順、付随して直すもの）は Skill の `refactor` にある。計画は Skill の `plan` で立てる。
- 置き場所は、ファイルごとに考えず、フォルダ全体の構成として決める。

### 開発者からの指示

- リファクタリングは、開発者に頼まれたとき、または提案して合意が取れたときに行う。
- 目指すのは、できるだけ読みやすいコード。置き場所に限らず、名前、関数の分け方、書き方も含めて、初めて読む人が追いやすいかで判断する。
  - コードの短さは目的にしない。
  - 抽象化（使う側が中身や場合の違いを知らずに済むよう、間に定義の形を挟むこと）は、してよい（下の「場合ごとの違いの持たせ方」）。
  - 共通化（似た処理を 1 つにまとめて、複数の場所から使うこと）は慎重に決める。今は同じでも、あとで中身が分かれると、まとめたものをばらし直すことになるため。
    - まとめるのは、同じ理由で一緒に直すものだけ。たまたま似ているだけなら、重複を残す。
    - まとめると読む場所が増えたり、流れが追いにくくなったりするときも、重複を残す。
  - 案が複数あって迷ったら、読みやすい方を選ぶ。

## 責務で分ける

- 1 つのファイルには、1 つの責務だけを持たせる。同じ責務を 2 つのファイルに分けない。関数も、1 つの関数に 1 つの仕事をさせる。
- 同じ責務のものは、型・定数・処理の別を問わず 1 つのファイルに置く。型と処理で分けたりしない。
  - 例: 部品の種類のピン・遅延・評価は、どれもその種類の仕様が変わったときに直すので、種類のフォルダの `spec.ts` にまとめている。
  - 例: `project.ts` のプロジェクトの構造と検証は、保存データの形が変わると一緒に直すので、同じファイルに置いている。
- 同じものを扱うコードでも、責務が違えば（直す理由が違えば）分ける。
  - 例: 種類のフォルダの `spec.ts` と `layout.ts` はどちらも部品の種類を扱う。前者は仕様（ピンの数、遅延）が変わったとき、後者はシート上の配置（大きさ、ピンの置き方）が変わったときに直すので分けている。
- 概念が近いこと自体は、まとめる理由にしない。そのかわり、先頭のコメントで互いの置き場所を示す。
- 境界に迷ったら、概念の近さではなく「何を知る必要があるか」で分ける。こうすると依存の境界と責務の境界がそろうので、線を引いた理由を説明しやすい。
  - 例: 回路は部品を含み、モジュールの部品はまた回路を指すので、概念では分けにくい。`circuit/` では「プロジェクトを知る必要があるか」で分けている。
- データの側には、保存や表示の都合を持ち込まない。持ち込むと、保存形式を変えるたびにデータの定義まで直すことになる。

## 場合ごとの違いの持たせ方

以下は開発者からの指示です。

- 種類などの場合によって変わる処理は、すべての場合を 1 か所に書き込まない（使う側で種類の名前を見て分岐させない）。場合ごとの定義に持たせ、使う側はその定義を引いて使うだけにする（制御の反転）。ある場合を足したり変えたりするときに、その場合の定義だけを直せば済むようにするため。
  - 例: 部品の大きさとピンの置き方は、種類ごとの配置（`parts/<種類>/layout.ts`）に持たせている。`geometry/layout.ts` は、配置を引いて px に直すだけ。
- 多くの場合に共通する振る舞いは、既定として用意し、違う場合だけが上書きする形にしてよい（例: 形ごとの既定の配置と、それを上書きする `output/layout.ts`）。既定は共通化の一種なので、上の「リファクタリング」の共通化の決まりに従う。既定と違ってきた場合は、まとめたものを直さず、その場合の定義で上書きする。
- 定義の形（型）は、使う側が必要とするものから決める。使う側が、どの場合かを知らずに済むようにするため。

## 構成を決めるとき

- ファイルごとに直す理由を挙げ、責務が 2 つ以上混ざっていないか確かめる。
- 数行のものは、責務の合うファイルがあればそちらに寄せる。読む側には import が 1 行増えるだけで、得るものが少ないため。寄せ先がなければ単独のファイルでよい。
- ファイル名と中身がずれたら、どちらかを直す。
- 構成が変わったら、[ソースの構成](structure.md)を直す。

### 開発者からの指示

- 汎用的な関数（型を問わない判定など）は、このアプリのどの責務にも属さないので `src/util.ts` に置く。今使っている側が 1 つの責務に偏っていても同じ。
- React を使わない `.ts` のファイルは、先頭のコメントにそのファイルの責務を書く。近い責務が別のファイルにあるなら、その置き場所も添える（例: `circuit.ts` の「部品のデータは component.ts」）。責務を足したり移したりしたら、このコメントも直す。
- 名前を決めるときは、候補を複数挙げて開発者に選んでもらう。

## 依存の向き

- 複数のファイルから使うデータや型は、使う側の 1 つではなく、それを作るファイルか、中立なファイルに置く（例: 座標の `Point` は、それを計算する `geometry/layout.ts`）。
- 互いに import し合う形（循環）は、それだけでは書き換える理由にしない。読み込みの途中の値を使って壊れる落とし穴（[ソースの構成](structure.md)の「依存の向き」）にだけ気を付ける。
- 依存について必ず守る決まりは、画面と計算の分け方（[ソースの構成](structure.md)）と、`util.ts` が何も import しないことの 2 つだけ。

### 開発者からの指示

- 依存の向きが一方向であることは必須ではない。逆向きに使う方が読みやすいなら、そうしてよい。一方向に保つために、型や処理を不自然な場所へ移したり、ファイルを分けたりしない。
- 目指す形は、下の層ほど簡素な機能を持ち、上の層がそれらを組み合わせてより複雑なことをする構造。
  - 土台は扱う対象そのもの（データの `circuit/`、部品の種類の `parts/`、回路を知らない画面部品の `ui/`）。その上がそれを使う処理（評価、編集、保存、共有）。いちばん上が画面全体の組み立て（`app/`）。
  - 置き場所に迷ったら、「どちらが簡素で、どちらがそれを組み合わせる側か」で上下を決める。簡素な側は、組み合わせる側の事情（使われ方、画面の都合）を知らないようにする。
  - 逆向きの依存が出てきたら、上下の決め方が合っているかを見直すきっかけにする。
