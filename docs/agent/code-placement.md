# コードの置き場所の決め方

個々のコードの置き場所を1つずつ考えるのではなく、先にフォルダ全体の構成を決め、それに従って置く。

## 新しいコードを書くとき

- 各ファイルの「何を書く場所か」に照らして、当てはまるファイルに書く。
- どのファイルにも当てはまらない、または2つに半分ずつ当てはまるなら、そのコードではなく構成のほうが合わなくなった合図。構成から見直す。

## 構成を決めるとき

- ファイルの一覧と、各ファイルに何を書くかを決める。各ファイルが「何を書く場所か」を1文で言えること。言えないファイルは、範囲の決め方を間違えている。
- 同じ依頼でいつも一緒に直すものは、関心が違っても1つのファイルに置く。別々の依頼で別々に直すものは分ける。
  - 例: 「部品を1種類増やして」では、部品の型・種類の一覧・ピンの数を必ず同時に直す。だから同じファイルに置く。
  - 例: 「壊れた保存データをもっと厳しく弾いて」では、検証だけを直す。だから分ける。
- 小さいまま単独のファイルにしない。数行のファイルは、読む側にとっては import が1行増えるだけで、得るものが少ない。
- ファイル名と中身がずれたら、どちらかを直す。名前を決めるときは候補を複数挙げて、開発者に選んでもらう。

## 依存が素直になるように並べる

- 層になるように並べる。土台は、そのフォルダが扱う対象そのもの（`engine/` なら回路とプロジェクトのデータ）。上の層ほど、それを使ってする仕事（評価、編集、検証、保存、共有）になり、下のファイルだけを使う。
  - データの側が、保存や表示の都合を知らないようにするため。知っていると、保存形式を変えるたびにデータの定義まで直すことになる。
- 互いに読み合う形になるなら、そこは分けられない。1つのファイルにまとめる。循環は、境界の引き方が間違っている合図。
- 複数のファイルから使うデータや型は、使う側の1つではなく、それを作るファイルか、どちらでもない中立なファイルに置く（例: 座標を表す `Point` は、それを計算する `layout.ts`）。データと、それを扱う処理が同じファイルにあること自体は問題ない。

## 移すとき

- 決めた構成を、ファイル・書くもの・import するもの、の形で開発者に示し、合意してから移動を始める。
- 振る舞いを変えない。移動・改名と、機能の変更は混ぜない。
- 移動の前後で結果が変わらないことを確かめたいときは、移動前のコードと突き合わせる使い捨てのテストを書いてよい。確認できたら消す。
- 決めた構成は[ソースの構成](structure.md)に書く。
