# コードの置き場所の決め方

コードをどのファイルに置くかと、構成を変えるときの考え方。今の構成は[ソースの構成](structure.md)にある。

普段のコーディングとリファクタリングする際とで考え方を切り替える。

- 「責務」とは、そのファイルが引き受ける仕事のこと。言い換えると、そのファイルを直すことになる理由。
- 「構成」とは、フォルダの分け方と、各フォルダの中のファイルの一覧と、各ファイルがどの責務を引き受けるかの割り当てのこと。1つのファイルは1つの責務を持ち、同じ責務が2つのファイルにまたがらないようにする。

## 普段のコーディング

- 責務が近いファイルに足してよい。ぴったりの置き場所を探して手が止まるくらいなら、近いところに書いて先へ進む。普段は置き場所の検討でコストをあまり払いたくない。

## リファクタリングする際

- リファクタリングは、開発者に頼まれたときに行う。作業の中で構成の乱れに気付いたら、エージェントから提案してよい（[作業の進め方](workflow.md)）。
- 進め方（構成案の示し方、移す順、付随して直すもの）は Skill の `refactor` にある。
- 目指すのは、できるだけ読みやすいコードにすること（開発者の方針）。置き場所に限らず、名前・関数の分け方・書き方も含めて、初めて読む人が追いやすいかを基準に判断する。
  - コードの短さや、共通化・抽象化の多さは目的にしない。共通化で読む場所が増えたり、処理の流れが追いにくくなったりするなら、重複を残す方を選ぶ。
  - 案が複数あって迷ったら、読みやすい方を選ぶ。
- コードの置き場所は、個々に考えるのではなく、フォルダ全体の構成として決める。

### 責務で分ける

- 1つのファイルは、1つの理由でだけ直すことになるようにする。関数も同じで、1つの関数には1つの仕事をさせる。
- 同じ責務のものは、型・定数・処理の別を問わず1つのファイルに置く。型と処理で分けたりはしない。
  - 例: ある部品の種類のピン・遅延・評価は、どれもその種類の仕様が変わったときに直すので、`parts/` の種類のフォルダ（`parts/and/spec.ts` など）にまとめている。
  - 例: `project.ts` のプロジェクトの構造と検証は、保存データの形が変わると一緒に直すので、同じファイルに置いている。ここに画面の都合が混ざってきたら、直す理由が違うので分ける。
- 同じものについてのコードでも、直す理由が違えば分ける。
  - 例: `component.ts` と `layout.ts` はどちらも部品を扱うが、前者は部品の仕様（ピンの数、遅延）が変わったときに、後者は画面での見せ方（大きさ、ピンの座標）が変わったときに直すので、分けている。
- 概念が近いこと自体は、ファイルをまとめる理由にしない。責務が違えば、分けておいた方が探しやすい。その代わり、先頭のコメントで互いの置き場所を示す。
- 責務の境界を引く場所に迷うときは、概念の近さではなく「何を知る必要があるか」で分ける。依存の境界と責務の境界がそろうので、線を引いた理由を説明しやすい。
  - 例: 部品・回路・モジュールは、回路が部品を含み、部品 (CUSTOM) がまた回路を指す入れ子の関係なので、概念だけでは分けにくい。`circuit/` では「プロジェクトを知る必要があるか」で線を引いている（`component.ts`・`circuit.ts` は知らない。`project.ts`・`module.ts` は知る）。
- フォルダは目的（機能）ごとに分け、1 つの目的の型・計算・画面・状態のフックを同じフォルダに置く（[ソースの構成](structure.md)）。その中で、画面と計算はファイルで分ける。編集処理（`editing/edit.ts`）は新しい回路を返すだけで、元に戻す対象にするかは `App.tsx` が決める。画面の部品は起きた出来事を知らせるだけで、回路は書き換えない。この分担を崩す処理（例: コンポーネントの中で履歴を積む）を足さない。

### 構成を決めるとき

- ファイルごとに直す理由を挙げてみて、1つにまとまらないものが混ざっていないか確かめる。
- 数行のものは、責務の合うファイルがあればそちらに寄せる。読む側にとっては import が1行増えるだけで、得るものが少ないため。寄せ先がなければ単独のファイルでよい。
  - ただし、汎用的な関数（型を問わない判定など）は、このアプリのどの責務にも属さないので、寄せずに `src/util.ts` に置く（開発者の方針）。今の使う側が1つの責務に偏っていても同じ。
- React を使わない `.ts` のファイル（データと計算）は、先頭のコメントにそのファイルの責務を書く（開発者の方針）。近い責務が別のファイルにあるなら、その置き場所も添える（例: `circuit.ts` の「部品のデータは component.ts」）。責務を足したり移したりしたら、このコメントも直す。
- ファイル名と中身がずれたら、どちらかを直す。名前を決めるときは候補を複数挙げて、開発者に選んでもらう。
- 構成が変わったら、[ソースの構成](structure.md)に反映する。

### 依存の向き

- 依存の向きが一方向であることは必須ではない（開発者の方針）。逆向きに使うほうが読みやすいなら、そうしてよい。一方向に保つために、型や処理を不自然な場所へ移したり、ファイルを分けたりはしない。
- 目指す形は、下の層ほど簡素な機能を持ち、上の層がそれらを組み合わせてより複雑なことを実現する構造（開発者の方針）。土台は扱う対象そのもの（回路とプロジェクトのデータの `circuit/`、部品の種類の `parts/`、回路を知らない画面部品の `ui/`）、その上がそれを使ってする仕事（評価、編集、保存、共有）、いちばん上が画面全体の組み立て（`app/`）。
  - 置き場所や分け方に迷ったら、「どちらが簡素で、どちらがそれを組み合わせる側か」で上下を決める。簡素な側が、組み合わせる側の事情（使われ方、画面の都合）を知らないようにする。
  - 一方向にすること自体は目的にしない（上の項目）。逆向きの依存が出てきたら、上下の決め方（どちらが簡素か）が合っているかを見直すきっかけにする。今の並びは[ソースの構成](structure.md)の「依存の向き」。
  - データの側には、保存や表示の都合を持ち込まない。持ち込むと、保存形式を変えるたびにデータの定義まで直すことになる。これは依存の向きの決まりではなく、責務の分け方の話（上の「責務で分ける」）。
- 互いに import し合う形（循環）は、それだけで直す理由にはしない。読み込みの途中の値を使って壊れる場合があるので、その落とし穴（[ソースの構成](structure.md)の「依存の向き」）にだけ気を付ける。
- 複数のファイルから使うデータや型は、使う側の1つではなく、それを作るファイルか、どちらでもない中立なファイルに置く（例: 座標を表す `Point` は、それを計算する `layout.ts`）。
