# コードの置き場所の決め方

コードをどのファイルに置くかと、構成を変えるときの考え方。今の構成は[ソースの構成](structure.md)にある。

普段のコーディングとリファクタリングする際とで考え方を切り替える。

- 「責務」とは、そのファイルが引き受ける仕事のこと。言い換えると、そのファイルを直すことになる理由。
- 「構成」とは、フォルダの分け方と、各フォルダの中のファイルの一覧と、各ファイルがどの責務を引き受けるかの割り当てのこと。1つのファイルは1つの責務を持ち、同じ責務が2つのファイルにまたがらないようにする。

## 普段のコーディング

- 責務が近いファイルに足してよい。ぴったりの置き場所を探して手が止まるくらいなら、近いところに書いて先へ進む。普段は置き場所の検討でコストをあまり払いたくない。

## リファクタリングする際

- リファクタリングは、開発者に頼まれたときに行う。作業の中で構成の乱れに気付いたら、エージェントから提案してよい。提案だけにとどめ、合意なしに始めない。
- 目指すのは、できるだけ読みやすいコードにすること（開発者の方針）。置き場所に限らず、名前・関数の分け方・書き方も含めて、初めて読む人が追いやすいかを基準に判断する。
  - コードの短さや、共通化・抽象化の多さは目的にしない。共通化で読む場所が増えたり、処理の流れが追いにくくなったりするなら、重複を残す方を選ぶ。
  - 案が複数あって迷ったら、読みやすい方を選ぶ。
- コードの置き場所は、個々に考えるのではなく、フォルダ全体の構成として決める。

### 責務で分ける

- 1つのファイルは、1つの理由でだけ直すことになるようにする。関数も同じで、1つの関数には1つの仕事をさせる。
- 同じ責務のものは、型・定数・処理の別を問わず1つのファイルに置く。型と処理で分けたりはしない。
  - 例: 部品の型・種類の一覧・ピンの数は、どれも部品の仕様が変わったときに直すので、`component.ts` にまとめている。
  - 例: `project.ts` のプロジェクトの構造と検証は、保存データの形が変わると一緒に直すので、同じファイルに置いている。ここに画面の都合が混ざってきたら、直す理由が違うので分ける。
- 同じものについてのコードでも、直す理由が違えば分ける。
  - 例: `component.ts` と `layout.ts` はどちらも部品を扱うが、前者は部品の仕様（ピンの数、遅延）が変わったときに、後者は画面での見せ方（大きさ、ピンの座標）が変わったときに直すので、分けている。
- 概念が近いこと自体は、ファイルをまとめる理由にしない。責務が違えば、分けておいた方が探しやすい。その代わり、先頭のコメントで互いの置き場所を示す。
- 責務の境界を引く場所に迷うときは、概念の近さではなく「何を知る必要があるか」で分ける。依存の境界と責務の境界がそろうので、線を引いた理由を説明しやすい。
  - 例: 部品・回路・モジュールは、回路が部品を含み、部品 (CUSTOM) がまた回路を指す入れ子の関係なので、概念だけでは分けにくい。`engine/` では「プロジェクトを知る必要があるか」で線を引いている（`component.ts`・`circuit.ts` は知らない。`project.ts`・`module.ts` は知る）。
- フォルダの間でも責務で分けている。`engine/` の編集処理は新しい回路を返すだけで、元に戻す対象にするかは `app/` が決める。`components/` は起きた出来事を知らせるだけで、回路は書き換えない。この分担を崩す処理（例: コンポーネントの中で履歴を積む）を足さない。

### 構成を決めるとき

- ファイルごとに直す理由を挙げてみて、1つにまとまらないものが混ざっていないか確かめる。
- 数行のものは、責務の合うファイルがあればそちらに寄せる。読む側にとっては import が1行増えるだけで、得るものが少ないため。寄せ先がなければ単独のファイルでよい。
  - ただし、汎用的な関数（型を問わない判定など）は、このアプリのどの責務にも属さないので、寄せずに `util.ts` に置く（開発者の方針）。今の使う側が1つの責務に偏っていても同じ。
- `engine/` の各ファイルは、先頭のコメントにそのファイルの責務を書く（開発者の方針）。近い責務が別のファイルにあるなら、その置き場所も添える（例: `circuit.ts` の「部品の種類の仕様は component.ts」）。責務を足したり移したりしたら、このコメントも直す。
- ファイル名と中身がずれたら、どちらかを直す。名前を決めるときは候補を複数挙げて、開発者に選んでもらう。
- 構成が変わったら、上の「今の構成」に反映する。

### 依存が一方向になるように分ける

- フォルダの中のファイル同士の依存が一方向になるよう、層に分ける。土台は、そのフォルダが扱う対象そのもの（`engine/` なら回路とプロジェクトのデータ）。上の層ほど、それを使ってする仕事（評価、編集、保存、共有）になり、下のファイルだけを使う。
  - データの側が、保存や表示の都合を知らないようにするため。知っていると、保存形式を変えるたびにデータの定義まで直すことになる。
- 互いに import し合う形（循環）になったら、境界の引き方が間違っている合図。まず、責務の境界を引き直して一方向にできないかを検討する。どう引き直しても分けられないなら、1つのファイルにまとめる。
- 複数のファイルから使うデータや型は、使う側の1つではなく、それを作るファイルか、どちらでもない中立なファイルに置く（例: 座標を表す `Point` は、それを計算する `layout.ts`）。

### コードを移すとき

- 決めた構成を、ファイルごとに、置くもの（型・関数・定数）と import するものを挙げて開発者に示し、合意してから移動を始める。
- 振る舞いを変えない。移動・改名と、機能の変更は混ぜない。
- 移動の前後で結果が変わらないことを確かめたいときは、移動前のコードと突き合わせる使い捨てのテストを書いてよい。確認できたら消す。
