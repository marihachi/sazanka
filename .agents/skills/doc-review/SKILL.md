# ドキュメントの見直し

エージェント向けのドキュメント（入口の `AGENTS.md` と、そこから辿れるもの）を、今のコードと取り決めに合わせる。ドキュメントの一覧と読み方は `AGENTS.md`、書き方の方針は `documentation.md`（`AGENTS.md` の一覧から辿る）にあるので、まずそれらを読む。

作業で触った部分の見直しは毎回行う。この Skill は、大きく作り変えたあとや、開発者に頼まれたときの**全体の見直し**に使う。

## 手順

1. **範囲を決める**。全体か、ある責務の周りだけか。全体なら、ドキュメントの置き場所にある全ファイルを対象にする。
2. **コードとの食い違いを探す**。ドキュメントが挙げている名前（ファイル、関数、定数、クラス名、キー名）が今も存在するかを確かめる。改名や削除に取り残された記述がいちばん出やすい。
3. **消すものを探す**。
   - コードを読めば分かるようになった記述。
   - 今後の判断に役立たない過去の経緯（以前の名前、採らなかった案、直した不具合）。
   - 役目を終えた記述（未リリース前提の判断など）。
4. **足りないものを探す**。直近の実装で決めたこと、選んだ理由、落とし穴、触ると壊れるものが書かれているか。書かれていなければ、その責務のファイルに足す。
5. **一覧との対応を確かめる**。ドキュメントの置き場所の全ファイルが、`AGENTS.md` のいずれかの一覧に載っているか。逆に、一覧にあってファイルがないものがないか。ファイル名が重なっているものがないか（Skill からはファイル名で参照するので、重なると一意に決まらない。重なっていたら、重ならない名前に変える）。
6. **節の名前で参照している箇所を確かめる**。「〜の「◯◯」にある」のように見出しを名指ししている記述は、その見出しが今もその名前であるかを確かめる（`grep` で「の「` などを探す）。リンクは生きていて節の名前だけが変わっている場合は、リンク切れの確認では見つからない。
7. **用語のぶれを確かめる**。用語のドキュメント（`glossary.md`。`AGENTS.md` の一覧から辿る）の言い方と、各ドキュメント・UI の文言・コードコメントがそろっているか。同じものを別の言葉で呼んでいる箇所を直す。
8. **責務の混ざりと長さを確かめる**。1 つのファイルに別の責務が混ざっていたら分け、元のファイルから 1 行で案内する。ほかと比べて長くなったファイルは、分けられないか検討し、分け方を開発者に示す。分けたら 5 もやり直す。
9. **文章を整える**。2〜8 で直したファイルを対象に、Skill の `doc-polish` で文章を整える。中身を合わせてから整えるのは、先に整えると、中身を直したときに整え直しになるため。
10. **整形**。整形の道具が Markdown を扱わないなら手で整える。表の桁をそろえ、リンクが切れていないか確かめる。最後に、`workflow.md` にある整形と Lint の確認を通す。
11. **報告**。見つけた問題と直した内容を、問題ごとに分けて開発者に伝える。確認して問題がなかった観点も、何を見たかが分かるように添える。

## 注意

- Skill を直したときは、`skills.md` の手順に従う（置き場所が複数あるなら、そろえる）。
- ドキュメントを消すか残すかで迷ったら、決め打ちせずに開発者に聞く。
- 開発者が決めた規則として区別されている記述（区別の仕方は `AGENTS.md` にある）は、コードと食い違っていても勝手に直さない。食い違いを報告し、どちらに合わせるかを開発者に聞く。
- 開発者が手で直した箇所を、整理のついでに元に戻してしまわないよう気を付ける。直す前に `git diff` と `git log` で、直近に手が入った箇所を見ておく。
