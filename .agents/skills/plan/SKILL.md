# 計画

実装の変更について、調べて計画を立て、開発者に案を示して決めてもらうまでの手順。取り決め（ドキュメントや Skill に書く方針・決まり）の変更には使わない（その場で直してよい。`workflow.md` の「合意してから進める」。`AGENTS.md` の一覧から辿る）。**実装（アプリの実装の変更）は始めない。** 始めるのは、開発者から開始の指示があってから（決まりは `workflow.md` の「実装を始める合図」）。実装の進め方は Skill の `implement` にある。

## 手順

1. **ドキュメントを読む**。`AGENTS.md` の「作業前に必ず読むドキュメント」と、これから触るものに当てはまる実装のドキュメントを読む。
2. **頼まれたことを確かめる**。何を実現したいのか、何を決めたいのかを言い直してみる。目的が複数に読めるなら、その違いで案が変わるかを見て、変わるなら聞く。
3. **今のコードを調べる**。触る範囲のコード、そこに依存しているもの、取り決め（ドキュメントの方針）とぶつかるところを洗い出す。ライブラリなら、ライセンス、依存の数、ファイルサイズ、動く環境も見る（ライブラリを足すときの決まりは `licenses.md`）。
4. **問題点を挙げる**。取り決めとのぶつかり、壊れそうなところ、性能、拡張性、手戻りになりそうなところ。分かっていないことは、分かっていないと書く。
5. **案を立てる**。選択肢があるものは候補を並べ、推す案とその理由、影響が及ぶ範囲、選ばなかった案の理由を添える。名前が要るものは候補を複数挙げる。
6. **実装の段階を分ける**。一度に全部を変えず、区切りで止めて確かめられる大きさの段階に分け、順番と、各段階で確かめることを書く。ドキュメントの更新も段階に含める。
7. **示して止まる**。計画と、決めてほしいことを箇条書きで示して終える。答えをもらっても、それが計画への合意なのか、実装を始める指示なのかを区別する。どこまでを合図とするかは `workflow.md` の「実装を始める合図」に従い、曖昧なら始めずに「実装を始めてよいか」を聞く。

## 注意

- 調べるために試しに動かすのはよい（作業用のフォルダで、使い捨ての確認をするなど）。リポジトリのファイルは変えない。変える必要があるなら、その前に聞く。
- 示したあとに開発者の答えで計画が変わったら、変わったところだけを示し直す。
- 推す案が決まらないときは、決め打ちせずに、何が分かれば決められるかを書く。
