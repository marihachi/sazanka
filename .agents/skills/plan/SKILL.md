# 計画

実装の変更（機能の追加・変更、リファクタリング、不具合修正など）について、調べて計画を立て、開発者に案を示して決めてもらうまでの手順。取り決め（ドキュメントや Skill に書く方針・決まり）の変更には使わない（その場で直してよい。`workflow.md` の「合意してから進める」。`AGENTS.md` の一覧から辿る）。**実装（アプリの実装の変更）は始めない。** 始めるのは、開発者から開始の指示があってから（決まりは `workflow.md` の「実装を始める合図」）。実装の進め方は、振る舞いを変える変更なら Skill の `modify`、振る舞いを変えない組み替えなら Skill の `refactor` にある。

## 手順

1. **ドキュメントを読む**。`AGENTS.md` の「作業前に必ず読むドキュメント」と、これから触るものに当てはまる実装のドキュメントを読む。
2. **頼まれたことを確かめる**。何を実現したいのか、何を決めたいのかを言い直してみる。目的が複数に読めるなら、その違いで案が変わるかを見て、変わるなら聞く。作業の種類（機能の追加・変更、リファクタリング、不具合修正など）も見極める。種類で調べることと実装を進める Skill が変わるため。
3. **今のコードを調べる**。触る範囲のコード、そこに依存しているもの、取り決め（ドキュメントの方針）とぶつかるところを洗い出す。種類ごとに、次のことも調べる。
   - 不具合修正: 再現する手順、原因（症状が出る場所ではなく、元になっている場所）、同じ原因でほかに壊れているところ、再発を防ぐテスト。再現できなければ、そう書く。
   - リファクタリング: Skill の `refactor` の「計画で調べること」。
   - ライブラリの導入: ライセンス、依存の数、ファイルサイズ、動く環境（ライブラリを足すときの決まりは `licenses.md`）。
4. **問題点を挙げる**。取り決めとのぶつかり、壊れそうなところ、性能、拡張性、手戻りになりそうなところ。分かっていないことは、分かっていないと書く。
5. **案を立てる**。決めることを挙げ、誰が決めるかで扱いを分ける。どれを開発者が決めるかは `workflow.md` の「合意してから進める」にある。
   - 開発者が決めるもの（データの形式、画面、ファイルの構成やファイル名など）: 選択肢を並べ、推す案とその理由、影響が及ぶ範囲、選ばなかった案の理由を添えて、選んでもらう。名前なら候補を複数挙げる。
   - エージェントが決めてよいもの（コードの中の名前、関数の分け方、データの渡し方など）: 決めて、決めた内容とその理由、選ばなかった案を示す。
   - リファクタリングなら、Skill の `refactor` の「計画で調べること」にある構成案の形（ファイルごとに置くものと import するもの）で示す。
6. **実装の段階を分ける**。一度に全部を変えず、区切りで止めて確かめられる大きさの段階に分け、順番と、各段階で確かめることを書く。ドキュメントの更新も段階に含める。振る舞いを変える変更と組み替えが両方あるなら、別の段階に分ける。
7. **示して止まる**。計画と、決めてほしいことを箇条書きで示して終える。実装を進める Skill（`modify` か `refactor`）も書く。答えをもらっても、それが計画への合意なのか、実装を始める指示なのかを区別する。どこまでを合図とするかは `workflow.md` の「実装を始める合図」に従い、曖昧なら始めずに「実装を始めてよいか」を聞く。

## 注意

- 調べるために試しに動かすのはよい（作業用のフォルダで、使い捨ての確認をするなど）。リポジトリのファイルは変えない。変える必要があるなら、その前に聞く。
- 示したあとに開発者の答えで計画が変わったら、変わったところだけを示し直す。
- 推す案が決まらないときは、決め打ちせずに、何が分かれば決められるかを書く。
