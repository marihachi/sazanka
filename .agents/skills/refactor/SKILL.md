# リファクタリング

責務の考え方、どう分けるか、どこに寄せるかの判断基準は [コードの置き場所の決め方](../../../docs/agent/code-placement.md) にある。始める前にそれを読む。ここには進め方を書く。

## 手順

1. **範囲と目的をはっきりさせる**。どのフォルダ・どの関心を対象にするか、今どこが読みにくいのか。目指すのは読みやすさで、コードの短さや共通化の多さは目的にしない。
2. **今の構成を把握する**。[ソースの構成](../../../docs/agent/structure.md)と、`engine/` 各ファイル先頭の責務コメントを読む。
3. **責務の混ざりを洗い出す**。ファイルごとに「直すことになる理由」を挙げ、1つにまとまらないものを見つける。概念の近さではなく、直す理由と「何を知る必要があるか」で見る。
4. **新しい構成案を示して合意を取る**。ファイルごとに、置くもの（型・関数・定数）と import するものを挙げて開発者に見せる。名前は候補を複数挙げて選んでもらう。ここで合意してから次へ進む。
5. **振る舞いを変えずに移す**。移動・改名と、機能の変更を混ぜない。1ファイルずつ移し、そのたびにテストを通す。
6. **付随して直すものを拾う**。
   - `engine/` の各ファイル先頭の責務コメント（近い責務が別ファイルにあるなら、その置き場所も）。
   - テストのファイル名と置き場所（対象と同じフォルダ・同じ名前）。
   - [ソースの構成](../../../docs/agent/structure.md)の記述。
   - フォルダ内・フォルダ間の依存の向き。循環したら、まず責務の境界を引き直せないかを考える。
7. **確認する**。`npm run check`、`npx tsc -b`、`npm test`、`npx vite build`。画面に関わる部分を動かしたなら、ブラウザでも確かめる（Skill の `browser-check`）。
8. **報告する**。移したものと、見たが移さなかったものを分けて伝える。移さなかった理由も書く。

## 注意

- 移動の前後で結果が変わらないことを確かめたいときは、移動前のコードと突き合わせる使い捨てのテストを書いてよい。確認できたら消す。
- 開発者が手で直した箇所を、整理のついでに元に戻してしまわないよう気を付ける。始める前に `git diff` と `git log` で、直近に手が入った箇所を見ておく。
- ファイル名と中身がずれたら、どちらかを直す。名前を変えるときも候補を複数挙げる。
