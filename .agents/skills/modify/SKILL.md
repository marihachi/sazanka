# 変更

合意した計画を、段階に分けて実装する手順。対象は、振る舞いを変える変更（機能の追加・変更、不具合修正）。振る舞いを変えない組み替え（リファクタリング）は Skill の `refactor` で進める。始めるのは、開発者から開始の指示があってから（決まりは `workflow.md` の「実装を始める合図」。`AGENTS.md` の一覧から辿る）。計画は Skill の `plan` で立てる。

## 手順

1. **計画を確かめる**。合意済みの計画があるかを確かめる。なければ Skill の `plan` で計画を立て、示して止まる。
2. **合図と範囲を確かめる**。開発者の指示が、実装を始めることをはっきり言っているかと、今回始めてよい範囲（全部か、ある段階までか）を確かめる（`workflow.md` の「実装を始める合図」）。曖昧なら始めずに聞く。
3. **ドキュメントを読む**。触るものに当てはまる実装のドキュメントを読む（`AGENTS.md` の一覧）。
4. **不具合修正なら、直す前に再現する**。計画にある手順で不具合が起きることを確かめる。できれば、不具合で失敗するテストを先に書く。再現できなければ、直さずに報告する。
5. **段階ごとに実装する**。計画の段階の順に進める。途中で計画を変えたくなったら、勝手に変えずに止めて示す。範囲の外の直したいところに気付いたら、直さずに報告に挙げる。
6. **段階ごとに確かめる**。整形、Lint、型、テスト、ビルドを通す（コマンドは `workflow.md`）。不具合修正なら、4 で書いたテストが通ること、再現の手順で不具合が起きなくなったことも確かめる。
7. **ドキュメントを合わせる**。触った部分のドキュメントを今のコードに合わせ、決めたこと、選んだ理由、落とし穴、触ると壊れるものを書く（書き方は `documentation.md`。`AGENTS.md` の一覧から辿る）。
8. **区切りで止める**。段階が終わったら、やったこと、確かめたこと、次の段階、決めてほしいことを報告し、次の段階の指示を待つ。まとめて進めてよいと言われているなら、止まらずに次の段階へ進む。
9. **動作を確かめる**。画面や操作に関わる変更は、実装が一通り終わったところでブラウザで確かめる（Skill の `browser-check`）。作業の区切りなら、荒い操作のテストも行う。途中の段階ごとに確かめるかは、開発者の指示に従う。
10. **報告する**。やったこと、確かめたこと、確かめられなかったこと、気になる動き、決めてほしいことを分けて書く。コミットは頼まれたときだけ行う。

## 注意

- 確かめて NG が出たら、直す前に、確認の手順の誤りではないかを見る。直したら、関係する確認をやり直す。
- 変更前のコードでも同じことが起きるかを確かめると、自分の変更で壊したのか、元からなのかを切り分けられる。
- 不具合修正では、症状を抑えるだけの直し方（特定の値だけを避けるなど）をしない。原因が計画と違っていたら、止めて示す。
- 機能の変更と組み替えを混ぜない。組み替えが要ると分かったら、止めて示す。
- 実装の途中で開発者から止めるよう言われたら、すぐ止め、どこまで進んでいるかを報告する。
